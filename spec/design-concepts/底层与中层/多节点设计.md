# 多节点设计（5 role）

> 版本：v8
> 日期：2026-09-14
> 状态：Normative（5 role 拓扑与职责、token↔主机边界、per-role 文件根的唯一口径）
> Supersedes：v7（连接数量与复用拓扑唯一 owner、spectre 提交态）
> 关联：字段定义见[配置一览 §2](../总览/配置一览.md)；接口基线见[三层整体架构设计 §4](../总览/三层整体架构设计.md)；并发与预算见[并发处理设计](并发处理设计.md)

## 1. 定位与边界

本版保留 **5 个 role**：`gui`、`daemon`、`command`、`file`、`spectre`。一个注册账号（token）最多可以连向五个不同目标。

**忠实投送原则（本设计的最高准则）**：bridge 只负责把指令或文件**正确投送到用户指定的目标位置**，并如实返回结果。

- bridge **不判断、不校验、不假设** role 之间是否在同一台主机、是否同账号、是否共享文件系统；
- 主机相同与否不是 bridge 要考虑的问题；用户给出什么目标，就忠实投送到什么目标；
- 由此产生的拓扑合理性（例如 CIW 与 daemon 是否同机、部署路径是否对 GUI 可见）属于**用户的拓扑责任**，bridge 只通过注册探测把"目标是否可用"如实报告给用户。

这条准则同时是评审 P0-01 的关闭口径：规范不再承诺"gui 与 daemon 必须同机"，也不再假设；bridge 按配置投送。

## 2. 五个 role 的职责

| role | 职责 | 被哪个接口消费 | 额外字段 |
|---|---|---|---|
| `gui` | Virtuoso CIW / X11 所在主机；执行 GUI 侧一次性命令（窗口枚举、dismiss、bootstrap 等） | **GUI 命令执行**（一次性） | — |
| `daemon` | SKILL daemon 监听主机；bridge 文件的部署目标 | **Skill 执行**（隧道到 daemon） | `daemon_port`、`local_port` |
| `command` | 通用命令执行主机（默认常驻 shell；`parallel=True` 走一次性 exec） | **命令执行** | — |
| `file` | 文件传输目标主机（上传/下载） | **文件执行** | — |
| `spectre` | Spectre 执行主机；给上层预留（上层未来经 **Spectre 命令执行** 调用 spectre） | **Spectre 命令执行**（一次性） | `bin`（可选记录） |

### 1.1 token 与主机边界（唯一口径）

- 一个 token 拥有**五个 role**，这些 role **可以分布在多个主机**（含混合 local/remote）；bridge 不因为 role 跨主机而拒绝注册或拒绝投送；
- 一个 token **只允许一个 daemon role、一个活动 daemon、一个 CIW**：daemon 是本版唯一“单实例”资源，第二处 `load` 同一 token 属于配置错误；需要第二个 CIW 时注册第二个 user/token；
- 除 daemon 之外，command / file / gui / spectre 各自可以是不同主机、不同账号、不同跳板，彼此不需要同机、同账号或共享文件系统；
- 该边界是[多用户设计 §10](多用户设计.md)遗留项表的唯一依据；其它文档不得再出现“一个 token 多主机：不支持”这类无限定的表述。

每个 role 都拥有 `mode / host / user / jump_host / jump_user / proxy / root` 七个字段：`role.<name>.mode=local` 表示客户端（中层）就在该 role 的目标主机上、直接本地执行、不经 SSH；`mode=remote` 表示经 SSH 投送到该 role 的 host/user。**不同 role 可以混合 mode**（例如客户端就在 daemon 主机上 → daemon=local、command/file=remote）。未填字段按[配置一览 §2.3.1](../总览/配置一览.md)逐字段回退全局默认（`mode` 回退 `mode.default`，连接字段回退 `ssh.default.*`，**文件根回退 `root.default/<role>`**）。字段结构与默认值不在本文重复。

## 3. 五个接口与 role 的对应关系

上层可用的操作接口共 **5 个**（详见[三层整体架构设计 §4.1](../总览/三层整体架构设计.md)）：

| # | 接口 | 目标 role | 执行形态 |
|---|---|---|---|
| 1 | Skill 执行 | `daemon` | 隧道 → daemon → Virtuoso（串行语义） |
| 2 | 命令执行 | `command` | 默认常驻 shell；`parallel=True` 一次性 exec |
| 3 | 文件执行（上传/下载） | `file` | 每次传输一个一次性通道 |
| 4 | GUI 命令执行 | `gui` | **一次性命令**（不建常驻 shell） |
| 5 | Spectre 命令执行 | `spectre` | **一次性命令**（不建常驻 shell） |

**GUI / Spectre 命令的本质**：它们是"用并行模式执行命令"——每次调用在对应 role 上执行一条一次性（one-shot）命令，不建立常驻会话、不保留 cwd/env，等价于 `parallel=True` 的命令语义。两者同样占用该 token 的 channel 预算（见[配置一览 §2.2](../总览/配置一览.md)与[并发处理设计](并发处理设计.md)）。

- GUI 命令用于 X11/窗口/CIW 相关的一次性操作；
- Spectre 命令用于 `spectre` 可执行文件的调用；`bin` 字段在注册期记录，供上层拼命令时使用；
- 两条通道都不经过 daemon，也不经过 Virtuoso 求值。

## 4. 注册阶段的探测合同

第三步探测**按 role 实际配置逐项执行**：`mode=local` 的 role 在客户端本机执行等价检查，`mode=remote` 的 role 通过 SSH 执行。每个 role 都必须探测"命令可用性"（一次性 `echo` 探测），并按对应功能补充专项探测（下表的 SSH/host-key 仅对 `mode=remote` 的 role 适用）：

| role | 命令可用性（必测） | 专项探测 | 失败级别 |
|---|---|---|---|
| `gui` | ✅ 一次性命令 | SSH 可达 + host-key；`role.gui.root` 可写 | ERROR |
| `daemon` | ✅ 一次性命令 | SSH 可达 + host-key；`role.daemon.python`；`daemon_port` 空闲；`role.daemon.root` 可写 | ERROR |
| `command` | ✅ 一次性命令（即命令冒烟） | SSH 可达 + host-key；`role.command.root` 可写 | ERROR |
| `file` | ✅ 一次性命令 | SSH 可达 + host-key；`role.file.root` 可见、可写 | ERROR |
| `spectre` | ✅ 一次性命令 | SSH 可达 + host-key；`role.spectre.root` 可写；`bin` 显式校验/自动探测 | **WARNING（不阻断）** |

- "命令可用性"= 在目标 role 上成功执行一条一次性命令（例如 `echo vb-ok`）并拿到预期输出；
- `spectre` 的探测失败只产生 WARNING，不阻断注册（本版口径不变）；失败时该 role 的 `root`/`expected_fingerprint`/`bin` 在提交态为 `null`；
- 其余四个 role 的任一项失败 → 注册在该步失败，不落盘；
- 探测使用与运行期相同的一次性命令路径，避免"探测能过、运行不通"。

## 5. 部署与文件根（每 role 独立）

**每个 role 都有自己的文件根（root），该 role 的所有文件需求都在自己的根下处理。** 采用"全局默认 + 显式覆盖"：

### 5.1 默认与覆盖规则（唯一算法）

根的计算**与 role 的 mode 无关**，只与“该 role 实际在哪台机器上工作”有关：

1. **基准**：`root.default` 未显式提供时等于 `~/.virtuoso-bridge/<userid>`；`~` 与 `<userid>` 都在**该 role 实际工作所在机器**上解释（`<userid>` = 注册表用户名，机器上使用哪个账号由该 role 的连接/运行账号决定）：
   - `mode=remote`：`~` 是该 role SSH 登录账号的 HOME；
   - `mode=local`：`~` 是运行中层的账号的 HOME；**不是**客户端传入的本地工作目录，也不是 registry 所在目录；
   - 两种 mode 的默认形状相同——在哪个机器上工作，就在哪个机器上建工作目录。
2. **role 根**：`role.<name>.root` 未显式配置时 = `<root.default>/<role>`；显式配置时**该值就是最终根**，不再追加用户名或 role 名。
3. **`~` 展开**：只在访问文件系统时展开，展开主体必须是该 role 实际使用的账号；`~` 无法解析属于路径错误（`VB-PATH-NOT-VISIBLE`），**不得**退化成字面 `~` 目录。
4. **注册表存什么**：未显式提供时 `root.default` 存空值（表示“用默认”）；注册探测完成后把**展开后的绝对路径**写回各 role 的 `root`，运行期不再重新解析 `~`、也不依赖远端环境变量。
5. **统一的路径解析**：各 role 的初始 cwd 与 `remote_path` 相对路径**共用同一个解析函数**——绝对路径原样使用；相对路径 = 该 role 的最终根 + 相对路径；`~` 开头按第 3 条展开。任何一层都不得另写一套解析。

### 5.2 各 role 的根各管什么

| role | 根里放什么 | 谁使用 |
|---|---|---|
| `daemon` | `ramic/`、`setup/`、`status/`（bridge 部署文件） | 部署 + Skill（il/daemon 路径） |
| `command` | 命令的初始工作目录与工作文件 | 命令执行 |
| `file` | 上传/下载的默认落点 | 文件执行 |
| `gui` | GUI 命令的初始工作目录与工作文件 | GUI 命令执行 |
| `spectre` | Spectre 命令的初始工作目录与工作文件 | Spectre 命令执行 |

- 相对路径按**目标 role 的根**解析；绝对路径不受限制；
- 常驻 shell（command role）建立时以该 role 的根作为初始 cwd，之后的 `cd` 属于会话状态；
- 各 role 的根互相独立：**bridge 不要求、也不检查任何两个 role 之间共享目录或互相可见**。

### 5.3 同主机时的自然结果（示例）

假设 roleA 的根 = `scratchroot/A`，roleB 的根 = `scratchroot/B`，roleC 的根 = `scratchroot/C`：

- 若 roleA 与 roleB 配到同一台主机：该主机 `scratchroot/` 下同时存在 `A/` 与 `B/` 两个目录，各自独立；
- roleC 在另一台主机：那台主机只存在 `scratchroot/C/`；
- bridge 不因此做任何"合并/共享"判断——它只是忠实投送到各自配置的根。

### 5.4 部署

- bridge 文件（daemon / il / setup）**只部署到 `daemon` role 的根**（`role.daemon.root`），上传动作走 daemon role 的连接；
- bridge **不检查**该根是否对 `gui` 可见：CIW 能否 `load` 该路径由用户拓扑负责（忠实投送原则）；
- 其余 role 的根不接收 bridge 部署文件，只承载各自的工作文件。

## 6. endpoint 与连接复用（索引）

- endpoint = 一个 **`mode=remote`** 的 role 解析后的 `(host, user, jump_host, jump_user, proxy)`；`mode=local` 的 role 没有 endpoint、不建 SSH 连接；
- **endpoint canonical key 的唯一 owner 是[配置一览 §6.5](../总览/配置一览.md)**（含规范化规则与测试向量），本文不复制算法；
- **连接数量与复用的唯一口径（本文为 owner）**：同一 token 内解析后相同的 endpoint 持有一条**业务连接**（backend 内多 channel 复用；`backend=openssh` 时该连接可启用 ControlMaster，`backend=paramiko` 时为其 transport）；**remote daemon role 另持有一条专用 Skill tunnel**（外部 `ssh -N -L`，不经过业务连接）；local role 无 SSH 连接。不同 endpoint 各自建连，跨 token 永不共享；生命周期（建连/重试/关闭）见[并发处理设计 §4](并发处理设计.md)。
- 线程池与 channel 预算每 token 一份（记账矩阵见[并发处理设计 §3](并发处理设计.md)），预算不因 role 数量而增加。

## 7. 本设计明确不做的事

1. **不做 role 间 mode 一致性约束**：允许 daemon=local 而 command=remote 这类混合拓扑，bridge 按每个 role 自己的 mode 忠实投送；
2. **不实现跨机启动 daemon 的协议（本版不做；未来版本 daemon 可能支持在其他节点启动）**：mpsserver / 远程 launcher 等均不在本版范围内。**当前版本 daemon 是 CIW 的本地 `ipcBeginProcess` 子进程**；启动方式与运行账号由站点拓扑决定，bridge 只忠实投送与连接、不参与也不校验：注册第四步结束后由用户自己 `load` 并拉起 daemon，bridge **不判断用户是否拉得起来**，只要求在第五步能**观察到**它（详见[多用户设计 §3.2](多用户设计.md)）。未来若支持其他节点启动，属于 daemon 侧能力扩展，不改变 5 role 与忠实投送原则；
3. **不校验 role 之间的主机/账号/路径一致性**：相同或不同都不影响 bridge 行为；
4. **不保证跨主机的文件可见性**：可见性由用户在注册探测中看到结果并自行负责；
5. **不提供 GUI/Spectre 的常驻会话**：两者只有一次性命令形态；
6. **接口总数固定为 5**：GUI 命令与 Spectre 命令是第 4、第 5 个接口，不是注册字段或后续能力，也不存在第 6 个接口。
