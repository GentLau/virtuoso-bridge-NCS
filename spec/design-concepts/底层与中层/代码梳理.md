## 1. 旧执行机制（逐条核对结果）

本节保留原文档的旧链路描述，并标注逐条核对结果：✅ = 与 `src_bak/` 一致；⚠️ = 大体正确但原文有细节偏差；❌ = 仓库无法支持该说法。

### 1.1 Skill 链路（旧）

```text
上层
 └─ VirtuosoClient.execute_skill(skill_code, timeout)
      └─ TCP 连 localhost:port（本地 daemon 或 SSH 隧道）
         请求 {"skill": ..., "timeout": ...}，SHUT_WR，读到 EOF
              └─ daemon（ipcBeginProcess 在 CIW 中拉起）
                   单行：let(((__vb_r <skill>)) hiFlush() __vb_r)\n
                   多行：临时 .il + load("...il") hiFlush() _vb_eval_result\n
                   watchdog 超时 → SIGINT
                   读 il 回包 STX/NAK + payload + RS，原样回 TCP
                       └─ ramic_bridge.il（CIW 内）
                            evalstring(strcat("(progn " data ")"))
                            成功：02 + %L result + 1e
                            失败：15 + errset.errset + 1e
      中层 _parse_response：02→SUCCESS，15→ERROR → VirtuosoResult
```

核对结论：

- ✅ `VirtuosoClient.execute_skill` → `_execute_skill_once`；payload 恰为 `{"skill": ..., "timeout": ...}`；`sendall` 后 `shutdown(SHUT_WR)`，再读到 EOF（`src_bak/virtuoso_bridge/virtuoso/basic/bridge.py:313/1440`）。
- ✅ daemon 收到 EOF 后 `json.loads`；单行/多行包装字符串与上图一致；多行临时文件内容为 `_vb_eval_result = progn(...)`（`src_bak/.../basic/resources/ramic_bridge_daemon_3.py:160-201`；`_27.py` 同构）。
- ✅ watchdog 超时向 Virtuoso 进程（daemon 的祖父进程）发 `SIGINT`，并回 `\x15TimeoutError`。
- ⚠️ “读 il 回包 STX/NAK + payload + RS，原样回 TCP”不精确：旧 `read_until_delimiter` 返回“起始标记 + payload”，**不包含结尾 RS**；RS 是 CIW→daemon 的帧尾，daemon 回 TCP 时已剥掉（`ramic_bridge_daemon_3.py:110-156`）。
- ✅ `ramic_bridge.il` 的 `evalstring(strcat("(progn " data ")"))`、`02+%L+1e`、`15+errset.errset+1e` 均与原文一致（旧 `ramic_bridge.il:84-90`）。
- ⚠️ `_parse_response` 的“02→SUCCESS、15→ERROR”只是主干；旧实现另有两条分支：空回包→ERROR、含 `TimeoutError`→ERROR；**没有 STX/NAK 标记的裸文本会被当作 SUCCESS 并附 warning**，而不是 ERROR（`bridge.py:1486`）。
- ✅ 关键事实均成立：一条 TCP 连接一个请求/响应、EOF 分帧；daemon 单线程 `accept()` 且 `listen(1)`；`printf` 不回 RPC；daemon 不执行 shell、不传文件。
- 现状变化：新 `SkillClient` 请求已加 `token/log_level/log_max_bytes`，回包改为 `02/15 + JSON {"value"|"error","log"} + 1e`；daemon `listen(128)`，中间层在客户端侧加 per-token 投递闸门（见 §3）。

### 1.2 命令 / 文件链路（旧）

```text
SSHClient（解析 GUI/Deploy/Daemon/Spectre/Jump 角色）
  ├─ run_command：persistent shell（base64 分 stdout/stderr/rc）
  │               失败回退 ControlMaster / 一次性 ssh sh -l，重试 transient/CM 错误
  ├─ upload/download：tar/scp 计划 + staging + 原子安装；目录走 tar 管道
  ├─ ensure_remote_setup：检测远端 python → 上传 daemon/il → 生成 setup il（setShellEnvVar）
  └─ ensure_tunnel：ssh -L 端口转发；state.json 记录端口/tunnel PID
```

核对结论：

- ✅ `SSHClient.from_env` 经 `remote_host_roles_from_os()` 解析 legacy/GUI/deploy/daemon/spectre/jump；`_new_role_runner` 为每个远端角色建独立 `SSHRunner`，并向 `SSHRunner` 传 `persistent_shell=True`（旧 `transport/tunnel.py:158-272`；`SSHRunner` 在 paramiko 后端、Windows+jump 场景会自行禁用）。
- ⚠️ 原图遗漏一个分支：旧 `SSHRunner.run_command` **先判断可选 paramiko 后端**，启用时直接走 `ParamikoSessionBackend.run_command`，不用 persistent shell；默认后端仍是 openssh（旧 `transport/ssh.py:676`）。persistent shell 协议确实用 stdout/stderr base64 + rc 分隔标记；失败回退 `ssh host sh -l` 一次性命令，并重试 transient/ControlMaster 错误。
- ✅ `upload/download`：单文件走 tar 管道/scp、目录走 tar；`transfer.py` 生成带 staging 目录、sha256 校验与原子安装的计划（旧 `transfer.py:84-398`）。
- ✅ `ensure_remote_setup`：`_detect_remote_python` → `upload_text` daemon/il → `_generate_virtuoso_setup_il` 写 `setShellEnvVar("RB_*")`；并做 daemon/GUI 可见性检查（旧 `tunnel.py:422-552`）。
- ✅ `ensure_tunnel`：`SSHRunner.start_port_forward` 实际命令为 `ssh -N -L <local>:127.0.0.1:<remote>`，显式关 ControlMaster；端口冲突时递增本地端口并回写 `.env` 的 `VB_LOCAL_PORT`；`save_state` 写 `state_{profile}.json`，字段含 `mode/port/tunnel_pid/daemon_host/setup_path/...`（旧 `ssh.py:439-598`、`tunnel.py:604-718/767-834`）。
- ✅ local 模式结论成立：`daemon_host=localhost` 不建 SSH；`ensure_local_setup` 把资源复制到 `state_dir()/local[_<profile>]`；旧 `VirtuosoClient.upload_file/download_file` 在无 `ssh_runner` 时用 `shutil.copy2/copytree` 本地复制（旧 `bridge.py:740-835`）。

### 1.3 配置 / 状态（旧）

- ✅ `env.py`：`.env` 查找顺序（显式 → 向上走目录找含 `VB_*` 的 `.env` → `~/.virtuoso-bridge/.env`），`load_dotenv` 加载 `VB_*`。
- ✅ `profile.py`：profile 解析顺序（显式 → `VB_PROFILE` → `--env` → venv 绑定文件 → 用户 `.env` → None）与 venv 绑定 `.virtuoso-bridge-profile`。

- ✅ `tunnel.py::save_state/read_state`：每 profile 一份 `state.json`（另有 `~/.cache` 旧位置兼容读取）。
- ✅ `daemon_guard.py`：事后查 `getShellEnvVar("USER")` 比较 `VB_REMOTE_USER`，以及比较 daemon banner hostname 与隧道端点 hostname；可用 `VB_ALLOW_CROSS_USER_DAEMON` 覆盖。
