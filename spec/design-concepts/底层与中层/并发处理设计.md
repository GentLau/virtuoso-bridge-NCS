## 1. 要解决的问题

**目标**：非阻塞式运行——不同用户同时发起请求时并发执行，谁先完成谁先返回。

**事实边界**：单个 daemon（= 单个 Virtuoso CIW 会话）是串行的，一次只能执行一条 SKILL。这是 Virtuoso 的语义，不可改变，也不应改变。

本文档解释：在"单通道串行"的前提下，**跨通道的并发为什么成立、如何成立、要守住什么纪律**。

---

## 2. 一次请求的完整旅程

先看一条 `execute_skill` 请求从发出到返回，一路上经过什么：

```text
上层服务（你的机器）
  │ ① 线程 T 从 session 池拿到 alice 的连接对象
  │ ② T 建立 TCP 连接: 127.0.0.1:65082（本地隧道端口，微秒级）
  │ ③ T 发送 JSON{skill, token}，然后进入 recv() 等待
  ▼
SSH 隧道进程（长驻，ssh -N）
  │ ④ 隧道进程把字节流转发到远端（内核转发，不占任何线程）
  ▼
远端 daemon 进程（alice 的独立 Python 进程）
  │ ⑤ accept() 接住连接，读 JSON，比对 token
  │ ⑥ 把 SKILL 写到 stdout 管道，等待 SKILL 回包
  ▼
CIW（Virtuoso）
  │ ⑦ evalstring 执行 SKILL（秒 ~ 分钟）
  │ ⑧ 结果经 stdin 管道回给 daemon
  ▼
返回路径 ⑥→④→③ 逆序回传
  │ ⑨ 内核唤醒线程 T：recv() 返回数据
  │ ⑩ T 解析结果，返回给上层调用者
```

**关键观察**：从 ③ 到 ⑨，线程 T 全程"睡觉"——它不占 CPU、不占任何共享资源，只是被操作系统内核挂起，等那个 socket 上有数据到达。

## 3. 三个参与者各自的并发角色

### 3.1 底层：daemon 是独立进程，并发由 OS 调度

每个用户的 daemon 是 `ipcBeginProcess` 拉起的**独立 OS 进程**：

```text
远端主机上的进程列表：
  PID 1234  virtuoso          ← alice 的 CIW
  PID 5678  ramic_bridge_daemon_3.py  ← alice 的 daemon（CIW 的子进程）
  PID 5679  ramic_bridge_daemon_3.py  ← bob 的 daemon（bob 的 CIW 的子进程）
  ...
```

- 每个 daemon 有自己的**内存空间**、自己的 socket、自己的 accept 循环；
- 它们由远端主机内核**独立调度**，一个忙不阻塞另一个；
- 所以"alice 的 SKILL 跑 10 分钟"和"bob 的 SKILL 跑 1 秒"在远端是**真并行**的——两个进程、两个 CIW、两套人马。

**进程隔离是并发的地基。** 这个架构天生就是多进程的，不需要桥做任何事。

### 3.2 中层：隧道进程多路复用，转发不占线程

`ssh -N -L 65082:...:65081` 的隧道进程长驻。它对并发的作用：

- 隧道进程自己内部用 select/poll 同时监听**所有**端口转发；
- 字节流到达任一转发端口，立即转发，**不占桥的任何线程**；
- 6 个用户的 6 路数据流过同一条隧道，是内核 + sshd 的多路复用，与桥无关。

**隧道是纯管道，天然并发。**

### 3.3 上层：每个请求一条线程，等待期间不占 GIL

服务形态下，每个请求分一条线程（thread-per-request）：

```text
请求(token=A) ──► 线程 T1 ──► session_A ──► 127.0.0.1:65082
请求(token=B) ──► 线程 T2 ──► session_B ──► 127.0.0.1:65083
...
```

线程 T1 进入 `recv()` 等待后，**GIL（全局解释器锁）被释放**，其他线程可以执行。这就是 Python 线程模型能支撑并发的关键：

> GIL 只串行化"计算"，不串行化"等待"。bridge 的负载 99.9% 是等待（等 daemon、等 SSH、等文件），所以 GIL 的影响可忽略。

## 4. Python 内部运行机制详解

### 4.1 GIL：同一时刻只有一个线程执行 Python 字节码

CPython 的解释器有一个全局锁（GIL），确保同一时刻只有一个线程在跑 Python 代码。**但是**：

| 操作类型 | GIL 行为 |
|---|---|
| 计算（解析 JSON、拼字符串、算 hash） | 持锁，串行 |
| I/O 等待（`recv()`、`read()`、`waitpid()`） | **立即释放锁**，线程被内核挂起 |

### 4.2 时间线：6 个请求的真实交错

```text
时刻轴（示意，单位非精确）：

t=0    T1 拿 GIL: 拼 JSON → 发请求 → 调 recv() 阻塞 → 释放 GIL
t=1ms  T2 拿 GIL: 拼 JSON → 发请求 → 调 recv() 阻塞 → 释放 GIL
t=2ms  T3 ... T6 同样走一遍（每人只占 GIL 约 1 毫秒）
t=3ms  全部 6 条请求都已发出，6 个线程全部阻塞在各自的 socket 上
       此刻 Python 进程里没有任何线程在跑代码——全部在内核里"睡觉"

t=30s  T3 的 socket 有数据到达 → 内核唤醒 T3 → T3 拿 GIL 解析 → 返回
t=1min T2 的 socket 有数据到达 → 内核唤醒 T2 → 返回
t=10min T1 的 socket 有数据到达 → 内核唤醒 T1 → 返回
```

**结论**：计算串行（微秒~毫秒级），等待并行（秒~分钟级）。并发吞吐由"等待"决定，而等待是并行的，所以整体是并发的。

### 4.3 为什么不用 asyncio

asyncio（单线程事件循环 + 协程）理论上更省内存，但对本项目不适用：

- `paramiko`（SSH 库）是**同步阻塞**的——直接放进协程会卡死整个事件循环；
- `subprocess` 同理；
- 标准解法是把它们丢进线程池（`run_in_executor`），结果还是线程。

**v1 决定**：线程模型。所有依赖都是阻塞库，线程 + GIL 的等待释放行为已经够好。

## 5. 单通道串行的精确机制

### 5.1 daemon 的 accept 循环

```text
daemon 主循环（单线程）：
  while True:
    conn = s.accept()          ← 从内核积压队列取一个连接
    data = conn.recv(...)      ← 读请求
    send_to_skill(data)        ← 写 stdout 管道给 CIW
    result = wait_skill()      ← 等 SKILL 执行完（期间什么都做不了）
    conn.sendall(result)       ← 回传
    conn.close()               ← 处理下一个
```

### 5.2 同 token 的两个并发请求会发生什么

```text
t=0    T1 的 TCP SYN 到达 → 三次握手 → 连接进入 daemon 的积压队列
t=0    T3 的 TCP SYN 到达 → 三次握手 → 也进入积压队列
       （握手由内核完成，daemon 根本还没 accept）

t=0.1  daemon accept 第一个连接（T1），开始处理，T3 在队列里挂着
t=10min T1 完成 → daemon accept 第二个连接（T3），开始处理
```

**两个关键点**：

1. **排队而非报错**——前提是积压队列没满。TCP 的 listen backlog 决定了队列深度，当前实现 `listen(1)`，积压上限很小；
2. **超限会报错**——若同 token 并发请求超过 backlog，新连接的 SYN 被内核**直接 RST**，客户端得到"Connection refused"。这是 TCP 语义，不是 Python 行为。

### 5.3 对上层的要求

| 情形 | 处置 |
|---|---|
| 同 user 低并发（≤ backlog） | 自然排队，无需任何机制 |
| 同 user 高并发（> backlog） | 上层**限流**（每 user 并发上限 = backlog 容量），或接受 refused 并重试 |
| 不同 user 并发 | 互不影响，各自队列各自排 |

## 6. 并发安全纪律（server 形态的硬要求）

服务形态下，线程安全不是可选项。三条纪律：

| 纪律 | 内容 | 违反后果 |
|---|---|---|
| **注册表只读共享** | 冷启动读一次 → 固化进连接对象内存；连接建立后不再访问注册表 | 若线程内反复读写，需要加锁；不加锁则数据竞争 |
| **连接对象实例私有** | 每个 session 的 socket / SSH channel / 隧道引用**只属于该 session** | 两线程共用一个 socket 会交错读写、响应串包 |
| **禁止模块级可变全局状态** | 不允许"当前用户""当前端口"这类全局变量 | 线程 A 改全局配置，线程 B 立刻受害——**旧架构 `.env` 全局状态模型进不了服务形态的根因** |

**对照旧架构**：旧代码的配置在环境变量和模块级变量里，天然假设"一个进程服务一个连接"。新设计的 token→session 对象模型把状态全部收进实例，服务形态自然成立。

## 7. 服务形态的两个补充（并发成立的必要条件）

并发框架是**结构性天生的**（进程隔离 + I/O 等待释放 GIL），但要真正跑好，需要补两块：

### 7.1 session 连接池（避免每请求 SSH 重握手）

| 连接种类 | 建立成本 | 是否需池化 |
|---|---|---|
| execute_skill 的 TCP（连隧道端口） | 微秒级 | 不需要（短连接即可） |
| SSH 会话（跑命令的 shell） | **秒级握手** | **必须池化** |

复用机制现有代码已具备：**ControlMaster**（同 host 所有 ssh 调用共享一条 TCP）+ **persistent shell**（复用远端常驻 shell），并有三级降级（persistent shell → ControlMaster → 裸 ssh）。server 化需要补的是**池化调度层**：按 user 找已有实例、没有才建、建了存起来、断了重建。

### 7.2 同 token 限流/重试（backlog 有限的现实）

见 5.3——排队是 TCP 语义，报错是超限语义，两者都要被上层显式处理。

---

## 8. 一句话总结

> 并发的地基是**进程隔离**（N 个 daemon = N 个 OS 进程，真并行）；并发的通道是**内核调度**（线程阻塞在各自 socket 的接收队列上，数据到达才唤醒）；并发的代价是**零**（等待期间 GIL 释放，计算只占微秒）；要守住的纪律是**无共享可变状态**（注册表只读、连接私有、禁全局变量）。服务形态补上 session 池和同 token 限流，就是完整的非阻塞多用户架构。
