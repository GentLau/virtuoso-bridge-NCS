# 上层：业务包与插件化

> 版本：Draft v14
> 日期：2026-09-17
> 状态：Normative（业务包与业务操作契约、插件注册唯一口径）
> Supersedes：Draft v12（import 白名单加入 common.*；本文收窄为 common.paths）
> 定位：五业务接口签名与错误总则见[四层整体架构与接口 §4](../总览/1-四层整体架构与接口.md)；顶层调度见[顶层 §2](../顶层/1-顶层.md)；role 与并发见[路由设计](../中层/3-路由设计.md)、[并发设计](../中层/2-并发设计.md)。

## 1. 概念

- **插件单元 = 业务包（Package）**：一个领域对象的一个或多个业务操作的集合（只有一个是正常情况），如 `schematic` 包、`netlist` 包。
- **业务操作（Operation）** = 一个操作名 + 一个方法 `method(request) -> Result`；方法把一次业务动作拆成若干步骤，业务步骤只调中层五个业务接口（参数准备可调用只读查询 `query`）。
- 例：`schematic` 业务包含 `create`、`read`、`write`、`delete` 等业务操作；`netlist.import` 业务操作内部执行 `上传网表 → Skill 导入 → Skill 建 symbol`。
- 三个不变量：**同步、无状态、token 原样透传**。

## 2. 业务操作契约

### 2.1 形态

```python
class SchematicPackage:
    def __init__(self, middle: Middle) -> None:
        self.middle = middle

    def create(self, request: SchematicCreateRequest) -> SchematicCreateResult: ...
    def read(self, request: SchematicReadRequest) -> SchematicReadResult: ...
```

### 2.2 方法契约

| 项 | 约定 |
|---|---|
| 入口 | 每个业务操作一个方法 `method(request) -> Result`；返回时业务已结束（成功或已失败） |
| 同步 | 返回时业务已结束（成功或已失败）；不返回任务句柄 |
| 无状态 | 包实例每次请求新建；中间数据不在实例属性里 |
| 注入 | 构造只接受 `Middle`；不创建连接/进程/隧道 |

### 2.3 Request / Result

- 每个业务操作一对数据类（`<操作>Request` / `<操作>Result`）；

| 字段 | 类型 | 约定 |
|---|---|---|
| `token` | `str` | 必填；每次中层调用原样透传 |
| 业务字段 | 包自定义 | 必须可序列化 |
| `ok` | `bool` | 业务是否成功 |
| `steps` | `list[dict]` | 步骤痕迹（§2.4） |
| `error` | `str` 或 `None` | 失败摘要；成功为 `None` |

### 2.4 步骤痕迹

- 每步记 `{"step": 名, "ok": 布尔, "detail": 中层结果}`；默认任一步失败即停止；业务操作可自行决定是否重试某步（条件与痕迹自行约定）；
- 保留全部痕迹；失败不得伪装成成功，也不得只留一句 `error` 丢弃步骤。

## 3. 数据纪律

### 3.1 token 与路径

- `token` 是调用中层接口的授权凭证：业务包每次调用都带上并原样透传，不缓存、不解析；合法性与路由由中层判定；
- 文件路径按业务需要给定，由中层按对应 role 根解析；**同一动作内前后要操作同一个文件时，用同一路径**；
- 需要本 token 的参数事实（`root`/`bin`）时，用[四层整体架构与接口 §4.2](../总览/1-四层整体架构与接口.md)的只读查询 `query`。

### 3.2 状态与长任务

- 不持有跨请求状态：没有内存任务表、缓存或"上次进度"；
- 需要跨请求看见的东西写到业务服务器文件，且可由请求参数确定性定位；
- 长动作拆成多次独立调用：先发起，再按调用方给的参数（如 `job`）发起查询；进度与取消由调用方经请求参数或业务服务器文件驱动，重试策略由业务操作自行决断；
- 多步 deadline 由业务操作内部自行调度：单次中层调用遵循接口 deadline（见[四层整体架构与接口 §5.8](../总览/1-四层整体架构与接口.md)）。

### 3.3 校验与错误

- 结构校验（类型、必填、范围）在 Request 构造期完成：失败抛 `TypeError`/`ValueError`，由顶层映射为 4xx（见[顶层 §3](../顶层/1-顶层.md)）；
- 领域校验失败是业务失败，写成 `Result(ok=false)`，**不得抛异常表达**；
- 下层结构化失败按错误总则处置：校验和不一致不忽略；重试策略由业务操作自行决断；中层只做传输层透明重试（见[并发设计 §4](../中层/2-并发设计.md)）；
- 失败类别枚举的唯一 owner 见[四层整体架构与接口 §4.5](../总览/1-四层整体架构与接口.md)，本文不复制。

## 4. 插件注册

### 4.1 显式注册

- **插件的登记单元是业务包，条目落在业务操作级**：`{业务操作名: (业务包类, 方法名, Request 模型)}`；注册表结构与重复登记错误由[顶层 §2.1](../顶层/1-顶层.md)唯一 owner；
- 加一个业务包 = 加一个文件 + 为该包的每个业务操作各加一行登记，不改既有业务包。

### 4.2 命名与自描述

| 项 | 约定 |
|---|---|
| 业务操作名 | 点分英文分段（领域.对象.动作）；发布后不改名 |
| 自描述 | 每个业务包导出：`Package` 类 + 每个业务操作的 `(操作名, 方法名, Request, Result)`；自描述是包级元数据，顶层注册表值仍为 §2.1 三元组（不含 Result） |

### 4.3 失败隔离

- 加载单元是业务包：加载失败即视为未加载——该包业务操作不可用（顶层按未知 operation 处理），失败信息写日志，其余包不受影响；
- 运行单元是业务操作：未预期异常只影响该次请求（见[顶层 §3](../顶层/1-顶层.md)）。

## 5. 本层不做

1. 导入/接触 `transport.*`、`socket`、`subprocess`、`paramiko`、隧道、端口、注册表、daemon 协议；
2. 读 `VB_*`/`.env`，判断 local/remote；
3. 生成随机且事后无法重建的路径。

## 6. 检查清单

- [ ] import 只有标准库、`common.paths`（共享路径基座）与 `pyapi.*`；
- [ ] 每个业务操作方法都是 `method(request) -> Result`，同步无状态；
- [ ] 每个操作一对 Request/Result，Result 含 `ok/steps/error`；失败保留步骤痕迹；
- [ ] 每次中层调用带 Request 里的 token；步骤间 deadline 由操作内自行调度；
- [ ] 同一动作内同一文件复用同一路径；
- [ ] 已显式登记，未与既有业务操作名冲突。
