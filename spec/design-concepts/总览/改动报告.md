# 改动报告：中层与底层

> 日期：2026-09-07
> 依据：[核心修改设计](核心修改.md)、[三层整体架构设计](三层整体架构设计.md)、[跨层接口协议](../../protocol-v1.md)
> 范围：只评估**中层**与**底层**。上层业务模块（schematic/layout/maestro/symbol/spectre）不在本次改动评估内。

## 1. 评估范围与方法

- 五项核心修改：并行机制、token 机制、注册表替换 profile、远端脱离环境变量、CDSlog 增量返回。
- 评估对象是当前工作树中的 `src/virtuoso_bridge/`（中层）和 `virtuoso/basic/resources/`（底层）。
- 结论按“改动位置 → 大致工作量 → 如何改 → 风险”给出，工作量用 S / M / L 表示。

## 2. 现状代码地图

## 3. 按修改项评估

### 3.1 并行机制

- **现状**：`SSHRunner.run_command()` 复用 persistent shell，命令全串行；没有 channel/线程池记账。
- **改动位置**：`transport/ssh.py`、`transport/tunnel.py`，以及新的中层运行时模块。
- **改动点**：
  1. `run_command(cmd, timeout, token, parallel)` 接口加 `parallel`；
  2. `parallel=True` 时开一次性 exec channel（`transport.open_channel() → exec_request()`），命令退出自动销毁；
  3. 每 token 一个线程池（默认 32，超限报错）和一个 channel 预算（默认 10，超限拒绝）；
  4. 默认仍走 persistent shell，保持命令顺序。
- **工作量**：M。核心是新写“每 token 执行器”和 channel 记账，SSH 底层能力已有。
- **如何改**：先做 `parallel=True` 的独立 channel 垂直切片，再补线程池/预算；不动 Skill 和 File 通道。

### 3.2 token 机制

- **现状**：请求 `{"skill", "timeout"}`，daemon 不校验身份；`daemon_guard` 事后查证。
- **改动位置**：
  - 中层：`bridge.py` 发请求处、`tunnel.py` 命令/文件接口、新增 registry/router；
  - 底层：两个 daemon 的 `handle_external_connection`、`ramic_bridge.il` 配置读取。
- **改动点**：
  1. 三个上层接口加 `token` 参数；
  2. 中层按 token 查 route，把 token 放入 `{"skill","timeout","token"}`；
  3. daemon 启动时从 il 常量/参数持有 token，请求 token 不匹配 → `0x15 + "invalid token"`，不写 Virtuoso stdin；
  4. token 不进入 `ramic_bridge.il` 执行层；
  5. token 按对称共享实现（客户端生成、daemon 比对），本版视为客户端公钥，预留未来双方公私钥的非对称扩展。
- **工作量**：M。中层路由是新模块，daemon 校验是小改动。
- **如何改**：先双轨（无 token 放行），注册表落 token 后逐步收紧为强制校验。

### 3.3 注册流程改造：profile → 注册表

- **现状**：`profile.py`/`env.py` 从 `VB_*_<profile>` 读配置，`state.json` 每 profile 一份，端口按用户名哈希。
- **改动位置**：新增 `middle/registry.py`、`register.py`、`connect.py`；改造 `tunnel.py`、`profile.py`、`env.py` 为迁移适配器。
- **改动点**：
  1. `registry.json`：user 为键，保存 token、route、expected，冷启动只读；setup/identity 路径由固定目录结构派生，不落注册表；
  2. 注册探测六项：SSH 指纹、hostname、端口空闲、部署根可见、python 版本、daemon user；
  3. 端口从哈希改为注册表分配，冲突显式报错；
  4. 连接两阶段校验 + 冒烟（`echo vb-ok`、`1+1==2`）后开放接口；
  5. `profile` 只保留 `from_env(profile=…)` 语法糖。
- **工作量**：L。这是最大的一块，但可以分阶段：先 registry 只读 + token，再注册/连接流程，最后删 profile 依赖。
- **如何改**：先落地 registry 数据模型和读取，再实现 `user register` / 两阶段连接，最后用旧 `.env` 导入脚本迁移存量。

### 3.4 远端脱离环境变量

- **现状**：
  - `tunnel.py:_generate_virtuoso_setup_il` 写 `setShellEnvVar("RB_*")`；
  - `ramic_bridge.il` 用 `getShellEnvVar` 读；
  - Spectre 依赖远端 shell source `VB_CADENCE_CSHRC`。
- **改动位置**：`tunnel.py`（setup 生成）、`ramic_bridge.il`（配置读取）、Spectre 命令构造（cli/runner）。
- **改动点**：
  1. setup il 把 `RB_DAEMON_PATH`/`RB_PYTHON_PATH`/`RB_PORT`/`RB_IDENTITY_PATH`/token 写成 il 常量（或 daemon 参数），部署到固定 `<user>/ramic|setup|status` 结构（路径用用户名，token 只用于路由/校验）；
  2. `ramic_bridge.il` 不再 `getShellEnvVar`，改读 load 时注入的常量/参数；
  3. 命令执行不要求远端 shell 预配置：注册时固化解出的绝对路径与所需环境，执行时显式传入。
- **工作量**：M。bridge 配置去 env 是 S；Spectre 环境显式化是 M。
- **如何改**：与 registry 部署流程一起改，保证生成的 setup il 一次写清全部配置。

### 3.5 CDSlog 增量返回

- **现状**：`execute_skill` 只回 SKILL 结果；`CDS.log` 需要人工去远端 tail/下载；daemon 的 `hiFlush()` 不是日志 flush。
- **改动位置**：
  - 底层：`ramic_bridge.il`（BEGIN/END marker、`hiFlushLogFile()`、回传 `path + end_offset`）；两个 daemon（本地读文件、分级过滤、限长、推进 cursor）；
  - 中层：`bridge.py`、`models.py`（解析回包，`VirtuosoResult` 加 `log` 字段）。
- **改动点**：
  1. il 写 marker、flush、`fileLength()` 回传 path/end_offset；
  2. daemon 读 `[cursor, end_offset)`，按 `log_level` 过滤、按 `log_max_bytes` 降级，推进 cursor；
  3. 回包 payload 改为 JSON `{"value", "log"}`；
  4. `VirtuosoResult` 加 `log` 字段，旧字段不变。
- **工作量**：M。风险集中在 il 的 marker/`fileLength`，需现场验证；daemon 双版本需同步。
- **如何改**：先跑通“一次 eval → 一个 `result.log`”；本版不考虑 split-host 下 CDS.log 与 daemon 不同主机的情况。

## 4. 汇总与实施顺序

| 修改项 | 主要文件 | 工作量 | 风险 | 依赖 |
|---|---|---|---|---|
| token | bridge.py、tunnel.py、daemon×2、il | M | 低（可双轨） | registry 数据结构 |
| 注册表 | 新增 registry/register/connect；profile/env 迁移 | L | 中（存量迁移） | — |
| 并行 | ssh.py、tunnel.py、新增执行器 | M | 中（channel/线程池） | token 隔离 |
| 远端去 env | tunnel.py、il、Spectre 命令构造 | M | 中（现场验证） | 注册表部署 |
| CDSlog 增量 | il、daemon×2、bridge.py、models.py | M | 中（SKILL wrapper / daemon 双版本） | — |

建议顺序：

```text
第 1 步：token + registry（一起落地，双轨兼容）
第 2 步：并行机制（在 token 隔离之上）
第 3 步：远端去 env（随 registry 部署流程一并切换）
第 4 步：CDSlog 增量返回（底层 il 改动独立，可与前几步并行开发）
```

## 5. 主要风险与验证方式

1. **底层 il / daemon 双版本**：Python 3 与 2.7 daemon 必须同步 token 校验和 log 返回；用同一组离线 fixture 双测。
2. **STX/NAK/RS 兼容**：token 不匹配仍回 `0x15`，多行打包仍走临时 `.il`，不能破坏现有 frame。
3. **CDSlog wrapper**：`hiFlush()` ≠ `hiFlushLogFile()`；`fileLength()` 字节 offset 需现场验证；daemon 本地读文件避免把大日志过 TCP。
4. **registry 迁移**：`from_env`/`profile` 只降级不删除，先保证旧脚本可用，再做增量删除。
5. **并发安全**：每 token 私有连接对象、禁止模块级可变状态；用并发测试验证响应不串包。

## 6. 结论

- **中层改动量最大**：主要集中在 registry/路由/执行器三个新模块，以及对 `SSHClient`、`VirtuosoClient` 的拆解。
- **底层改动量小但关键**：daemon 加 token 校验是小改；`ramic_bridge.il` 的去 env + CDSlog marker 是现场风险最高的部分。
- 先做 **token + registry** 打地基，再依次做并行、远端去 env、CDSlog 增量，每步都保持现代码兼容。
