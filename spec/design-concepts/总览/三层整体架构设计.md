# 三层整体架构设计

> 版本：Draft v2
> 日期：2026-09-10
> 状态：已冻结（接口唯一基线）
> 范围：定义上层、中层、底层的职责边界和层间接口；不定义原理图、版图、测试平台、Maestro、Spectre 等业务操作的内部实现。
> 接口基线：本文第 4 节；CDS.log 请求字段、JSON payload 与过滤规则由[日志返回设计标准](../底层与中层/日志返回设计标准.md)专项扩展。

## 1. 总述与术语

### 1.1 总述

本项目把对 Virtuoso 的自动化访问划分为三个逻辑层次：

- **上层**负责把原理图、版图、测试平台（TB）、仿真等复杂操作封装成业务能力；
- **中层**负责把指令或文件正确地传输到指定位置，或者在指定位置运行指令；
- **底层**是与 Virtuoso 会话绑定的常驻守护进程，负责监听连接端口，把 Skill 送入 Virtuoso 并返回结果。

上层不关心操作发生在本机、业务服务器、跳板机后的计算节点，还是多个角色主机上。上层只通过中层的三个接口完成工作：

```text
技能执行（Skill）       在 Virtuoso 中执行 SKILL
命令执行（RunCommand）   在指定命令环境运行命令行
文件操作（File）         在调用方与业务服务器之间传输文件
```

三层是职责边界，不要求每层都是独立进程。上层和中层可以暂时位于同一个 Python 进程；底层必须以 Virtuoso 可加载、可管理的常驻守护进程方式运行。

### 1.2 术语

| 术语 | 定义 |
|---|---|
| **上层** | 业务与领域封装层，包含原理图、版图、TB、Maestro、库/符号、仿真等模块，以及命令行和工具调用适配器。 |
| **中层** | 业务服务器运行时，向上层提供 Skill、RunCommand、File，隐藏本地/SSH、隧道、端口和主机拓扑。 |
| **底层** | Virtuoso 常驻守护进程，由 Virtuoso 中加载的 SKILL bridge 和其启动的 `daemon.py` 组成，只处理 Skill。 |
| **Skill** | 在 Virtuoso CIW 及其数据库上下文中求值的 SKILL 文本。 |
| **RunCommand** | 在指定命令环境中运行的命令行指令，不通过 Virtuoso。 |
| **File** | 调用方本地路径与业务服务器路径之间的上传、下载及必要校验。 |
| **业务服务器** | 上层看到的逻辑执行环境，不一定对应一台物理主机。 |
| **指定位置** | 中层根据 token 参数和路由选择的底层 Skill 端点、命令主机或文件系统。
| **token** | 上层每次调用携带的寻址与授权参数；中层据此路由，不绑定会话对象。
| **CIW** | Virtuoso 命令窗口，底层 Skill 的实际求值环境。 |

## 2. 整体架构一览

### 2.1 结构

```text
┌──────────────────────────────────────────────────────────────────┐
│                         上层：业务封装层                         │
│                                                                  │
│  原理图 · 版图 · 测试平台 · Maestro · 库/符号 · 仿真 · 工具适配器 │
│                                                                  │
│  只依赖：技能执行接口 · 命令执行接口 · 文件操作接口              │
└──────────────────────────────┬───────────────────────────────────┘
                               │ 三个接口
                               ▼
┌──────────────────────────────────────────────────────────────────┐
│                       中层：业务服务器运行时                     │
│                                                                  │
│  token 路由 · 指令投送 · 命令执行 · 文件传输 · 结果诊断           │
└───────────────┬──────────────────┬───────────────────────────────┘
                │ 技能执行         │ 命令执行 / 文件操作
                ▼                  ▼
┌──────────────────────────┐  ┌───────────────────────────────────┐
│ 底层：Virtuoso 守护进程  │  │ 中层选择的指定位置                  │
│ 监听技能连接端口          │  │ 命令环境 / 文件系统                 │
│ IPC 连接 Virtuoso 命令窗口 │  │ 中层在此运行命令或传输文件           │
│ 只执行 SKILL             │  │                                   │
└──────────────────────────┘  └───────────────────────────────────┘
```

“指定位置”是中层管理的外部执行目标，不是第四层。底层就是 Virtuoso 守护进程：一端监听中层连接端口，另一端连接 Virtuoso。命令和文件可以与底层位于同一台机器，也可以位于不同主机；上层对此不感知。

每个接口都是**请求 + 返回**一对：箭头向下是请求，结果沿原路反向返回。

```text
返回方向：
  底层守护进程 ──STX/NAK/RS──> 中层 ──结果──> 上层
  命令环境 ──returncode/stdout/stderr──> 中层 ──结果──> 上层
  文件系统 ──传输结果/校验摘要──> 中层 ──结果──> 上层
```

### 2.2 三条数据流

```text
技能执行：
  请求：上层 → 中层 → TCP/隧道 → 底层守护进程 → Virtuoso CIW
  返回：Virtuoso CIW → 底层守护进程 → TCP/隧道 → 中层 → 上层（VirtuosoResult）
命令执行：
  请求：上层 → 中层 → 本地进程或 SSH → 指定命令环境
  返回：stdout / stderr / returncode → 中层 → 上层（CommandResult）
文件操作：
  请求：上层 → 中层 → 本地复制或远程传输 → 指定文件系统
  返回：传输结果 / 校验摘要 → 中层 → 上层（CommandResult）
```

三条数据流相互独立：命令和文件不进入底层，底层只处理 Skill。

## 3. 各层次职责

### 3.1 上层：封装业务复杂度

上层的任务是把基础操作组织成可用的业务能力，例如创建、读取和修改原理图，编辑 TB，生成网表，运行仿真和解析结果。上层负责：

1. 业务参数校验、操作顺序和领域对象；
2. 组合 Skill、RunCommand 和 File 完成复杂流程；
3. 解释基础接口返回值，向调用者提供稳定的业务 API。

上层只依赖中层三个接口，不直接依赖 SSH、隧道、socket、subprocess、SCP、物理主机、端口或底层协议。上层也不能把 `csh()`、`system()` 等命令行调用伪装成 Skill。

### 3.2 中层：路由、投送和执行

中层的核心目标是：**把请求送到正确的位置，并在正确的位置得到可验证的结果。**

| 请求类型 | 中层职责 | 实际目标 |
|---|---|---|
| 技能执行（Skill） | 找到底层端点并正确投送 Skill | Virtuoso 守护进程 / CIW |
| 命令执行（RunCommand） | 在目标环境启动命令并收集结果 | 指定命令主机 |
| 文件操作（File） | 在两侧传输、覆盖控制并按需校验 | 指定文件系统 |

此外，中层负责：

- 根据每次调用携带的 token 参数进行路由与多用户隔离；
- 屏蔽本地模式、SSH 模式、跳板机和分裂主机；
- 为每个 token 维护线程池：一次未完成的调用占用一个线程，结果返回后线程回池，超限返回错误；统一处理连接生命周期、超时、错误分类和诊断信息；
- 保持 `LocalPath` 与 `ServerPath` 的命名空间边界。

中层不理解原理图、TB 或仿真的业务含义，也不替上层决定业务流程。

### 3.3 底层：连接端口与 Virtuoso

底层是 Virtuoso 常驻守护进程，`ramic_bridge.il` 与 `daemon.py` 的组合统称为底层。它只做以下事情：

1. 在 Virtuoso 会话中启动并维持 `daemon.py`；
2. 由 `daemon.py` 监听一个 Skill 连接端口；
3. 通过 `ipcBeginProcess` 与 Virtuoso 命令窗口通信；
4. 将 Skill 交给 Virtuoso 求值，并把结果或错误返回给中层。

底层不执行普通 shell，不上传或下载文件，不识别上层业务类型，也不承担多用户业务路由。一个底层守护进程对应一个 Virtuoso 会话和一个 Skill 端点。

### 3.4 依赖方向

```text
上层 → 中层 → 底层 → Virtuoso
```

上层不能绕过中层直接连接底层或目标主机；中层不能把传输对象泄漏给上层；底层不能反向调用上层业务代码。

## 4. 层间接口

本节是两条跨层接口的基础契约；底层与 Virtuoso 之间的管道属于底层内部实现，不是跨层接口。CDS.log 的可选请求字段、JSON payload 和过滤规则由[日志返回设计标准](../底层与中层/日志返回设计标准.md)专项扩展。

### 4.1 上层 ↔ 中层：业务调用接口

调用形态如下（无绑定会话，token 是每次调用的参数）：

```python
middle.execute_skill(skill_code, timeout=None, *, token)
middle.run_command(cmd, timeout=None, *, token, parallel=False)
middle.upload_file(local_path, remote_path, timeout=None, *, token, recursive=False)
middle.download_file(remote_path, local_path, timeout=None, *, token, recursive=False)
```

# 返回示例
```python
r1 = middle.execute_skill("1+2", token="a3f9c2…")
# VirtuosoResult(status="success", output="3")

r2 = middle.run_command("spectre netlist.scs", token="a3f9c2…")
# CommandResult(returncode=0, stdout="...", stderr="")
```

约定：

- 三个接口的参数名、顺序和返回类型与现代码一致：**`token` 是唯一新增必填关键字参数**；`run_command` 的 `parallel` 与文件接口的 `recursive` 为可选新增参数；token 缺失直接报错。
- `skill_code` 是 SKILL 文本，`cmd` 是命令行文本，二者不可混用；
- 接口只有三个：Skill / RunCommand / File。`run_command` 新增 `token` 和 `parallel` 两个参数；`parallel=True` 是新建的显式并行机制，不是第四个接口；
- `local_path` 属于调用方，`remote_path` 属于业务服务器；
- 返回现有 `VirtuosoResult`（Skill）和 `CommandResult`（RunCommand/File），保持现状；
- 上层不传 host、端口、SSH、隧道或 daemon 地址。

### 4.2 中层 ↔ 底层：Skill 投送接口

传输采用 TCP，一条连接承载一个请求和一个响应，以 EOF 结束，与现代码一致。v1 请求只允许 Skill：

```json
{
  "skill": "getVersion()",
  "timeout": 30.0,
  "token": "opaque-token"
}
```

`skill`、`timeout` 是现代码字段；`token` 是唯一新增**必填**字段；`log_level`/`log_max_bytes` 属于[日志返回设计标准](../底层与中层/日志返回设计标准.md)的可选扩展字段。响应保持现代码的 `STX/NAK/RS` 帧：

```text
成功：02 33 1e     （02=STX 成功，33=字符 '3'，1e=RS 帧结束）
失败：15 <错误文本> 1e
```

命令执行与文件操作不经过此接口。上层传入 token，中层转发给底层，底层校验 token；校验失败时不得接触 Virtuoso。token 不进入下一层，也不回显给上层。

**token 语义（本版）**：当前 token 是**对称共享的授权票（bearer ticket）**——客户端生成并持有，部署时注入 daemon 一份用于比对；它不是公钥，也不承担 SSH 认证。未来可扩展为 daemon 与客户端**各自持有公私钥对**的非对称认证（客户端用私钥、daemon 持客户端公钥，反之亦然）；**本版不做**，但 token 的设计不堵死这条演进路。

### 4.3 底层内部实现：连接 Virtuoso（非跨层接口）

底层通过 `ipcBeginProcess` 管道连接 Virtuoso，这是底层自己的实现，不是跨层接口：

```text
daemon.py  ⇄  ramic_bridge.il  ⇄  Virtuoso CIW
```

最小约定为：

```text
请求：一条物理行的 SKILL 包装 + LF
响应：STX/NAK + payload + RS
```

字节示例：成功 `02 33 1e`（`02`=STX，`33`=字符 `3`，`1e`=RS）；失败 `15 <错误文本> 1e`。

这一层不携带 token，不承担用户路由；CIW 的普通 `printf` 也不自动等同于接口返回值。

## 5. 设计要点

### 5.1 接口严格分工

技能执行、命令执行和文件操作分别解决三个问题：在 Virtuoso 中做什么、在指定命令环境中运行什么、如何把数据送到指定文件系统。一个接口不可隐式退化为另一个接口。

### 5.2 上层只面向逻辑业务服务器

本地、SSH、跳板机和分裂主机只是中层实现方式。部署位置改变时，上层的业务 API、参数和结果语义不应改变。**本版范围**：split-host 承诺 route 分解与主机映射；CDS.log 增量仅支持 daemon 与 CDS.log 同主机，split-host 的日志增量列为后续版本（见日志返回设计标准）。

### 5.3 中层保证“正确位置”和“可验证结果”

中层不仅负责发送请求，还要确认请求对应的目标、执行阶段和结果。路径不可见、连接失败、命令非零退出、Skill 错误和文件校验失败必须能够区分。

### 5.4 底层最小化且一对一

底层只连接一个 Virtuoso 会话并执行 Skill，不扩展成通用远程命令代理。不同 token 不得共享同一个底层 Skill 通道。

### 5.5 多用户隔离由中层负责

中层按 token 隔离 Skill 端点、命令通道和文件空间。**线程池、channel 预算与 ControlMaster 全部 per-token**：ControlPath 命名空间包含 token，两个 token 不共享 master socket；性能靠同一 token 内部复用 ControlMaster 获得，关闭只拆本 token 的 master，对 SSH 层使用者无感。

### 5.6 路径和位置语义明确

`LocalPath` 与 `ServerPath` 属于不同命名空间。`route.file.root` 只是**默认可用工作目录**（截图、日志、导入网表等），不是沙箱：文件操作允许访问业务服务器上任意可达路径。若 Skill、命令和文件需要共享同一文件，中层必须确认目标位置可见；不可见时明确报错，不悄悄改写路径或隐式复制。

### 5.7 单 CIW 串行，跨 CIW 并行

同一个 Virtuoso CIW 的 Skill 请求必须串行；不同底层会话可以并行。命令默认串行，`parallel=True` 显式并行（新机制），文件传输天然并行。具体并发机制和隔离规则见[并发处理设计](../底层与中层/并发处理设计.md)。

### 5.8 可靠性和可扩展性

所有调用使用端到端超时；中层不得在内部阶段重新开始完整 timeout，子阶段只继承剩余预算。本版不引入 `request_id` 参数/字段（daemon 同一时刻只有一个 in-flight 请求，增量由 cursor 定界）。无法判断请求是否已经产生副作用时返回“结果未知”，不盲目重试非幂等操作。增加新的业务能力时扩展上层，增加新的本地/远程传输方式时扩展中层，三层边界不改变。安全模型预留演进：当前 token 是对称共享授权票，未来可升级为双方各自持有公私钥的非对称认证，三层边界不变。
