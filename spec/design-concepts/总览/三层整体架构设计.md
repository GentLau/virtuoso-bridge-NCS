# 三层整体架构设计

> 版本：Draft v13
> 日期：2026-09-14
> Supersedes：Draft v12（Skill 投递前按 token 排队）
> 状态：已冻结（接口唯一基线）
> 范围：定义上层、中层、底层的职责边界和层间接口；不定义原理图、版图、测试平台、Maestro、Spectre 等业务操作的内部实现。
> 接口基线：本文第 4 节；CDS.log 请求字段、JSON payload 与过滤规则由[日志返回设计标准](../底层与中层/日志返回设计标准.md)专项扩展。

## 1. 总述与术语

### 1.1 总述

本项目把对 Virtuoso 的自动化访问划分为三个逻辑层次：

- **上层**负责把原理图、版图、测试平台（TB）、仿真等复杂操作封装成业务能力；
- **中层**负责把指令或文件正确地传输到指定位置，或者在指定位置运行指令；
- **底层**是与 Virtuoso 会话绑定的常驻守护进程，负责监听连接端口，把 Skill 送入 Virtuoso 并返回结果。

上层不关心操作发生在本机、业务服务器、跳板机后的计算节点，还是多个角色主机上。上层只通过中层的**五个接口**完成工作：

```text
技能执行（Skill）                    在 Virtuoso 中执行 SKILL
命令执行（RunCommand）               在指定命令环境运行命令行
文件执行（File）                     在调用方与业务服务器之间传输文件（上传/下载）
GUI 命令执行（GUI command）          在 GUI 主机执行一次性命令
Spectre 命令执行（Spectre command）  在 Spectre 主机执行一次性命令
```

接口签名与返回、错误总则的唯一 owner 是本文 §4.1 / §4.4；其它文档只引用，不再复制清单。

三层是职责边界，不要求每层都是独立进程。上层和中层可以暂时位于同一个 Python 进程；底层必须以 Virtuoso 可加载、可管理的常驻守护进程方式运行。

### 1.2 术语

| 术语 | 定义 |
|---|---|
| **上层** | 业务与领域封装层，包含原理图、版图、TB、Maestro、库/符号、仿真等模块，以及命令行和工具调用适配器。 |
| **中层** | 业务服务器运行时，向上层提供五个接口（见 §4.1），隐藏本地/SSH、隧道、端口和主机拓扑。 |
| **底层** | Virtuoso 常驻守护进程，由 Virtuoso 中加载的 SKILL bridge 和其启动的 `daemon.py` 组成，只处理 Skill。 |
| **Skill** | 在 Virtuoso CIW 及其数据库上下文中求值的 SKILL 文本。 |
| **RunCommand** | 在指定命令环境中运行的命令行指令，不通过 Virtuoso。 |
| **File** | 调用方本地路径与业务服务器路径之间的上传、下载及必要校验。 |
| **业务服务器** | 上层看到的逻辑执行环境，不一定对应一台物理主机。 |
| **指定位置** | 中层根据 token 参数和路由选择的底层 Skill 端点、命令主机或文件系统。
| **token** | 上层每次调用携带的寻址与授权参数；中层据此路由，不绑定会话对象。
| **endpoint** | 一次 SSH 连接的目的地身份，由 `(host, user)` 加可达路径 `(jump, proxy)` 唯一确定；只表达“连到哪”，不携带 token，不携带预算。同一 token 内按 endpoint 去重复用连接，不同 token 即使 endpoint 相同也不共用连接。 |
| **CIW** | Virtuoso 命令窗口，底层 Skill 的实际求值环境。 |

## 2. 整体架构一览

### 2.1 结构

```text
┌──────────────────────────────────────────────────────────────────┐
│                         上层：业务封装层                         │
│                                                                  │
│  原理图 · 版图 · 测试平台 · Maestro · 库/符号 · 仿真 · 工具适配器 │
│                                                                  │
│  只依赖：Skill · 命令 · 文件 · GUI 命令 · Spectre 命令（5 接口） │
└──────────────────────────────┬───────────────────────────────────┘
                               │ 五个接口
                               ▼
┌──────────────────────────────────────────────────────────────────┐
│                       中层：业务服务器运行时                     │
│                                                                  │
│  token 路由 · 指令投送 · 命令执行 · 文件传输 · 结果诊断           │
└───────────────┬──────────────────┬───────────────────────────────┘
                │ 技能执行         │ 命令执行 / 文件操作
                ▼                  ▼
┌──────────────────────────┐  ┌───────────────────────────────────┐
│ 底层：Virtuoso 守护进程  │  │ 中层选择的指定位置                  │
│ 监听技能连接端口          │  │ 命令环境 / 文件系统                 │
│ IPC 连接 Virtuoso 命令窗口 │  │ 中层在此运行命令或传输文件           │
│ 只执行 SKILL             │  │                                   │
└──────────────────────────┘  └───────────────────────────────────┘
```

“指定位置”是中层管理的外部执行目标，不是第四层。底层就是 Virtuoso 守护进程：一端监听中层连接端口，另一端连接 Virtuoso。命令和文件可以与底层位于同一台机器，也可以位于不同主机；上层对此不感知。

每个接口都是**请求 + 返回**一对：箭头向下是请求，结果沿原路反向返回。

```text
返回方向：
  底层守护进程 ──STX/NAK/RS──> 中层 ──结果──> 上层
  命令环境 ──returncode/stdout/stderr──> 中层 ──结果──> 上层
  文件系统 ──传输结果/校验摘要──> 中层 ──结果──> 上层
```

### 2.2 五条数据流

```text
技能执行（Skill）：
  请求：上层 → 中层 → TCP/隧道 → 底层守护进程 → Virtuoso CIW
  返回：Virtuoso CIW → 底层守护进程 → TCP/隧道 → 中层 → 上层（VirtuosoResult）
命令执行（RunCommand）：
  请求：上层 → 中层 → 本地进程或 SSH → command role
  返回：stdout / stderr / returncode → 中层 → 上层（CommandResult）
文件执行（File）：
  请求：上层 → 中层 → 本地复制或远程传输 → file role
  返回：传输结果 / 校验摘要 → 中层 → 上层（CommandResult）
GUI 命令执行（一次性）：
  请求：上层 → 中层 → 本地进程或 SSH → gui role → 返回（CommandResult）
Spectre 命令执行（一次性）：
  请求：上层 → 中层 → 本地进程或 SSH → spectre role → 返回（CommandResult）
```

五条数据流相互独立：只有技能执行进入底层，其余四条由中层在各自 role 上完成，底层只处理 Skill。

## 3. 各层次职责

### 3.1 上层：封装业务复杂度

上层的任务是把基础操作组织成可用的业务能力，例如创建、读取和修改原理图，编辑 TB，生成网表，运行仿真和解析结果。上层负责：

1. 业务参数校验、操作顺序和领域对象；
2. 组合五个接口（Skill / 命令 / 文件 / GUI 命令 / Spectre 命令）完成复杂流程；
3. 解释基础接口返回值，向调用者提供稳定的业务 API。

上层只依赖中层五个接口，不直接依赖 SSH、隧道、socket、subprocess、SCP、物理主机、端口或底层协议。上层也不能把 `csh()`、`system()` 等命令行调用伪装成 Skill。

### 3.2 中层：路由、投送和执行

中层的核心目标是：**把请求送到正确的位置，并在正确的位置得到可验证的结果。**

五个请求类型分别投送到各自的 role（Skill→daemon、命令→command、文件→file、GUI→gui、Spectre→spectre）；**唯一映射与职责见[多节点设计 §3](../底层与中层/多节点设计.md)**，本文不复制表格。

此外，中层负责：

- 根据每次调用携带的 token 参数进行路由与多用户隔离；
- 屏蔽每个 role 的 local/remote 投送方式、跳板机和分裂主机；
- 为每个 token 维护线程池：一次未完成的调用占用一个线程，结果返回后线程回池，超限返回错误（唯一口径：[并发处理设计 §4](../底层与中层/并发处理设计.md)）；统一处理连接生命周期、超时、错误分类和诊断信息；
- 保持 `LocalPath` 与 `ServerPath` 的命名空间边界。

中层不理解原理图、TB 或仿真的业务含义，也不替上层决定业务流程。

### 3.3 底层：连接端口与 Virtuoso

底层是 Virtuoso 常驻守护进程，`ramic_bridge.il` 与 `daemon.py` 的组合统称为底层。它只做以下事情：

1. 在 Virtuoso 会话中启动并维持 `daemon.py`；
2. 由 `daemon.py` 监听一个 Skill 连接端口；
3. 通过 `ipcBeginProcess` 与 Virtuoso 命令窗口通信；
4. 将 Skill 交给 Virtuoso 求值，并把结果或错误返回给中层。

底层不执行普通 shell，不上传或下载文件，不识别上层业务类型，也不承担多用户业务路由。一个底层守护进程对应一个 Virtuoso 会话和一个 Skill 端点。

### 3.4 依赖方向

```text
上层 → 中层 → 底层 → Virtuoso
```

上层不能绕过中层直接连接底层或目标主机；中层不能把传输对象泄漏给上层；底层不能反向调用上层业务代码。

## 4. 层间接口

本节是两条跨层接口的基础契约；底层与 Virtuoso 之间的管道属于底层内部实现，不是跨层接口。CDS.log 的可选请求字段、JSON payload 和过滤规则由[日志返回设计标准](../底层与中层/日志返回设计标准.md)专项扩展。

### 4.1 上层 ↔ 中层：业务调用接口

调用形态如下（无绑定会话，token 是每次调用的参数）：

```python
middle.execute_skill(skill_code, timeout=None, *, token)                 # 1 Skill 执行
middle.run_command(cmd, timeout=None, *, token, parallel=False)          # 2 命令执行
middle.upload_file(local_path, remote_path, timeout=None, *, token, recursive=False)    # 3 文件执行（上传）
middle.download_file(remote_path, local_path, timeout=None, *, token, recursive=False)  # 3 文件执行（下载）
middle.run_gui_command(cmd, timeout=None, *, token)                      # 4 GUI 命令执行（一次性）
middle.run_spectre_command(cmd, timeout=None, *, token)                  # 5 Spectre 命令执行（一次性）
```

返回示例（节选，`kind` 语义见 §4.4）：

```python
r1 = middle.execute_skill("1+2", token="a3f9c2…")
# VirtuosoResult(status="success", output="3", log="…")

r2 = middle.run_command("spectre netlist.scs", token="a3f9c2…")
# CommandResult(returncode=0, stdout="...", stderr="", kind="command")

r3 = middle.run_command("spectre netlist.scs", token="a3f9c2…", parallel=True)
# 并行模式：独立一次性 exec channel，同样占用该 token 的 channel 预算
```

约定：

- 接口共 **5 个**：**Skill 执行 / 命令执行 / 文件执行 / GUI 命令执行 / Spectre 命令执行**；`token` 是每次调用的必填关键字参数，token 缺失直接报错；
- `skill_code` 是 SKILL 文本，`cmd` 是命令行文本，二者不可混用；
- 文件执行是一个接口的两个方向（`upload_file` / `download_file`），不是两个接口；
- **GUI 命令执行与 Spectre 命令执行本质上是"并行模式的一次性命令"**：每次调用在对应 role 上执行一条一次性命令，不建常驻 shell、不保留 cwd/env，同样占用该 token 的 channel 预算；`run_command` 的 `parallel` 与文件接口的 `recursive` 为可选参数；
- `local_path` 属于调用方，`remote_path` 属于业务服务器；
- 返回 `VirtuosoResult`（Skill）和 `CommandResult`（其余四个接口），字段合同见 §4.4；
- 上层不传 host、端口、SSH、隧道或 daemon 地址；role 与目标位置见[多节点设计](../底层与中层/多节点设计.md)。

### 4.2 中层 ↔ 底层：Skill 投送接口

传输采用 TCP，一条连接承载一个请求和一个响应，以 EOF 结束，与现代码一致。v1 请求只允许 Skill：

```json
{
  "skill": "getVersion()",
  "timeout": 30.0,
  "token": "opaque-token"
}
```

`skill`、`timeout` 是现代码字段；`token` 是唯一新增**必填**字段；`log_level`/`log_max_bytes` 属于[日志返回设计标准](../底层与中层/日志返回设计标准.md)的可选扩展字段。响应保持 `STX/NAK/RS` 帧，**当前唯一 payload 格式为 JSON**（格式、log 字段与 `off` 语义见日志标准，本文件不复制）：

```text
成功：02 {"value": "3", "log": ""} 1e
失败：15 {"error": "...", "log": ""} 1e
```

命令执行与文件操作不经过此接口。上层传入 token，中层转发给底层，底层校验 token；校验失败时不得接触 Virtuoso。token 到达 daemon 供校验，但不得进入 Virtuoso/SKILL 求值文本，也不回显给上层。

**token 语义（本版）**：当前 token 是**对称共享的授权票（bearer ticket）**——客户端生成并持有，部署时注入 daemon 一份用于比对；它不是公钥，也不承担 SSH 认证。未来可扩展为 daemon 与客户端**各自持有公私钥对**的非对称认证（客户端用私钥、daemon 持客户端公钥，反之亦然）；**本版不做**，但 token 的设计不堵死这条演进路。

### 4.3 底层内部实现：连接 Virtuoso（非跨层接口）

底层通过 `ipcBeginProcess` 管道连接 Virtuoso，这是底层自己的实现，不是跨层接口：

```text
daemon.py  ⇄  ramic_bridge.il  ⇄  Virtuoso CIW
```

最小约定为：

```text
请求：一条物理行的 SKILL 包装 + LF
响应：STX/NAK + payload + RS
```

字节示例：成功 `02 33 1e`（`02`=STX，`33`=字符 `3`，`1e`=RS）；失败 `15 <错误文本> 1e`。

这一层不携带 token，不承担用户路由；CIW 的普通 `printf` 也不自动等同于接口返回值。

### 4.4 结果与错误合同（本版冻结）

五个接口**对外一律返回结构化结果，不向上抛传输异常**。参数编程错误（token 缺失、类型错误）是调用方错误，允许直接抛出 `TypeError/ValueError`；运行期错误（unknown token、daemon NAK、文件失败、传输失败）必须封装为结果。

`CommandResult` 增加稳定 `kind` 字段：`command`（真实命令）/ `timeout` / `transport` / `path` / `unknown-effect` / `rejected`（容量拒绝）/ `checksum`（文件摘要不一致）/ `invalid-token`（未知 token）；真实命令返回码即使等于 124/255 也保持 `kind=command`，桥保留码只在 `kind != command` 时解释。

| 情形 | Skill (`VirtuosoResult`) | 命令/文件/GUI/Spectre (`CommandResult`) |
|---|---|---|
| 正常 | `status=success`、`output`、`log` | `kind=command`、`returncode=命令自身退出码`、`stdout/stderr` |
| 超时 | `status=error`、`errors=["SKILL execution timed out"]` | `kind=timeout`、`returncode=124`、`stderr` 含超时说明 |
| 传输失败（连不上/断连） | `status=error`、`errors` 含 `Daemon connection failed` | `kind=transport`、`returncode=255`（SSH/Paramiko 非零 rc；中层包装的异常以 `VB-TRANSPORT:` 开头） |
| 路径不可见/文件缺失 | 不适用 | `kind=path`、`returncode≠0`、`stderr` 含 `VB-PATH-NOT-VISIBLE:` 或 SSH/SCP 的 no-such-file 诊断 |
| 结果未知（可能已产生副作用） | `status=error`、`errors` 含 `SKILL execution timed out`；**客户端超时不等于未投递** | `kind=unknown-effect`、`returncode=255`、`stderr` 含 `VB-UNKNOWN-EFFECT:`，**不得盲目重试非幂等命令** |
| 容量拒绝（线程池/channel 超限） | `errors` 含 `thread pool exceeded` | `kind=rejected`、`returncode=1`、`stderr` 含 `thread pool/channel budget exceeded`，可重试 |
| 文件校验失败 | 不适用 | `kind=checksum`、`returncode=1`、`stderr` 含 `sha256 mismatch` |
| unknown token | `status=error`、`errors=["invalid token"]` | `kind=invalid-token`、`returncode=1`、`stderr="invalid token"`（token 不发送给命令本体，但参与中层路由） |
| Skill 求值错误 | `status=error`、`errors=[...]` | 不适用 |

- 自动重试只发生在“确认未产生副作用”的传输阶段；`VirtuosoResult.warnings` 供 CI 决策，`CommandResult` 的非致命诊断写入 `stderr`（不新增字段、不新增接口）；
- `Skill` 的 `log` 字段语义见[日志返回设计标准](../底层与中层/日志返回设计标准.md)。


### 4.5 文件执行合同（上传/下载，唯一 owner）

`File` 是一个接口的两个方向（`upload_file` / `download_file`），对外语义与 mode 无关（local 与 remote 等价）：

- **对象**：`recursive=False` 只传**单个常规文件**；`recursive=True` 传**目录树**。对象类型与 `recursive` 不符 → `kind=path`；
- **落盘**：先写入临时位置，传输成功后**原子替换**到目标；中途失败清理临时内容、不改动已存在的目标；目标已存在则**覆盖**；
- **校验**：单文件传输完成后做 **SHA-256** 校验，不一致 → `kind=checksum`；目录传输**跳过**逐文件校验；
- **路径**：`remote_path` 绝对路径原样使用，相对路径按 file role 的根解析（见[多节点设计 §5](../底层与中层/多节点设计.md)）；源不存在 → `kind=path`；
- **symlink**：跟随传输（传送目标内容），不承诺保留链接本身；
- 实现细节（临时目录位置、传输工具、块大小等）不属本合同。

## 5. 设计要点

### 5.1 接口严格分工

五个接口分别解决各自的问题：在 Virtuoso 中做什么（Skill）、在指定命令环境中运行什么（RunCommand）、如何把数据送到指定文件系统（File）、在 GUI 主机做什么（GUI 命令）、在 Spectre 主机做什么（Spectre 命令）。一个接口不可隐式退化为另一个接口，也不存在第六个接口。

### 5.2 上层只面向逻辑业务服务器

本地、SSH、跳板机和分裂主机只是中层实现方式。部署位置改变时，上层的业务 API、参数和结果语义不应改变。**本版范围**：

- 五个 role（gui/daemon/command/file/spectre）各自独立配置；能力与职责、探测矩阵、部署与 endpoint 规则由[多节点设计](../底层与中层/多节点设计.md)唯一 owner 定义，本文不重复；
- **忠实投送**：bridge 只按用户给定的 role 目标投送指令/文件，不判断 role 之间是否同机、同账号或共享路径；
- 同一 token 内按解析后的 endpoint 去重（唯一口径：[多节点设计 §6](../底层与中层/多节点设计.md)）：每个 endpoint 一条业务连接 + remote daemon 的专用 Skill 隧道；跨 token 不共用；
- Skill 走 daemon、命令走 command、文件走 file、GUI 命令走 gui、Spectre 命令走 spectre；
- 每个 role 有自己的文件根；根的回退、`~` 展开、role cwd 与相对路径解析的唯一 owner 是[多节点设计 §5](../底层与中层/多节点设计.md)，本文不复制算法；
- CDS.log 增量的同机假设、split-host 的可观察行为与后续方向见[日志返回设计标准](../底层与中层/日志返回设计标准.md)，本文不重复。

### 5.3 中层保证“正确位置”和“可验证结果”

中层不仅负责发送请求，还要确认请求对应的目标、执行阶段和结果。路径不可见、连接失败、命令非零退出、Skill 错误和文件校验失败必须能够区分。

### 5.4 底层最小化且一对一

底层只连接一个 Virtuoso 会话并执行 Skill，不扩展成通用远程命令代理。**一个 token = 一个活动 daemon = 一个 CIW**；不同 token 不得共享同一个底层 Skill 通道；需要第二个 CIW 必须注册第二个 user/token。

### 5.5 多用户隔离由中层负责

中层按 token 隔离 Skill 端点与命令通道；文件侧只提供“每用户默认目录”约定，**不提供安全沙箱**（见 §5.6）。预算与连接复用的唯一 owner 是[并发处理设计 §4](../底层与中层/并发处理设计.md)：本文只保留两条原则——**预算每 token 一份（token 内所有 role/endpoint 共用，跨 token 永不共享）**、**SSH 连接在同一 token 内按 endpoint 去重复用**；具体记账表、ControlPath 命名与关闭语义不在此重复。

### 5.6 路径和位置语义明确

`LocalPath` 与 `ServerPath` 属于不同命名空间：

- `remote_path` 允许**绝对路径**或**相对目标 role 文件根**的相对路径；相对路径先做规范化（去 `.`、保留 OS 语义的 `..`，不额外做 root 沙箱拦截）；目标 role 的根见[多节点设计 §5](../底层与中层/多节点设计.md)；
- 各 role 的 `root` 只是该 role 的**默认工作目录约定**（部署文件、截图、日志、导入网表等），**不是沙箱**：文件操作允许访问业务服务器上任意可达路径；同 SSH 账号下不同 user 之间不承诺跨目录隔离，安全边界由 OS 账号权限提供；
- symlink、不存在的目标、覆盖目录按 OS 语义；目标不可见 → 结构化错误 `VB-PATH-NOT-VISIBLE`，不悄悄改写路径或隐式复制；
- bridge 不要求 role 之间共享目录；若一次流程确实需要跨 role 传递文件，由调用方保证路径可见性并自行负责。

### 5.7 单 CIW 串行，跨 CIW 并行

同一个 Virtuoso CIW 的 Skill 请求必须串行；不同底层会话可以并行。串行在中层**投递前**按 token 排队（per-token 投递闸门）：仍在排队时超时 → 请求**不投递**（确定未执行、可安全重试）；**已投递**的请求进入 daemon 队列，客户端超时不取消该请求。命令默认串行，`parallel=True` 显式并行（新机制），文件传输天然并行。具体并发机制和隔离规则见[并发处理设计](../底层与中层/并发处理设计.md)。

### 5.8 可靠性和可扩展性

所有调用使用端到端超时：单次调用默认 30s，连接建立默认 `runtime.connect_timeout=15s`；中层不得在内部阶段重新开始完整 timeout，子阶段只继承剩余预算。传输重试最多 3 次，且只发生在确认未产生副作用的阶段（建连/握手）；错误分类与保留码见 §4.4。

**五接口 deadline 唯一表**（`timeout=None` 时；每个接口一次调用只有一条 deadline，下表各相位共享它）：

| 接口 | 默认预算 | deadline 覆盖的相位（同一预算内顺序扣除，不重置；线程预算超限直接拒绝，不排队） |
|---|---|---|
| Skill 执行 | 30s | 线程预算占用（超限即 `rejected`） + **投递前按 token 排队** + 隧道建立 + TCP 连接 + daemon 执行 + log 第二帧 |
| 命令执行（默认串行） | 30s | 线程预算占用（超限即 `rejected`，不排队） + 等待该 token 的串行命令位 + 常驻 shell 内执行 |
| 命令执行（`parallel=True`） | 30s | 线程预算占用（超限即 `rejected`，不排队） + channel 记账 + 连接建立 + 一次性 exec |
| 文件执行（上传/下载） | 30s | 线程预算占用（超限即 `rejected`，不排队） + channel 记账 + 连接建立 + 传输 + 校验子命令 |
| GUI 命令执行 | 30s | 线程预算占用（超限即 `rejected`，不排队） + channel 记账 + 连接建立 + 一次性命令 |
| Spectre 命令执行 | 30s | 线程预算占用（超限即 `rejected`，不排队） + channel 记账 + 连接建立 + 一次性命令 |

- `runtime.connect_timeout`（默认 15s）是**该预算内的子预算**，不额外增加总预算；超时返回 `kind=timeout` / `returncode=124`；
- 重试（≤3 次总尝试）只发生在无副作用阶段，且与初次尝试共享同一条 deadline；
- **注册各步**的 deadline（探测、部署、第五步各校验相位）唯一 owner 是[多用户设计 §3.2](../底层与中层/多用户设计.md)，本表不重复。

可测试化的边界表：

| 问题 | 唯一答案 |
|---|---|
| `timeout=None` | 五个接口一律等于默认 30s（见上表） |
| “最多 3 次重试” | **最多 3 次总尝试**（1 次初次 + 2 次重试），只覆盖无副作用阶段（TCP 建连 / SSH 握手 / 隧道建立） |
| persistent shell 重建 | 重建为**全新登录 shell**（初始 cwd/env），不恢复旧会话状态；**命令一旦投递成功即不自动重发**——投递后 shell 死亡返回 `kind=unknown-effect`，仅在确认未投递时透明重建 |
| log 第二帧超时 | Skill 第一帧结果优先返回，`log=""` 并附固定 warning，见[日志返回设计标准 §6.3](../底层与中层/日志返回设计标准.md) |

本版不引入 `request_id` 参数/字段（daemon 同一时刻只**执行**一个 SKILL；已投递、待执行的请求在其队列中。日志增量由每请求的 `[start,end)` offset 定界）。无法判断请求是否已经产生副作用时返回“结果未知”，不盲目重试非幂等操作；该纪律同样适用于 Skill：**投递前**排队超时=确定未执行、可安全重试；**投递后**超时=结果未知、不盲目重试。增加新的业务能力时扩展上层，增加新的本地/远程传输方式时扩展中层，三层边界不改变。安全模型预留演进：当前 token 是对称共享授权票，未来可升级为双方各自持有公私钥的非对称认证，三层边界不变。
