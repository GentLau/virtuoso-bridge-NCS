## 1. Python 基础语法（对话中出现的高频点）

> 单片机工程师的常见问题：类/实例/工厂在 Python 里的写法与 C/Java 差异。

### 1.1 dataclass：自动生成样板代码

```python
@dataclass(frozen=True)
class _Deadline:
    timeout: float
    deadline: float
```

- `@dataclass`：自动生成 `__init__` / `__repr__` / `__eq__`。字段声明即构造参数声明。
- `frozen=True`：实例不可变，属性赋值抛 `FrozenInstanceError`。→ 跨线程共享安全（只读对象无数据竞争）。
- `timeout: float` 是类型注解（提示用），不是赋值；运行时不做强制检查。

### 1.2 类、实例、构造函数、工厂

| 概念 | Python 写法 | 对应 C/Java |
|---|---|---|
| 类 | `class Foo:` | class |
| 实例 | `f = Foo()`（无 new 关键字） | `new Foo()` |
| 构造函数 | `def __init__(self, ...)`（不 return） | 构造函数 |
| 私有 | 命名约定 `_foo`（无关键字） | private |
| 类方法 | `@classmethod def start(cls, ...)`，`cls` = 类本身 | static 方法（近似） |

**工厂（Factory）**：不直接调构造函数，而是经一个方法构造。用途：封装初始化逻辑、语义清晰、支持多创建方式。

```python
d = _Deadline.start(30.0)   # 内部计算 deadline = time.monotonic() + 30
```

`_Deadline.start()` 里 `cls(...)` 等价 `_Deadline(...)`；写成 `cls` 使子类自动获得正确类型。

### 1.3 高频语法速查

| 语法 | 示例 | 含义 |
|---|---|---|
| `with ... as x` | `with self._session_lease(...) as transport:` | 自动资源管理（≈ try-with-resources / RAII） |
| `@contextmanager` | `def _session_lease(...)` + `yield` | 把函数变成 `with` 可用：`yield` 之前=进入，之后=退出 |
| `*` 参数 | `def f(self, *, host, user)` | `*` 后全部 keyword-only |
| `raise ... from exc` | `raise X(...) from exc` | 异常链，保留原始 traceback |
| `time.monotonic()` | `deadline = now + timeout` | 单调时钟，适合测量时长（不受系统时间调整影响） |
| `-> "类型"` | `def f() -> "_Deadline":` | 前向引用写法（或 `from __future__ import annotations`） |

## 2. Python 的三种并行形态（与单片机概念对照）

| 单片机世界 | Python 对应 | 真并行？ |
|---|---|---|
| RTOS 多任务（FreeRTOS） | `threading` 多线程 | 否（单核分时 / CPython 有 GIL） |
| 多块 MCU 协作 | `multiprocessing` 多进程 | 是（多核，≈ 开多个命令行） |
| 中断 + 主循环（协作式） | `asyncio` 单线程事件循环 | 否（协作式让出） |

### 2.1 threading（本项目采用）

- 同一进程内多线程，**共享内存** → 需锁保护共享数据。
- **GIL（全局解释器锁）**：任何时刻只有一个线程执行 Python 字节码。

| 操作类型 | GIL 行为 |
|---|---|
| 计算（解析 JSON、拼串、算 hash） | 持锁，串行 |
| I/O 等待（`recv()`、`read()`、`waitpid()`） | **立即释放锁**，线程被内核挂起 |

> 本项目负载 ≈ 100% 是"等待"（等 daemon / SSH / 文件），GIL 影响可忽略 → 线程模型成立。

### 2.2 本项目为什么不用 asyncio

`paramiko`、`subprocess` 都是同步阻塞库，直接放入协程会卡死事件循环；标准解法仍是丢线程池。v1 决定：线程模型。

### 2.3 判断依据

> **I/O 密集（等网络/磁盘）→ 线程或 asyncio；计算密集 → 多进程才能真正用满多核。**

## 3. SSH 是什么

SSH（Secure Shell）是**协议**：在本地机与目标机之间建立一条**加密的字节管道**。TCP 负责连通（IP 找机器、端口找程序），SSH 在 TCP 之上负责**认证 + 加密**。

- 建连（握手：TCP 三次握手 → 密钥交换 → 身份认证）是**秒级**成本。
- 建好后管道内跑多少命令都复用同一管道；管道内可开多个 **channel（逻辑子通道）** 并发复用（scp/sftp/`-L` 转发/exec 互不干扰）。
- 远端 sshd 主进程监听 22 端口，**每来一条 SSH 连接 fork 一个子进程专门服务它**；子进程阻塞在 `select()` 上等字节。前台只负责"接客"，不搬运数据。

### 3.1 一次 SSH 登录的进程拓扑（修正常见误解）

```text
本地机                                       远端 server
ssh 客户端进程（隧道等）  ◄── 一条加密 TCP 连接 ──►  sshd 主进程（监听 22）
                                                └─ fork → sshd 子进程（与客户端 1:1）
```

**关键事实：**
- "常驻"不是某个特殊实体，而是**两端各有一个进程阻塞在等待上**（`select()`/`recv()`），中间一条活着的 TCP 连接。
- 子进程数按 **SSH 连接数** fork，不按 channel 数。channel 是子进程内部的逻辑状态机。
- 命令真正执行时，sshd 子进程再 fork 一个**临时 shell**（如 `sh -l`），跑完即退。

### 3.2 一次命令（exec channel）的完整路径

```text
本地 ssh 客户端                                 远端 sshd 子进程
开 channel → exec_request("sh -l") ───────────► fork 出 shell 子进程
sendall("ls")  ───────────────────────────────► shell 的 stdin
recv() 阻塞 ◄─────────── stdout/stderr 加密回传 ── shell 的 stdout/stderr
recv_exit_status() ◄────────────── 退出码 ────── shell 退出
```

> **命令不是发给"某个端口"，而是发给 sshd 的一个执行请求**；sshd 把 channel 与子进程的 stdin/stdout/stderr 对接。这解释了"命令发到哪、怎么回来"。

## 4. 端口转发（隧道）：为什么本地程序能访问远端的 127.0.0.1

daemon 只监听远端 `127.0.0.1:65081`（安全：不暴露给局域网）。本地程序要访问它，用 `ssh -N -L`：

```text
ssh -N -L 65082:127.0.0.1:65081 user@server
     └─ 本地监听 65082，把字节经 SSH 加密送到远端，sshd 以"远端本地人"身份连 65081
```

**本质**：本地 ssh 客户端进程在 65082 开一个"假服务端"，任何程序连它，ssh 客户端就把连接吞下、加密搬进 SSH 管道；远端 sshd 解密后**替它**去连 `127.0.0.1:65081`，回复原路返回。两端看到明文，中间密文。

**"常驻"的全景**（本项目中每个常驻者都阻塞在同一模式上）：

| 常驻者 | 在等什么 | 等的方式 |
|---|---|---|
| sshd 前台（远端） | 新登录者连 22 | `accept()` 阻塞 |
| sshd 子进程（远端） | 该连接上的字节 | `select()` 阻塞 |
| 隧道进程（本地，`start` 拉起） | 65082 敲门 + SSH 有字节 | `select()` 阻塞 |
| daemon（远端，CIW 拉起） | 65081 敲门 | `accept()` 阻塞 |
| 请求线程（上层，每请求一个） | 自己的 socket 有数据 | `recv()` 阻塞 |

> 共同点：全部阻塞在系统调用上，CPU 占用 ≈ 0，由内核唤醒。没有轮询、没有忙等。

### 4.1 SSH 常驻的三种形态辨析

- sshd 前台：常驻监听 **22 端口**——但它是**认证入口**，不是"服务转发器"。
- 隧道进程：常驻监听 **65082**——这才是"转发窗口"，且窗口开在本地（`-L`）。
- 22 的"客人"是 ssh 客户端（一次）；65082 的"客人"是上层程序（每次请求都来）。

比喻：22 是"大门"（开一次），65082 是"窗"（随请求开关），管道是"走廊"（一直亮灯）。

### 4.2 -L 与 -R：为什么分方向（端口是否对等？）

**TCP 连接建立后是全双工的、两端对等**——回复沿原连接原路返回，不需要任何"回传寻址"设计。不对称只存在于"谁先伸手"：

| | `-L` 本地转发（本项目） | `-R` 远程转发 |
|---|---|---|
| 窗口开在哪 | 本地 | 远端 |
| 谁先伸手 | 本地程序连本地窗口 | 远端程序连远端窗口 |
| ssh 在对侧 | 替本地程序连远端目标 | 替远端程序连本地目标 |
| 适用 | daemon 在远端只听 127.0.0.1，本地想访问 | 服务在本地只听 127.0.0.1，远端想访问 |

> 窗口永远开在"伸手的人"这边。回复不需要专门设计——全双工是 TCP 的内置属性。

### 4.3 单次请求经过隧道的接力（数据搬运工是谁）

```text
你的线程          隧道进程(本地)         sshd子进程(远端)         daemon
sendall(JSON) ──► 内核缓冲（线程即走，去 recv 睡觉）
                  select 醒来→读出→加密→扔进 SSH 连接 ──► 解密 → 以"本地人"身份连 127.0.0.1:65081 ──► accept/读JSON/执行
                  ◄────── 加密回传 ──────────────────── ◄── sendall(回复)
select 醒来？否：recv() 一直阻塞；内核唤醒 ◄── 解密写回 conn 65082
```

- 每段只有一个搬运工：线程只碰第一跳和最后一跳；隧道进程与 sshd 子进程各自阻塞在 `select()` 上"有活就搬"。
- 数据穿过 4 次"写→读"接力，但请求线程只参与第一棒。

## 5. 本项目的两大通道（与"两条服务"的关系）

项目实际管理两条**相互独立**的服务：

| 通道 | 用途 | 路径 | 协议 |
|---|---|---|---|
| Skill 通道 | 执行 SKILL | 上层 → TCP 连本地 65082 → 隧道 → daemon → **IPC 管道** → CIW | JSON+EOF（见 protocol-v1） |
| 命令/文件通道 | 敲命令、传文件 | 上层 → SSH exec channel / SFTP → 远端 shell/tar | 不经 daemon、不经隧道端口 |

- daemon 通道**不执行命令行，不处理文件**（protocol-v1 明文）。
- 两条通道共享同一条 SSH 连接（OpenSSH 后端用 **ControlMaster**：同 host 所有 ssh 调用共享一条 TCP，"N 次冷握手 → 1 次"；paramiko 后端共享一条 transport），但语义完全独立——daemon 死了不影响命令通道。

### 5.1 Skill 通道为什么"每次请求都新建 TCP 连接"？

协议设计：**一条连接 = 一个 request + 一个 response**（写完后 `shutdown(SHUT_WR)`，EOF 即帧边界）。刻意为之，三个理由：

1. **帧边界零成本**：TCP 是字节流无消息边界；"连接关闭"天然是分帧符，无需长度前缀/分隔符。
2. **daemon 串行，排队由内核白送**：新连接在 TCP backlog 排队，daemon 忙完前一条再 accept 下一条。
3. **崩溃隔离**：一条连接坏只死一个请求，重试 = 重新 connect（微秒级）。

**成本结构（项目通用哲学：贵的常驻，便宜的一次性）**：

| 通道 | 贵的部分 | 策略 | 每次请求付的 |
|---|---|---|---|
| Skill 通道 | SSH 握手（秒级） | 隧道常驻 | 本地 TCP 握手（微秒） |
| 命令通道 | SSH 握手（秒级） | transport/ControlMaster 常驻 | 开一个 channel（微秒） |

> 何时才需要 keep-alive 复用同一条 TCP？每请求耗时极短且频率极高（每秒数百次）时。协议已预留 `request_id`，但 v1 不做。

### 5.2 常驻 vs 临时完整清单

```text
常驻（生命周期长，建立代价高）：
  sshd 前台 / sshd 子进程（随连接）/ CIW / daemon（CIW 活着它就活着）
  隧道进程（ssh -N）/ SSH 连接本身 / 上层服务进程 / 注册表（磁盘）
临时（生命周期短，建立代价低）：
  每次 execute_skill 的 TCP 连接（本地 65082，用完即弃）
  每次 run_command 的 channel 与远端临时 shell
```

生命周期责任链：

```text
virtuoso-bridge start（本地 CLI，临时）→ 起隧道（常驻）+ 部署 SKILL 桥文件 + 打印 load 行
用户手动在 CIW load → ipcBeginProcess 拉起 daemon（常驻，直到 CIW 退出）
上层 Python（服务形态，常驻）→ 冷启动读注册表建 session 池 → 每请求查池连隧道 → 失败自愈
```

## 6. "一个进程服务多个请求"：三种组织方式

**破除误区：一个请求不需要一个进程。** 进程在 `recv()` 阻塞时被内核挂起、不占 CPU，因此单进程内可以同时"等"很多请求。单进程内三种组织方式：

| 方案 | 进程 | 线程 | 同时处理的请求 | 适用 |
|---|---|---|---|---|
| 单线程顺序 accept | 1 | 1 | 1（其余在 TCP 队列排队） | daemon（Virtuoso 语义必须串行） |
| **每请求一线程** | **1** | 1+N | N | 服务形态（推荐，本项目文档采用） |
| select 事件循环 | 1 | 1 | N | 隧道进程 / sshd 子进程 / asyncio |

**结论：一个 PID 足以服务几十上百个并发请求**——只要负载是"等待"而非"本地计算"。多进程在本项目中的目的不是并发，而是**进程隔离**（每用户一个 daemon，崩溃不互连、CIW 串行语义互不干扰）。

### 6.1 三层"数量"不要混淆

```text
进程（PID）  ← 上层 server 一个；每用户 daemon 一个；隧道一个
线程        ← 每请求一个（或 select 模型下没有）
channel     ← 每并发命令一个（受 MaxSessions / BoundedSemaphore 限制）
```

### 6.2 多用户并发模型速览（详见并发处理设计.md）

- **跨用户**：真并发。每用户独立 daemon 进程 + 独立 SSH 会话，OS 调度，无需额外机制。
- **单用户单 daemon 内**：串行排队。CIW `evalstring` 同步执行，TCP backlog 天然排队（当前 `listen(1)` backlog 过小，重构需调大或上层限流）。
- **上层 API**：同步阻塞调用，并发由调用方（`ThreadPoolExecutor` 等）实现。
- **并发安全三条纪律**：注册表只读共享（冷启动读一次）；连接对象实例私有（禁止跨 session 共享 socket）；禁止模块级可变全局状态（旧架构 `.env` 全局状态模型进不了服务形态的根因）。

### 6.3 多 SSH 连接：何时需要？

同一地址开任意多条 SSH 都合法（sshd 天生多连接）。共享一条是因握手贵而 channel 便宜。需要多条的场景：

1. 突破单连接内并发上限（MaxSessions 默认 10，一条连接内并发 channel 上限）；
2. 按角色/用户/密钥/跳板路径隔离（本项目 split-host 角色、多 profile 即多条 SSH 并存的现成例子）；
3. 故障隔离（一条断不影响另一条）。

### 6.4 三用户三连接布局示例（修正的进程账目）

```text
布局：A、B → 1号机器；C → 2号机器；每人一条 SSH，内含两个 channel（命令 + -L 隧道）
1号机器：sshd 前台 1 + sshd 子进程 2（按 SSH 连接数 fork：A、B 各一）
         每子进程内部 2 个逻辑通道（命令 channel、隧道 channel）
         + daemon_A、daemon_B（CIW 拉起，独立进程，与 sshd 无父子关系）
2号机器：sshd 前台 1 + sshd 子进程 1（C）
         + daemon_C
```

> 子进程数按"SSH 连接数"，不按"通道数"；通道是子进程内部的状态机。daemon 与临时 shell 是独立进程，不在 sshd 的账本里。

## 7. 网络请求旅程总图（HTTP server 场景的传输层骨架）

无论上层是 HTTP 还是 MCP，请求-响应在传输层的骨架一致（以 execute_skill 为例）：

```text
① socket()      向内核要文件描述符
② connect(127.0.0.1:65082)   三次握手（微秒级，backlog 排队由内核完成）
③ sendall(JSON) 交给内核发送缓冲（线程随后去 recv 睡觉）
④ daemon 读完整 JSON → 校验 token → SKILL 写入 CIW IPC 管道 → 阻塞等待
   （CIW evalstring 执行：秒 ~ 分钟）
⑤ 请求线程早已 recv() 阻塞挂起——不占 CPU，其他线程照常运行
⑥ daemon 回复经隧道回到本地 65082 → 内核唤醒线程 → recv() 返回
⑦ close() 四次挥手
```

> **最重要的一句话**：`recv()` 不是"持续盯着看数据来没来"，而是"我睡下了，数据来了叫我"——叫人的是操作系统内核。
