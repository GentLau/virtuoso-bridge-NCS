## 五、冻结前必须收口的主要冲突

### P0-01：默认 Paramiko 与“一 endpoint 一条 SSH”冲突

**当前文本：**

- `配置一览.md §2.2` 第 37 行规定默认 `paramiko`；命令、文件、GUI、Spectre 走 Paramiko 多 channel，而 Skill 隧道由外部 OpenSSH `ssh -N -L` 承载；
- 架构术语及 §5.2/§5.5、多节点 §6、并发 §11.1 均规定同一 token 内相同 endpoint 复用一条 SSH 连接；
- 配置 §6.5 第 353、367 行还写成同 endpoint “共享一条 SSH 连接与 ControlMaster”；
- 并发 §7/§10.2 又出现“对每台目标机器一条 SSH，内含 `-L`”与“隧道连接单独承载 Skill 转发”两种描述。

按当前默认配置，同一 endpoint 至少存在业务 Paramiko transport 和外部 OpenSSH tunnel 两条 SSH 连接。这里不是实现细节，而是公开配置值与连接资源合同不一致。

**最小整改：**任选一种并统一 owner：

1. 定义为“每 token×endpoint 一条业务连接，daemon role 另有一条专用 Skill tunnel”；
2. 让 Paramiko transport 同时承载 Skill forwarding；
3. 暂时取消 Paramiko 作为本版完整后端。

不要求指定实现方案，只要求 endpoint 的连接数量、ControlMaster、tunnel 生命周期和 channel 账本采用同一口径。

### P0-02：逐 role 探测 owner 与 spectre 失败边界冲突

**owner 重复：**

- README owner 表把“探测/部署/连通性合同”归入多用户设计；
- 多节点 §4 又完整定义逐 role 探测矩阵；
- 多用户第 146 行反过来又说逐 role 探测矩阵的唯一 owner 是多节点设计。

**行为冲突：**

- 多节点 §4 第 68–72 行和多用户第 146 行把 spectre role 的命令、SSH/host-key、root、bin 探测失败整体写成 WARNING、不阻断；
- 配置 §4.1–§4.3 只明确 `role.spectre.bin` 和 spectre 指纹为 WARNING 例外，root/配置不可用仍落入拒绝规则；
- 多用户第五步又把业务 role host-key mismatch 写成 ERROR，同时把 spectre 指纹写成 WARNING；
- canonical registry 要求探测后五个 `role.*.root` 都有最终绝对路径，但若 spectre SSH/root 探测失败仍允许注册，提交态如何形成没有定义。

**最小整改：**

1. 明确 owner 分工：多用户只拥有六步时序、deadline 和注册失败合同；多节点拥有逐 role 探测矩阵；另一处只保留摘要+链接；
2. 明确 spectre 例外覆盖范围：是整个 spectre role，还是仅 `bin`/指纹；若允许 SSH/root 失败继续，说明 root 的提交态，否则将 SSH、命令可用性和 root 列为阻断项。

不要求增加 Spectre 功能，只要求注册成功/失败结果唯一。

## 六、冻结前应修正的局部基本行为

### P1-01：SSH alias / `~/.ssh/config` 的读取边界不一致

- 配置 §2.2 第 37 行要求按 `ssh -G` 解析 alias 和 ProxyJump；
- 配置 §6.5 第 373 行要求根据 alias/跳转链解析实际端口并拒绝非 22；
- 同一 §6.5 第 354 行又写明“不读 `~/.ssh/config` 做映射”。

这可以被合理解释为“允许读取 SSH 配置用于 transport 参数和端口校验，但不把 alias 与真实 hostname 合并为同一 endpoint 身份”，然而当前文本没有明确这层区分。

**建议：**明确 SSH config 只用于 transport 解析/22 端口校验，canonical key 仍按规范化后的输入字符串计算；或删除 `ssh -G` 规则并完全禁止读取。

### P1-02：注册第一步的必填参数与配置 owner 不一致

多用户第 87、113 行仍称第一步必选参数包含“各 role 主机/端口”。但配置 owner 明确：

- host/user 只对 remote role 生效，并可从全局默认继承；
- local role 显式提交这些字段是参数错误；
- 只有 daemon role 有端口字段，且 daemon/local port 可缺省自动分配。

**建议：**多用户只写“必填项以配置一览 §4 为准；至少 `mode.default`、`user`，remote role 必须可解析目标”，不要再次复制字段清单。

### P1-03：`mode=local` 的 daemon/local port 需要联合 reservation

配置 §2.3.2、§6.3 明确 `mode=local` 时 `local_port = daemon_port`；但 §6.4 的流程又规定：

- 缺省 `local_port` 在第二步锁内先分配；
- 缺省 `daemon_port` 留到第三步才分配。

当 daemon role 为 local 且两者都缺省，当前文本没有明确第三步必须复用第二步已分配的同一个端口；当只填写其中一个时，也没有写明另一个如何镜像该值。实现者可能错误地选择两个不同端口。

**建议：**把 local mode 的两个字段定义为一个联合 reservation：任一缺省都由同一候选端口生成并同步写入；显式给出两个值时必须相等。

### P1-04：全局 SSH 默认 host/user 的必填条件过宽

配置 §4.2/§6.1 写“存在 remote role 时 `ssh.default.host/user` 必填”，但同表又允许每个 remote role 显式提交自己的 `role.<name>.host/user`。因此“每个 remote role 都显式提供 host/user、没有全局默认”到底是否合法，当前文本没有唯一答案。

**建议：**改为“存在未提供 role 级 host/user 的 remote role 时，全局 default host/user 必填”；或者明确全局值始终必填并删除 role-only 方案。

### P1-05：建连重试次数有两种解释

- 架构 §5.8 第 340、348 行、多用户第 214 行写“最多 3 次总尝试”（初次+2 次重试）；
- 并发 §11.1 第 419 行写“最多重试 3 次”，多用户第 215 行也写“重试 3 次”。

**建议：**并发 owner 统一写“最多 3 次总尝试（含初次）”，其他位置只索引。

### P1-06：split-host CDS.log 当前可观察合同不闭合

范围文档 §2 第 24 行写 split-host 本版“不返回该增量”，但同时写 bridge 不做拓扑判断、仅按第二帧/路径可用性决定；日志 owner 又允许 daemon 在可读 path 上按 offset 读取。若 CIW 与 daemon 不同主机但共享文件系统，daemon 可能读到日志并返回增量，无法同时满足两句规范。

**建议二选一：**

- 改成“本版不保证 split-host；不可读时返回空 log+warning，可读时按普通路径处理”；或
- 保留“一律不返回”，并定义可识别的 split-host 判定。

不要求增加完整 split-host 日志系统。

### P1-07：探测结果写入 registry 的术语与第六步唯一写盘点冲突

配置 §4.3 第 196 行写 `role.daemon.python` 在探测时“写入注册表”；多用户 §3.2 第 65、180、186–190 行明确前五步不写 registry，第六步才提交。

**建议：**统一为“写入内存候选对象/ProbeResult；第六步写入 registry”。`registry.reservation` 仍可作为第二步起的临时旁车，但不应称为 user registry 条目。
