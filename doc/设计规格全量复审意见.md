## 三、P0：必须在冻结前解决的直接冲突

### P0-01：`token`/`log_level`/`log_max_bytes` 到底是每次调用参数还是注册配置

**证据：**

- `C:\Users\user\Desktop\repos_Github\virtuoso-bridge-NCS\spec\design-concepts\总览\配置一览.md:16` 将 `token`、`log_level`、`log_max_bytes` 一并列为“每次调用的参数，不进配置”；
- 同文件 `:26` 又将 `token` 定义为“配置”，`:46-47` 将 `cdslog.log_level`、`cdslog.log_max_bytes` 定义为持久化配置；
- `C:\Users\user\Desktop\repos_Github\virtuoso-bridge-NCS\spec\design-concepts\底层与中层\日志返回设计标准.md:89-95` 明确说两个日志字段由中层从注册表填充，上层接口不新增参数；
- `C:\Users\user\Desktop\repos_Github\virtuoso-bridge-NCS\spec\design-concepts\总览\三层整体架构设计.md:164-169` 的接口签名也没有 `log_level`/`log_max_bytes`。

**影响：**

实现者可以合法地实现成：

- A：每次上层调用显式传日志级别和上限；或
- B：注册时固定，运行期只从 registry 注入。

这两种实现的 API、registry schema、缓存策略和测试断言不同。`token` 还具有“持久化身份”和“每次调用携带值”两种不同角色，不能用一个“是否进配置”的句子覆盖。

**必须收口：**

明确写成两层语义：

- `token`：持久化身份/路由配置，同时是每次 Skill/Command/File 调用携带的授权与寻址参数；
- `cdslog.*`：若本版固定由注册配置决定，就从“每次调用参数”列表删除，并保留“中层注入 wire 请求”的说明；若要逐调用覆盖，则必须把字段加入上层接口签名、定义覆盖优先级和审计行为。

这是当前最直接的规格冲突之一。

### P0-02：一个 token 对应一个 CIW，还是允许多个 CIW 同时 load 同一部署

**证据：**

- `三层整体架构设计.md:135-145` 定义一个底层 daemon 对应一个 Virtuoso 会话和一个 Skill 端点；`:271-273` 再次规定底层一对一；
- `多用户设计.md:45-50` 将 token 绑定到“daemon 主机 + daemon 端口 + CIW 会话”；
- 但 `多用户设计.md:396` 又把“一份部署一个 token，可被同一用户的多个 CIW load”列为已定行为。

**影响：**

同一部署包含固定 daemon 端口和固定 token。两个 CIW 同时 load 时，至少会出现以下未定义情况：

1. 两个 daemon 竞争同一监听端口；
2. 若其中一个成功，token 到底代表哪一个 CIW；
3. 若两个端口被人为改写，registry 又没有多个 endpoint 或选择规则；
4. `execute_skill(token)` 无法保证“到达哪个 CIW”。

这不是文案问题，而是路由唯一性和安全边界问题。

**必须收口：**

推荐本版改成“一个 token 对应一个活动 daemon/一个 CIW；需要第二个 CIW 就注册第二个 user/token”。如果确实要支持同 token 多 CIW，必须增加并定义 endpoint 集合、端口分配、选择/广播语义、并发语义和回收规则；不能只写“多个 CIW load”。

### P0-03：split-host 已被宣布支持，但 endpoint/schema/探测/文件根合同不完整

**证据：**

- `三层整体架构设计.md:261-265` 明确允许 `skill/command/file/spectre` 落在不同主机，并要求按每个不同 `(host,user,jump)` endpoint 建连接；
- `配置一览.md:34` 只有 `expected.ssh_endpoints` 指纹 map，但没有定义 map key 的规范序列化、同 host 不同 user/jump 的区分规则、proxy 是否参与 endpoint 身份；
- `配置一览.md:62-69` 定义了 daemon/command/file/spectre host，却没有为 `file` 和 `spectre` 定义独立 user，也没有为每个 role 定义独立 jump/proxy 组合；
- `配置一览.md:65` 把 `route.command.user` 默认到 `expected.daemon_user`，但注册流程又同时区分 SSH 登录用户和 daemon 进程用户（`多用户设计.md:105-110`）；
- `多用户设计.md:107-115` 的第三步探测表主要只描述一个 SSH/daemon/deploy 主机，`:177-180` 又要求第五步检查“全 endpoint host-key”，两者之间没有逐 endpoint 的清单；
- `三层整体架构设计.md:283-286` 宣布一个 `deploy.scratch_root` 同时是部署根和文件默认根，但没有说明 file host 与 daemon host 不同且没有共享文件系统时，默认根如何成立。

**影响：**

当前规范无法唯一回答：

- File 连接以哪个 user 登录；Spectre 未来连接以哪个 user 登录；
- 两个 endpoint 的 host 相同但 jump/user 不同是否共享 ControlMaster；
- 每个 endpoint 的 host key 从哪个 known_hosts/跳板路径取得；
- file host 是否必须与 daemon 共享 `scratch_root`；
- 第三、四、五步到底逐个检查哪些 endpoint；
- channel budget 是每 endpoint 还是整个 token；
- 路径默认根在分裂主机上是否可见。

**必须二选一：**

- **收窄本版**：只支持单一远端 SSH endpoint，删除/降级 split-host 承诺和悬空 role 字段；或
- **补完本版**：为每个 role 定义 `(host,user,jump,proxy,known_hosts,root)`，定义 canonical endpoint key、每 endpoint 指纹、探测/部署/连通性矩阵、共享文件根条件、channel/ControlMaster 作用域和失败行为。

在没有二选一前，split-host 不是“已完成设计”。

## 四、P1：影响唯一实现或验收完备性的缺口

### P1-01：Spectre 被声明为不支持，却被做成注册硬前置条件

**证据：**

- `本版范围与明确不支持.md:16` 规定不提供 `purpose` 和 Spectre 业务消费入口，`route.spectre.host/bin` 只在注册期探测/记录；
- `配置一览.md:67-68,102,122` 又规定 `route.spectre.bin` 必须显式提供或自动探测，探测/校验失败即拒绝注册；
- `多用户设计.md:269-275` 的路由差异只定义 Skill、RunCommand、File，没有 Spectre 的本版调用合同。

**问题：**

没有 Spectre 业务入口时，Spectre 不可用是否应阻断一个本来可以正常使用 Skill/Command/File 的用户注册？当前文本同时允许“仅记录”和“硬门禁”两种解释。

**建议：**

本版若不消费 Spectre，应将其设为可选、非阻断的未来字段；若必须作为环境准入条件，应在范围文档中明确“注册成功的必要环境包括 Spectre”，并补上调用入口、endpoint user、路径和测试合同。

### P1-02：注册第五步、runtime 冷启动、断线重连的检查矩阵没有闭合

`多用户设计.md:173-180` 将主动检查分成注册第五步、runtime 冷启动、断线重连和业务调用，但检查项不一致：

- 注册第五步要求全 endpoint host-key、banner、daemon user、命令冒烟、Skill 冒烟；
- 冷启动只写“建连接 + 隧道就绪 + 首次 Skill 冒烟”；
- 断线重连只写“同冷启动，并比对 banner”；
- `配置一览.md:127` 又说所有 `expected.*` 运行期都要比对，host-key 例外阻断。

未定义的关键问题包括：

1. 冷启动/重连是否都必须比对 host-key；
2. `expected.daemon_user` 在运行期如何获取；
3. command、file、spectre endpoint 是否各自做连接/可见性检查；
4. 注册部署失败或第五步失败后，远端半成品如何回滚；
5. 业务调用“零探测”与 token 校验、连接重建之间的边界。

应增加一张唯一的时机 × endpoint × 检查项 × 失败级别矩阵，避免注册流程、运行时和并发文档各写一部分。

### P1-03：deadline、连接重试、幂等性与结果未知没有可执行的统一合同

**证据：**

- 架构文档 `:292-294` 只规定端到端 deadline 和剩余预算；
- 配置文档 `:45` 只有 `runtime.connect_timeout`；
- 并发文档 `:416` 又规定握手阶段最多重试 3 次；
- 架构错误表 `:241-248` 要求区分 124/255/UNKNOWN，但没有定义默认业务 timeout、重试间隔、重试次数如何受调用 timeout 约束；
- persistent shell 失效时，文档说幂等命令可重发、非幂等命令返回未知，但没有幂等声明参数、判定规则或上层确认机制。

应明确：`timeout=None` 的默认值、`connect_timeout` 与调用 deadline 的优先级、每次重试是否重新消耗同一预算、命令超时后的 shell 状态、何时生成 `VB-UNKNOWN-EFFECT`、如何避免真实命令返回码 124/255 与桥保留码混淆。

### P1-04：结果模型与错误合同仍有字段/行为缺口

- `三层整体架构设计.md:236-248` 说三个接口一律返回结构化结果且结果附 `warnings`；但同一合同只明确了 `VirtuosoResult` 的 `warnings`，没有定义 `CommandResult`/File 如何承载 warnings。
- `:182` 又说 token 缺失“直接报错”，与“对外一律返回结构化结果、不向上抛传输异常”之间没有区分参数编程错误、运行时未知 token、daemon NAK。
- `CommandResult` 用 `returncode=124/255` 和 stderr 文本区分 timeout/transport/unknown effect，但没有稳定的 machine-readable `kind/code` 字段；真实命令也可能返回同样数值。
- `unknown token`、文件校验失败、注册表损坏、host-key mismatch 的公共返回形态没有统一到同一错误枚举。

冻结接口前应给出公共错误码/错误类别表，明确哪些是 Python 参数异常、哪些必须封装成结果。

### P1-05：Registry 生命周期声明了 update/remove，但没有闭合撤销、并发和缓存语义

`多用户设计.md:192-200,402-411` 已定义 `user update`、`user remove`、原子覆盖和运行时缓存关闭，但仍缺少：

- 多进程同时注册/更新时的文件锁或版本冲突策略；单纯 tmp+replace 不能避免两个进程丢失更新；
- token 碰撞是在第二步拒绝，还是到第六步才拒绝；自动生成碰撞如何重试；
- `user update` 改 route/expected/cdslog 后，已缓存的 token client 何时失效、连接如何 drain；
- `user remove` 在“registry 删除但远端 daemon/部署目录保留”时，是否称为注销、撤销还是仅本机解绑；
- 删除后旧进程仍持有 token 时，token 是否仍可通过已存在 tunnel 调用。

尤其是“remove 才销毁 token”与“remove 不停 daemon、不删远端部署”不能同时作为安全撤销语义，必须改名或补充真正的远端撤销/轮换动作。

### P1-06：host-key 首信任规则有分支，但输入合同不完整

`配置一览.md:134-137` 规定：known_hosts 匹配、用户显式提供指纹、两者都没有则失败。这一规则方向正确，避免无条件 TOFU；但 §4.2 可提交参数中没有对应的“显式 host-key 指纹”字段，也没有说明多 endpoint 时如何提交每个指纹。

应增加明确的 per-endpoint 指纹输入 schema，或删除“用户显式提供指纹”分支；同时规定 alias、IPv4/IPv6、jump/proxy、known_hosts 文件来源和指纹算法。

### P1-07：日志标准仍缺少内部元数据帧和限长边界的精确定义

正式日志方向已经正确，但以下细节仍允许不同实现：

1. `日志返回设计标准.md:39-41,127-129` 只写“第二帧返回 path/start/end”，没有定义内部 frame 的字节格式、编码、分隔符、转义、整数格式、frame 顺序和超时行为；
2. `:78-82` 规定降级/截断说明不受 `log_max_bytes` 限制，因此“单次日志内联长度上限”实际不是返回 payload 的硬上限；应明确上限只约束原始日志字节，或把说明做成结构化字段；
3. `:114` 写“非法值按配置校验拒绝或夹紧为默认”，冻结规范不应同时允许两种行为；
4. `:55-61` 的 `\e`、`\w` 等前缀没有明确是两个 ASCII 字符还是控制转义；
5. UTF-8 字节截断是否允许拆分多字节字符、缺失/轮转 warning 的固定字段和文本尚未定义。

### P1-08：注册输入、registry schema、端口和跨平台路径合同仍不完整

当前配置文档是字段目录，不是完整的注册 API/schema 合同：

- `配置一览.md:105-122` 使用“SSH host”“daemon port”等人类标签，没有给出注册请求的 canonical 字段名、JSON/CLI/HTTP 映射、缺省字段的序列化规则和未知字段处理；
- `多用户设计.md:82-86` 要求六步注册，但没有定义注册状态、错误、warning、候选对象和第六步 commit 的公共返回模型；
- 第二步只检查 registry 内端口，第三步才探测 OS 端口，缺少跨进程 reservation/TOCTOU 规则；local 默认端口、自动 token、自动端口的冲突重试规则也没有统一写出；
- `user` 同时是 registry key 和跨平台路径段，`配置一览.md:132` 只有字符正则，没有定义 Windows 大小写折叠、保留设备名、尾点/尾空格和目录规范化后的冲突处理；
- `三层整体架构设计.md:283-286` 提到原子落盘、symlink、覆盖目录和路径可见性，但没有给出 recursive File 操作、目录覆盖、权限、校验和失败返回的完整 owner 合同。

冻结前至少应补一个 canonical registry schema/注册 API 附录，以及 mode × route 的兼容矩阵、端口 reservation、跨平台 user/path 规则。

### P1-09：版本治理自身没有完全执行 README 的规则

`spec/README.md:11-21` 规定 owner 和 `Supersedes`，但：

- README 的 owner 列表漏列了同一 README 文档表中标为 Normative 的《本版范围与明确不支持》；
