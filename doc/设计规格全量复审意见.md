## 三、P0：仍需在冻结前解决的直接冲突

### P0-01：Spectre 的“非阻断”与“全 endpoint host-key 强制 ERROR”互相冲突

**证据：**

- `C:\Users\user\Desktop\repos_Github\virtuoso-bridge-NCS\spec\design-concepts\总览\本版范围与明确不支持.md:16`：Spectre 仅注册期探测/记录，探测或校验失败只 warning、不阻断注册；
- `C:\Users\user\Desktop\repos_Github\virtuoso-bridge-NCS\spec\design-concepts\总览\配置一览.md:104-105`：只有 `route.spectre.bin` 被列为非阻断例外，但 host-key mismatch 仍是统一 ERROR；
- `C:\Users\user\Desktop\repos_Github\virtuoso-bridge-NCS\spec\design-concepts\底层与中层\多用户设计.md:177-182`：注册第五步检查“全 endpoint host-key”，endpoint 集合包含 `spectre.host`。

当 `spectre.host` 是独立主机而该主机没有 known_hosts 指纹、指纹变化或 SSH 不可达时，当前文字允许两种实现：

- 按 Spectre 非阻断策略继续注册；
- 按全 endpoint host-key 安全规则阻断注册。

这会直接改变注册是否成功。必须明确：

1. 若 Spectre 本版不消费，`spectre` endpoint 不进入注册必检集合，或只记录 warning；
2. 若所有 endpoint 都必须做安全校验，则应把 Spectre 明确从“非阻断未来字段”升级为注册安全前置条件。

### P0-02：canonical 注册 schema 仍不是自洽、可执行的完整合同

**证据：**

- `配置一览.md:146-162` 的注册请求字段没有列出 `route.command.host/user`、`route.file.host/user`、`route.spectre.user`，但 `配置一览.md:67-70,174-179` 的配置表和 registry 示例又使用这些字段；
- `配置一览.md:166` 声明 §6.2 是“完整 JSON 示例”，但示例中的 `a3f9c2…`、`/opt/…/spectre`、`1725…` 不是合法 JSON/token 值；
- 示例路由包含 `daemon-a` 和 `server-a` 两个 SSH endpoint，但 `expected.ssh_endpoints` 只有 `server-a|...` 一项，缺少 daemon endpoint 的指纹；
- `配置一览.md:200-205` 的 mode×route 矩阵只列 host，没有列 role user、jump/proxy、文件根和 fingerprint 必检规则。

因此 §6 不能作为注册页面、CLI、HTTP API 或测试 fixture 的唯一输入合同。必须补齐：

- 每个 canonical request 字段及其与 CLI/HTTP 的映射；
- role user 的提交/默认规则；
- 所有 endpoint 的完整 fingerprint 示例；
- 使用真实合法占位值的 JSON 示例；
- unknown field、缺省字段、空值和序列化规则。

### P0-03：channel budget 的作用域与并发文档互相矛盾，且漏记 SSH forwarding channel

**证据：**

- `配置一览.md:44`、`三层整体架构设计.md:281`、`多用户设计.md:170`：channel budget 是 **per token × endpoint**；
- `并发处理设计.md:410-412`：SSH connection 按 token×endpoint，但 channel budget 表写成“每 token 1 份”；
- `并发处理设计.md:470-479` 又按每 token 汇总，并固定为“隧道 channel ×1”；
- 同一文档 `:237` 规定每个 `execute_skill` 使用一个独立 TCP 连接，`ssh -L` 对每个被转发的 TCP 连接会产生独立 forwarding channel，因此不能固定只记一个 tunnel channel。

当前实现者无法确定：

- 预算是每 endpoint 独立，还是整个 token 的总额度；
- Skill forwarding channel 是否占预算；
- 一个 token 有多个 role endpoint 时，命令/文件/Skill 如何分别扣账；
- `ssh.max_sessions` 与 `runtime.channel_budget` 谁是硬上限、取 min 还是分别处理。

必须选定一个模型。建议以 **per token × endpoint** 为唯一预算，明确 forwarding channel 的计数规则，并将 `ssh.max_sessions` 定义为远端能力上限/观测值或删除重复配置项。

## 四、P1：影响完备性、唯一实现或验收真实性的问题

### P1-01：endpoint canonical key 仍缺少稳定、无歧义的序列化算法

`配置一览.md:34,159,213-215` 将 key 写成：

```text
host|user|jump_host|jump_user|proxy
```

但没有规定：

- host alias、大小写、尾点、默认端口、IPv6 的规范化；
- `proxy` URL 或其他字段包含 `|` 时的转义；
- 空值与显式默认值是否等价；
- 同一跳板通过 alias/IP 表示时是否视为同一 endpoint；
- key 变更时 expected fingerprint 如何迁移。

“canonical”若没有规范化和 escaping，不能保证同一 endpoint 只得到一个 key，也不能保证不同 endpoint 不碰撞。应定义版本化编码（例如长度前缀或 JSON canonicalization + hash），并给出正反例。

### P1-02：split-host 文件根语义在配置文档中仍与架构条件不一致

- `三层整体架构设计.md:265-269` 已规定：`deploy.scratch_root` 在 daemon 主机；只有 `file.host == daemon.host` 时才是文件默认根，分 host 时 `remote_path` 必须绝对路径；
- 但 `配置一览.md:71,76` 仍把同一个 scratch root 直接描述为“部署根 = 文件默认根”，没有条件限定；
- `多用户设计.md:165,197`、`src/transport/registry.py:57-60` 也没有把 file host 不同的条件写入 File 路由合同。

这会使调用方在 split-host 下误把 daemon 主机路径当成 file 主机路径。配置 owner 至少需要引用架构的条件语义，并在 mode×route 矩阵中明确：不同 file host 时默认根为空/禁用，只接受绝对 `remote_path`。

### P1-03：daemon_user 仍没有“如何运行成该用户”的合同

当前 Spec 允许 `daemon_user` 与 SSH 登录用户不同（`配置一览.md:65,153`），第三步只验证 `id <daemon_user>`，第五步再比较实际 daemon user。但没有定义：

- CIW 的 `ipcBeginProcess` 以谁的 Unix 身份启动 daemon；
- 是否允许/需要 sudo、setuid、SSH 直接登录 daemon_user；
- `deploy.scratch_root` 和 identity 文件由哪个账号创建、读取；
- 实际 daemon user 从哪个 banner/identity 字段取得；
- 无权切换用户时是注册失败还是 warning。

这不是简单的字段默认值问题；它决定部署能否成功和用户隔离是否成立。建议本版直接强制 `daemon_user == SSH 登录用户`，或补齐明确的 run-as 机制及失败矩阵。

### P1-04：新错误模型没有在 Spec 示例、外围文档和新 `src/` 同步落地

- 架构 `:238` 宣布 `CommandResult.kind` 是稳定字段，但 `:240-248` 的表没有列出 `capacity/rejected`、`checksum`、`invalid-token` 等类别，也没有说明 File warning 放在哪里；
- `三层整体架构设计.md:182` 仍只说 token 缺失“直接报错”，没有与运行期 unknown token 的封装边界示例；
- `C:\Users\user\Desktop\repos_Github\virtuoso-bridge-NCS\src\pyapi\models.py:53-58` 的 `CommandResult` 仍只有 `returncode/stdout/stderr` 三个字段，当前 `src/transport/middle.py`、`src/transport/tunnel.py` 也按三元组构造返回值；
- `C:\Users\user\Desktop\repos_Github\virtuoso-bridge-NCS\src/transport/register/flow.py:228-250` 在 Spectre 不可用时仍抛出注册失败，而最新 Spec 要求仅 warning；
- `C:\Users\user\Desktop\repos_Github\virtuoso-bridge-NCS\src/transport/registry.py:57-65` 没有 `route.file.user` / `route.spectre.user`。

因此当前 Spec 即使文字层面继续冻结，代码也不能判定为满足 Spec。需要先统一结果模型和实现字段，再重跑契约测试。

### P1-05：timeout/retry 的边界仍没有完全可测试化

最新架构 `三层整体架构设计.md:296-298` 已给出单次调用默认 30s、connect 默认 15s、传输最多重试 3 次，但仍未明确：

- `timeout=None` 对 Skill、Command、File 是否全部等于 30s；
- 注册第五步的 30s 是否包含用户等待 CIW load；
- “重试 3 次”是总尝试 3 次还是初次失败后再重试 3 次；
- persistent shell 重建后 cwd/env 是否恢复，重发失败如何生成 `unknown-effect`；
- log metadata 第二帧超时与 Skill 已完成但日志未读完时的最终状态。

这些都应转成可断言的状态/计时表，不能只用叙述性文字。

### P1-06：remove 的语义虽已补充，但旧表述仍会造成误读

`多用户设计.md:397` 仍写“`user remove` 才销毁 token”，而 `:411-412` 已明确 remove 只是本机解绑、远端 daemon 仍接受 token，真正吊销需要 `RBStop()` 并删除远端部署。两处对同一操作的安全含义不一致。

应把表格改为“remove = 本机 registry 解绑；不等于远端吊销”，并在 README/配置文档中统一说明 token 仍可被持有旧 tunnel 的进程使用。

### P1-07：历史/调用指南仍有会误导实现者的过期副本

尽管 `spec/` 的 Normative owner 已改善，以下非 Spec 文档仍会被实际开发者直接阅读：

- `C:\Users\user\Desktop\repos_Github\virtuoso-bridge-NCS\doc\接口调用指南.md:126-145` 仍描述调用区间 marker、旧的 error-only + 头尾 100 行算法，且 `:230` 仍链接已删除的 `spec/design-concepts/底层与中层/注册配置一览.md`；
- `spec/research/03-rebuild-key-technical-points.md:558-579` 仍把新实现证据写成不存在的 `src/virtuoso_bridge/...` 路径；
- `spec/research/04-log-return-system-proposal.md` 虽有历史声明，但仍保留旧 marker 方案和无效的历史 JSON 示例。

这些内容不应推翻 Normative owner，但违反“应索引而不复制”的验收目标。应修正调用指南，或在其顶部明确“仅历史、不适用于当前 API”，并统一旧实现路径指向 `src_bak/`。
