# 改动建议：管理员权限与每用户凭据（供 spec 采纳）

> 日期：2026-09-23
> 性质：**spec 层建议** —— 给出字段、语义、权限与流程；不规定实现手段
> 场景定位：公司内网，防误触发与误配置，非高安全等级服务
> 关联：控制面与业务面（权限等级）、配置一览（role 覆盖规则）、多用户与注册（注册流程）

## 一、要解决的问题

1. **"以什么身份运行"实际不可配**：所有用户共用服务账号的一把密钥，用户无法声明自己的远端凭据；
2. **`mode=local` 无归属限制**：普通用户可自助声明本地模式，等于以服务账号身份执行；
3. **身份/凭据的复用没有授权入口**：既无登记关系，也无"是否已被他人使用"的判定。

## 二、核心机制：注册时提供"加强凭据"

**注册（含变更）时可提交一份加强凭据，用于证明本次登记的正当性。**

| 凭据 | 用途 |
|---|---|
| 管理员凭据 | 任意注册与变更（现行机制，保留） |
| **已注册用户的 token** | 需要复用该用户**已登记的身份或凭据**时 |

规则：**复用他人身份/凭据必须由原持有者授权**，不能自行挂靠。管理员可代所有人登记；用户之间共用身份时须走此流程。

## 三、新增配置字段

沿用现行"role 覆盖 default"的规则。

| 字段 | 层级 | 语义 | 约束 |
|---|---|---|---|
| `key_dir` | `ssh.default.key_dir`、`roles.<name>.key_dir` | 凭据所在目录 | 目录路径 |
| `key` | `ssh.default.key`、`roles.<name>.key` | 凭据标识 | 文件名，不含目录成分 |

**解析规则**：`roles.<name>.key_dir` 优先于 `ssh.default.key_dir`；`key` 同理。二者需成对解析出完整凭据位置。

**命名提示**：既有实现中 `key` 一词已被占用表示 **endpoint 身份**（由 host/user/跳板/代理推导），因此 spec 在描述"凭据"时应使用独立措辞，避免与 endpoint 身份混淆。

**未解析到凭据时的行为**——需在 spec 中明确，二选一：
- （建议）远程模式必须解析出凭据，否则注册校验不通过；
- 回退到服务账号默认密钥（等同现状，但会保留"共用密钥"的形态）。

## 四、权限矩阵（建议）

| 动作 | 所需凭据 |
|---|---|
| 声明 `mode=local` | 管理员凭据 |
| 注册 / 变更任意条目 | 管理员凭据 |
| 复用他人已登记的身份或凭据 | 管理员凭据，**或**该凭据原持有者的 token |
| 查询用户列表 / 用户条目 | 管理员凭据 |
| 业务面调用（执行业务操作） | 个人 token |

补充口径：**`mode=local` 是单用户形态**，多用户身份隔离一律走 `mode=remote`（含指向 localhost 的 remote）。

## 五、凭据复用规则

- **判定**：该凭据是否已被其他条目登记使用；
- **命中**：要求申请方提供原持有者的 token；校验不通过则拒绝登记；
- **未命中**：正常登记为该条目的凭据。

需在 spec 中明确三个点：

1. **判定粒度**：按凭据位置，还是按公钥指纹（指纹更准，可识别同一密钥的不同位置）；
2. **授权记录的生命周期**：登记被删除后，该凭据是否仍视为"已被使用"（否则会重新变为可自由认领）；
3. **判定与登记的原子性**：检查通过后才写入，避免并发申请双双通过。

## 六、责任边界

- 凭据在远端账号 `authorized_keys` 中的**授权与撤销由用户负责**（内网定位下服务不承诺远端吊销）；
- 登记被删除时，系统应**告知需撤销的凭据**（凭据标识 + 公钥指纹），使该责任可执行；
- 凭据仍被其他条目引用时，不得因单个登记删除而失效。

## 七、待定项（需 spec 决策）

1. 未解析到凭据时的行为（见第三节）；
2. 复用判定按位置还是按指纹；
3. 授权记录是否随登记删除而失效；
4. 登记删除时凭据本身的处置；
5. 是否允许用户自定义 `key_dir`（若允许，则"指向他人目录但该凭据从未登记"的情形无法拦截；若需收紧，可限定为默认目录、仅管理员可改）。

## 八、明确不做（本版）

非对称 token、TLS / mTLS、请求签名与防重放、SSH 短期证书。
