## 一、结论先行

本轮走查发现三个问题，它们的**共同点是：正确性依赖未写进代码、也未写进文档的隐式前提**。

| # | 发现 | 严重度 | 与 Spec 关系 | 触发条件 | 建议动作 |
|---|---|---|---|---|---|
| 1 | **skill 请求一旦投递即不可撤销**：客户端超时 ≠ 请求取消，排队中的 SKILL 仍会执行 | **高** | 与三层架构 §5.8「无法判断是否已产生副作用时返回结果未知、不盲目重试」的精神冲突（该保护只覆盖了命令通道） | 同一 token 并发 ≥2，且先到的请求耗时超过后到请求的 timeout | 在投递前增加 **per-token skill 闸门**；投递后超时标记为 unknown-effect |

### 三个被隐式假定的前提

1. **「客户端超时 = 请求取消」** —— 对 skill 通道不成立（发现 1）。
2. **「`channel_budget` == 单连接上限 == 远端 MaxSessions」** —— 三个本应独立的数字，靠默认值巧合相等（发现 2）。
3. **「CPython 有 GIL + `_capacity` 的 key 永不删除 + registry 永不热更新」** —— 三个未写下来的前提同时成立时，发现 3 才无害。

### 本记录有意不涉及

按评审约定，以下三项不作为本文问题陈述：同 token 内路径冲突（由调用方自行保证）、长任务模式（调用方已采用 detached + 轮询）、`close()` 与在飞请求耦合（调用方已确认按轮询模式处理）。

## 二、背景口径：三道计数器

走查对象是并发准入路径。当前实现里共存在**三道计数器**，只有前两道与配置字段一一对应：

| | 计数器 | 位置 | 计量单位 | 作用域 | 容量来源 | 满了的行为 |
|---|---|---|---|---|---|---|
| Gate 1 | `BusinessServer._capacity[token]` | `src/transport/middle.py:363` | 在途请求数 | 每 token 一份 | `runtime.thread_pool_size`（默认 32） | `acquire(blocking=False)` → 立刻 `rejected` |
| Gate 2 | `RemoteClient._channel_sem` | `src/transport/tunnel.py:68` | channel 数 | 每 token 一份，跨所有 endpoint 共用 | `runtime.channel_budget`（默认 10） | `acquire(blocking=False)` → 立刻 `rejected` |
| Gate 3 | `ParamikoSessionBackend._session_gate` | `src/transport/paramiko_backend.py:275` | 单条 SSH 连接的 session 数 | 每个 endpoint 一份 | **`entry.runtime.channel_budget or 10`（`src/transport/tunnel.py:53`）** | `acquire(timeout=deadline)` → 阻塞 → `timeout` |

Gate 1 与 Gate 2 是两个独立维度（一个请求可以占用 0 个 channel（Skill）或 1 个 channel（文件 / 并行命令）），其数值也没有固定比例，因此必须各自成字段——这部分现状是正确的。

Gate 3 则不是：它是「单条 SSH 连接能开几条 channel」的本地护栏，物理约束来自**远端 sshd 的 `MaxSessions`（环境能力）**，却从**租户策略字段 `channel_budget`** 取值。发现 2 即由此而来。

**Skill 路径不占 Gate 2**（Spec §11.2 明确「Skill 执行：不占 channel 预算」），只占 Gate 1 的线程预算；而 Gate 1 是**快速拒绝**语义，不是排队闸门。因此 Skill 通道目前**没有任何投递前闸门**——这正是发现 1 的成因。
## 三、发现 1（P1）：skill 请求一旦投递即不可撤销

### 3.1 现象

同一 token 的两个 skill 请求并发发出，若先到的那个耗时超过后者的 timeout，**后者会向调用方返回超时错误，但它的 SKILL 稍后仍会被 daemon 执行**。调用方看到的失败与远端实际发生的事不一致。

### 3.2 机制

投递路径（`src/transport/middle.py:397-410`）：

```python
def execute_skill(self, skill_code, timeout=None, *, token):
    ...
    if not self._acquire(token, entry):          # Gate 1：快速拒绝，不是排队闸门
        return VirtuosoResult(status=ERROR, errors=["thread pool exceeded"])
    ...
    self._remote(token).ensure_tunnel(deadline=deadline)
    return self._skill(token).execute_skill(skill_code, timeout=remaining)   # 直接投递
```

`SkillClient._execute_once`（`src/transport/skill_client.py:92-110`）：

```python
s.connect((self.host, self.port))            # 连本地隧道端口
s.sendall(json.dumps(payload).encode())      # 请求字节发出
s.shutdown(socket.SHUT_WR)                   # ⇐ EOF 即帧边界
while True: ... s.recv(...)                  # 等结果
```

超时或异常时，`with socket.socket(...)` 关闭本地 socket；**但请求字节早已发出**，并且已经穿过隧道、进入远端 daemon 的内核接收队列：

- daemon 单线程 `accept` 循环（`src/bridge/resources/ramic_bridge_daemon_3.py:383`、`:404`），`listen(128)` 让内核在三次握手完成后就把连接排进 accept 积压队列（请求数据已在 socket 接收缓冲里）；
- `handle_connection`（同文件 `:260-281`）是 `while True: recv` 直到 **EOF** 才认为一帧完整，然后校验 token、写 CIW、阻塞等结果。

因此 **"排队"发生在内核的 accept 积压队列里，不在任何应用层队列**。客户端放弃时只是关闭了自己的 socket——在 daemon 看来，**"请求发完了"和"客户端已经跑了"是同一种状态**（帧边界就是 EOF），无法区分，协议里也没有 `request_id` / cancel 消息去撤销。

Spec 的对照：`spec/design-concepts/总览/三层整体架构设计.md:352` 以"daemon 同一时刻只有一个 in-flight 请求"论证本版不需要 `request_id`。这句在**执行**层面成立（CIW 一次只求值一个 SKILL，`spec/design-concepts/底层与中层/并发处理设计.md:26`），但在**投递**层面不成立——**"已投递、还在排队"的请求同样是一个不可撤销的副作用承诺**，而客户端对它既没有取消手段，也没有"可能已执行"的表达。

### 3.3 触发条件与后果

触发条件：同一 token 并发 ≥2，且先到的请求耗时 > 后到请求的 timeout（默认 30s，`src/transport/middle.py:30`）。

| # | 后果 | 说明 |
|---|---|---|
| A | **幽灵执行** | 调用方收到 `SKILL execution timed out`，但 SKILL 在稍后真实执行 |
| B | **重复执行** | 调用方若对 timeout 做朴素重试，同一 SKILL 会执行两次；Spec 明令"不盲目重试非幂等操作"，但这条路径让调用方无法区分 |
| C | **污染后续请求** | 迟到执行会修改 CIW 状态（当前 cellview、window、编辑栈），影响该 token 之后的所有请求 |
| D | **错误语义缺失** | `VirtuosoResult` 没有 `kind` 字段；命令通道有 `kind=unknown-effect`（`CommandResult`，Spec 三层架构 §5.8 表），skill 通道没有对应表达 |

### 3.4 已有的对照范式（说明修复成本低）

命令通道的默认（串行）路径**已经实现了正确语义**（`src/transport/tunnel.py:253-272`）：

```python
if not self._serial_lock.acquire(timeout=max(0.0, float(timeout))):
    return CommandResult(returncode=124, stdout="",
        stderr=f"command timed out waiting for the serial command slot after {timeout}s",
        kind="timeout")            # ⇐ 确定未投递，可安全重试
...                                 # 拿到名额才真正投递
```

即：**"投递前排队、拿不到名额就确定未投递"这个模式在项目里已经存在，skill 路径只是没有套用它。**

### 3.5 建议修复

1. 在 `BusinessServer.execute_skill`（`local` / `remote` 两个分支**之上**）或 `RemoteClient` 上增加 **per-token skill 投递闸门**：`threading.Lock()` 或 `BoundedSemaphore(1)`。
2. 闸门必须在 `ensure_tunnel` / `connect()` **之前**获取；用**剩余 deadline** 去 acquire（`timeout = deadline - now`），排队时间从端到端预算里扣，符合 Spec「一条 deadline 覆盖各相位」的纪律。
3. 拿不到 → 返回"投递前超时"，此时**确定零副作用、可安全重试**。
4. 必须在 `finally` 中释放，异常/超时都不能漏（否则该 token 永久卡死）。
5. **粒度必须 per-token，不能全局**——全局闸门会把 alice 和 bob 串起来，违背跨用户并行目标。
6. 投递**之后**才超时的，应表达为"结果未知 / 可能已执行"，禁止静默重试（对齐命令通道的 `unknown-effect` 语义）。
7. 可选加固：等待队列深度上限（例如每 token 最多 N 个在等，超出直接 `rejected`），避免线程无限 parked 在闸门上。
8. 若需要**严格 FIFO**，用 `collections.deque` + `Condition` 显式排队；`Lock` 只提供近似的先来先服务。

### 3.6 验证方法（最小实验）

**实验一（协议级，确定性强，推荐先做）**

使用已有的 fake daemon（`test/tb/fake_daemon_host.py`，可记录收到的请求并人为延迟响应）：

- 并发发出 A、B 两个 skill；A 让 fake daemon 延迟 10s 才回，B 的 `timeout=1`。
- 修复前预期：B 在约 1s 返回 timeout，但 fake daemon 在约 10s 后**仍然收到** B 的请求。
- 修复后预期：B 从未出现在 fake daemon 的请求记录中（它在投递前就超时放弃了）。

**实验二（真机 Virtuoso）**

- A = 耗时数秒的大循环 SKILL；B = `hiPrintToLogFile("VB-REVOKE-PROBE")`，B 的 `timeout=1`。
- 修复前预期：B 返回 timeout，但 A 完成后 `VB-REVOKE-PROBE` 出现在 CDS.log。
- 修复后预期：该 marker 永不出现。

## 四、发现 2（P2）：第三道闸门的来源错误

### 4.1 现象

"每条 SSH 连接最多几条 channel"这道闸门（Gate 3）没有独立的配置来源，直接等于租户的 `channel_budget`。

### 4.2 机制与证据

| 环节 | 位置 | 内容 |
|---|---|---|
| 容量来源 | `src/transport/tunnel.py:53` | `"max_sessions": entry.runtime.channel_budget or 10` |
| 建闸 | `src/transport/paramiko_backend.py:275` | `self._session_gate = threading.BoundedSemaphore(max_sessions)` |
| 获取 | `src/transport/paramiko_backend.py:967-976` | `acquire(timeout=deadline.remaining(command))`；等不到 → `TimeoutExpired` → `kind=timeout` |
| 配置模型 | `src/transport/registry.py:171-174` | `Runtime` 只有 `thread_pool_size` / `channel_budget` / `connect_timeout`，**没有 max_sessions 字段** |
| 默认值 | `src/transport/ssh.py:269-270` | `if max_sessions is None: max_sessions = 10` |
| 唯一消费者 | `src/transport/ssh.py:348` | 只传给 `ParamikoSessionBackend`；openssh 后端路径上 `_max_sessions` **没有任何消费者** |
| Spec 口径 | `spec/design-concepts/底层与中层/并发处理设计.md:505` | **"远端 MaxSessions 是环境能力，不是配置项"** |

即：Gate 3 的物理含义是"代理远端 sshd 的 `MaxSessions` 环境能力"，却被接到了"每 token channel 配额"这个租户策略字段上。两个数字今天都等于 10，纯属默认值巧合（registry 默认 10、`ssh.py` 兜底默认 10、sshd 出厂默认 10），没有任何代码保证它们一致。

### 4.3 后果

1. **调高 `channel_budget` 会顺带拆掉本地护栏**：把某用户从 10 调到 20，Gate 3 也变成 20，而远端 `MaxSessions` 仍是 10 → 第 11 条并发 channel 被**本地放行、远端拒绝**，错误从干净的 `rejected` 退化为远端 SSH 通道错误（`administratively prohibited` 一类）。
2. **无法表达"token 总量 N、每连接 M"**：3 个 endpoint 分布在不同机器时，无法单独限制弱机器的单连接并发——降低 `channel_budget` 会同时压低 token 总量。
3. **换 backend 即换并发语义**：openssh 后端没有 Gate 3，paramiko 后端有；同一份 registry 配置，行为不同。
4. **同一物理原因给出两种错误类型**：Gate 2 满 → `rejected`（快速失败、可重试）；Gate 3 满 → `timeout`（阻塞到 deadline）。Spec 的记账表把 channel 超限统一写成 `rejected`，内层不一致。

### 4.4 建议修复

| 方案 | 内容 | 优点 | 缺点 |
|---|---|---|---|
| **A（推荐）** | 新增独立字段，如 `runtime.max_channels_per_connection`（默认 10），并允许 per-role / per-endpoint 覆盖 | 语义清晰；可单独为弱机器限流；调 `channel_budget` 不再破坏护栏 | 需要改配置模型 + 注册页/文档 |
| **B（最小改动）** | Gate 3 退化为常量 10，并注明"对远端 MaxSessions 的本地保守代理，不是租户策略，不跟随 channel_budget" | 改动一行；立刻消除耦合 | 不可按环境调整 |
| **C（坚持单字段）** | 显式写 `min(channel_budget, 10)` 并在文档写死"单连接上限恒为 10" | 不改配置模型 | 用户把配额调高却看不到效果，易误判为配置未生效 |

无论选择哪种，都建议在 `src/transport/tunnel.py:53` 处留注释说明该值的语义来源（环境代理 vs 租户策略）。

### 4.5 验证方法

- **单测**：构造 `RemoteClient`（mock 掉 `SSHRunner`），断言 `channel_budget=20`、`max_channels_per_connection=2` 时，Gate 2 容量为 20、Gate 3 容量为 2，且互不影响。
- **集成**：测试 sshd 设置 `MaxSessions 2`，把 `channel_budget` 设为 20。修复前：第 3 条并发 channel 得到远端错误；修复后：Gate 3 = 2，得到本地 `timeout`，错误类型与 Spec 一致。
## 五、发现 3（P3）：`_capacity` 字典的线程安全与容量快照

### 5.1 现象：创建加锁、释放不加锁

```python
# src/transport/middle.py:363-371  创建路径
def _acquire(self, token, entry=None) -> bool:
    if entry is None:
        entry = self._entry(token)
    with self._lock:                                   # ← 加锁
        sem = self._capacity.get(token)
        if sem is None:
            sem = threading.BoundedSemaphore(entry.runtime.thread_pool_size)
            self._capacity[token] = sem
    return sem.acquire(blocking=False)

# src/transport/middle.py:373-376  释放路径
def _release(self, token) -> None:
    sem = self._capacity.get(token)                    # ← 不加锁
    if sem is not None:
        sem.release()
```

`self._capacity` 是**所有请求线程共享**的可变字典（`middle.py:289`，一个 `BusinessServer` 一份）。共享可变状态的一般规则是：要么读写都在同一把锁下，要么能证明不需要锁。这里创建路径加锁、释放路径不加，属于"没有证明，但碰巧安全"。

补充：`_capacity` 还有第二个创建点 `_remote()`（`middle.py:325-338`，用 `setdefault`），它同样在 `with self._lock` 内——所以**唯一无锁的是释放路径**。

### 5.2 今天为什么无害（三个隐式前提同时成立）

1. CPython 有 GIL，`dict.get` / `dict.__setitem__` 单次操作是原子的，不会读到结构损坏的字典；
2. `_capacity` 里的 key **从不被删除或替换**：只有 `_acquire` / `_remote` 插入新 token；`close()`（`middle.py:296-311`）只清 `_clients` 与 `_local_sessions`，不碰 `_capacity`；
3. `_release` 只在 `acquired == True` 之后调用（各接口均为 `finally: if acquired: self._release(token)`），所以 key 必然存在。

三条同时成立时，`_release` 拿到的永远是自己曾 acquire 过的那个 semaphore 对象。

### 5.3 什么情况下会咬人

一旦有人给 `_capacity` 加上"删除 / 替换"逻辑（用户被删除、配额热更新、token 轮换），或引入 registry 热重载：

- `_release` 可能拿到**另一个** semaphore 去 release → 对从未 acquire 过的对象 release，`BoundedSemaphore` 抛 `ValueError: Semaphore released too many times`；
- 或者旧对象的计数永远回不来，该 token 的配额被**永久泄漏**一个名额。

作者其实已经意识到这个危险，并在代码里留了注释（`middle.py:333`）：*"Never replace a semaphore that `_acquire()` may already hold."*——但释放路径仍然无锁，两者不一致。

另外，这段安全的依据是"CPython 有 GIL"这个**实现细节**（no-GIL 构建下不成立），而不是代码契约。

### 5.4 关联发现：`_capacity` 是"首次使用时的一次性快照"

```python
sem = threading.BoundedSemaphore(entry.runtime.thread_pool_size)   # ← 建它那一刻的数字
```

semaphore 的容量是**创建那一刻**从 entry 读来的，之后没有任何代码会重建它。同样的问题覆盖整个 `RemoteClient`：

| 冻结对象 | 冻结的配置 | 后果 |
|---|---|---|
| `_capacity[token]` | `thread_pool_size` | 改配额不生效 |
| `RemoteClient._channel_sem` | `channel_budget` | 同上 |
| `_runner_kwargs["max_sessions"]` | `channel_budget` | Gate 3 容量不变 |
| `_runner_kwargs["connect_timeout" / "backend" / "control_master"]` | SSH 配置 | 换后端 / 改超时不生效 |
| `_runners` 里的 transport / 隧道 | host / user / jump / proxy | 换机器不会重连 |

它们全部在 `RemoteClient.__init__` 时建好，缓存进 `BusinessServer._clients[token]`，**永不失效**。

**今天为什么看不出来**：`Registry.load()` 是一次性读入（`src/transport/registry.py:211-226`：首次读文件后置 `_loaded=True`，之后再调是 no-op），**进程内没有热更新路径**；`_clients` 也没有失效机制（只有 `close()` 清空）。所以"配置值"与"计数器容量"在同一进程生命周期内不可能分叉。

**为什么不能简单替换 semaphore**：若 alice 有 5 个请求正握着旧 semaphore 的 5 个名额，执行 `_capacity[alice] = BoundedSemaphore(4)` 之后，那 5 个请求稍后 `release()` 释放的是**新对象** → 新对象从未被 acquire → `ValueError` 且名额被错误增加；旧对象的 5 个名额永久泄漏。这正是 `middle.py:333` 注释警告的情形。

**正确做法（三选一）**：

1. **动态限额（推荐）**：改为"整数计数 + `threading.Condition`"，`_acquire` 时读**当前**限额；调参立即生效，不需替换对象；在飞数大于新限额时，语义自然表现为"不再放行新的，等旧的跑完"。
2. **排空后替换**：给 token 打 drain 标记 → 停止放行新请求 → 等在飞归零 → 关旧 client / 建新 client / 建新 semaphore。
3. **明确不支持热更新**：把 registry 定义为启动时配置（现状），变更走重启，并在文档与接口中写死该约束，避免留一个"看起来能改、实际不生效"的 update 路径。

### 5.5 建议修复（锁问题）

最小且最稳的改法是让 `_acquire` **直接返回 semaphore 对象**，调用方持有它、`finally` 释放同一对象，释放路径根本不碰字典：

```python
sem = self._acquire(token, entry)        # 返回 semaphore 或 None
...
finally:
    if sem is not None:
        sem.release()                    # 释放的就是自己拿到的那一个
```

若不想改签名，至少把 `_release` 中的 `get` 放进 `with self._lock`。

### 5.6 验证方法

- **单测（配额泄漏）**：`_acquire` 成功后人为 `_capacity.pop(token)`（模拟删除或替换），再调用 `_release`。修复前：该 semaphore 计数泄漏、后续 acquire 失败；修复后：释放的是持有的对象，计数正确。
- **单测（快照）**：首次调用后修改 `entry.runtime.thread_pool_size`，断言容量不变——把这个"已知行为"固化下来，明确它是设计还是缺陷。
- **静态检查项**：所有共享字典（`_clients` / `_skill_clients` / `_capacity` / `_local_locks` / `_local_sessions`）的读写都在 `self._lock` 下。
## 六、修复方案汇总

| # | 优先级 | 改动点 | 影响面 | 预估工作量 | 依赖 / 前置 |
|---|---|---|---|---|---|
| 1 | **P1** | `BusinessServer.execute_skill`（或 `RemoteClient`）加 per-token skill 投递闸门；投递后超时标注 unknown-effect | 中层；skill 排队位置从内核 backlog 移到应用层 | 小（约 50 行 + 单测） | 需先决定闸门 size（1 或 N）与超时表达方式 |
| 2 | **P2** | Gate 3 容量独立：新增 `max_channels_per_connection` 字段，或退化为常量 10 | 配置模型、注册页、文档、paramiko 路径 | 小～中 | 需决定是否 per-role / per-endpoint 可配 |
| 3a | **P3** | `_acquire` 返回 semaphore 对象，调用方持有并释放 | 中层内部重构 | 极小 | 无 |
| 3b | **P3** | `_capacity` 动态限额，或 drain-then-swap，或明确写死"不支持热更新" | 中层 / registry / 部署文档 | 中 | 取决于是否要支持热更新与多 worker |

建议顺序：**3a（顺手改，零风险）→ 1（正确性，最高优先）→ 2（配置语义）→ 3b（取决于部署形态决策）**。

## 七、待确认问题

1. skill 闸门 size 取 **1**（严格单发，最贴合 CIW 串行语义）还是 **N**（允许 N 个在飞，但仍在 daemon 排队）？
2. 是否需要**严格 FIFO**？若是，`Lock` 不够（只是近似公平），需要 `deque` + `Condition`。
3. 投递后超时如何表达？`VirtuosoResult` 目前没有 `kind` 字段（对比 `CommandResult.kind`），是加字段还是用 `warnings` / `metadata` 约定？
4. 是否引入 `request_id`？Spec 明确本版不引入（`spec/design-concepts/总览/add-本版范围与明确不支持.md:22`、`spec/design-concepts/总览/三层整体架构设计.md:352`），因此**投递后去重**在本版做不到，只能做投递前取消。
5. Gate 3 是否需要 per-endpoint 可配？（不同远端 sshd 的 MaxSessions 可能不同）
6. 业务服务是否会做热更新 / 多 worker？（决定 3b 的优先级；多 worker 还会让 per-token 计数器在进程间各算一份，需要另外的准入方案。）
