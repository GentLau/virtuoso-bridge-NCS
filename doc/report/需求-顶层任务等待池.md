# 已否决：顶层任务等待池

> 日期：2026-09-20
> 状态：**已否决**，不再作为需求提交给顶层 spec owner
> 结论：不新增等待池；长任务用普通的"启动 + 查询"操作实现，顶层零改动
> 保留原因：本文件记录被否决的构想与否决理由，避免后续重复提出

## 1. 否决结论

原构想是：顶层提供"任务等待池"，上层把"还没完、请继续问"登记进去，由顶层后台轮询；调用方可选阻塞等结果或立刻拿句柄。

**结论：不做。** 阻塞和非阻塞两种需求都能用普通同步操作满足，不需要顶层保存任何状态。

## 2. 否决理由

### 2.1 阻塞模式下不需要池

阻塞就是"包内循环到完成再返回"，一个普通操作即可。池在这条路上完全是多余的。

### 2.2 非阻塞模式下池只是挪动循环，不减少任何交互

非阻塞的本质就是"起一次 → 隔一会儿问一次"，两个普通操作就能做到。池把这个循环从调用方挪到服务端，调用方**仍然要轮询**，只是从"轮询仿真状态"变成"轮询池子"——交互次数一次没少，还多绕了一层。

### 2.3 池不会带来更多进度信息

进度只能来自目标侧（`axlGetRunStatus` 的完成点数/测试数、marker 文件）。直接问，粒度更细；经过池，只能拿到池缓存下来的那一份快照，反而更粗。

### 2.4 代价是实打实的

| 代价 | 说明 |
|---|---|
| 顶层变成有状态 | 与顶层 spec 现行"不保存状态、不做业务"冲突，需要新增章节，扩大顶层职责 |
| 重启即丢 | 任务表是内存态，进程重启后在途任务全部丢失，还要在 spec 里写明不承诺恢复 |
| 持续消耗中层预算 | 每次轮询都是一次真实的中层调用，占用该 token 的线程/通道预算；长任务高频轮询会挤占正常业务，需要额外的上限与退避策略来兜底 |
| 第二套真相风险 | 池里的状态若与目标侧事实不一致，会出现"池说在跑、其实早跑完" |

### 2.5 推送这条路走不通

池的价值之一被设想为"完成后通知调用方"。但 agent 是 HTTP 客户端，没有稳定的回调入口，服务端无法主动推送。现实选项只有长轮询（等价于阻塞模式）或调用方轮询（就是普通查询）。推送这条价值不存在。

## 3. 替代方案（采纳）

三个普通同步操作，全部不需要顶层改动：

| 操作 | 形态 |
|---|---|
| `run` | 启动仿真，立刻返回 history 名 |
| `run_status`（或并入 `read_history`） | 无状态查询：running / done / failed + 进度 |
| `run_and_wait`（可选便利封装） | 包内循环 `run_status`，调用方感受为阻塞 |

阻塞还是非阻塞由调用方选择调哪个操作决定，服务端不记住任何东西。同形态适用于后续 GDS 导入、Verilog 导入、Spectre 批量等长任务。

## 4. 什么情况下值得重新考虑

只有一种场景值得重新提：**无人值守的自动收集**——起一个十几小时的仿真，人离开，希望服务端在完成那一刻自动把结果收好、清理临时文件和会话，下次连上来直接能看到。

那是"自动收集 + 可见性"需求，不是"轮询"需求；真要提，需求描述应该围绕"完成后自动做什么"，而不是"提供轮询池"。

## 5. 遗留待验证项

替代方案里有一个实现细节需要在真机上确认：`run_status` 判断"跑完了"的可靠来源——

- 回调 marker（精确，但要求 marker 文件在工作角色之间可见）；
- 或 `axlGetRunStatus`（不依赖 marker，但需要与期望的点/测试总数对上）。

这一项随 maestro 的 `run` / `run_status` 定稿时一起验证。

## 6. 原始构想存档（被否决的设计，仅备查）

- 上层不调用顶层接口，只在 Result 里带 `pending`：`{job_id, follow_up:{operation,payload}, poll_interval, deadline}`；
- follow_up 返回值约定三态：`running` / `done` / `failed`；
- 顶层登记任务、后台按节拍驱动 follow_up，调用方可选阻塞等结果或拿句柄后查询；
- 有界（每 token + 全局上限）、节拍退避、内存态不恢复。

以上均**不再实施**。
