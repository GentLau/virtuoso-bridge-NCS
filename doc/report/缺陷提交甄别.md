## 二、驳回理由详述

### B7（GUI 跨用户可见）：不是 bridge 的隔离缺陷

- 《路由设计》§1"忠实投送原则"：bridge 只按用户给定目标投送，不判断 role 之间是否同机、同账号、共享路径/display；
- 《多用户与注册》§1：token 只防 Skill 通道误连，不承担 SSH 认证；隔离依赖 OS 账号权限；
- 两个用户都把 `gui` role 指向同一台机器的同一个 `DISPLAY=:99`，在该 display 上就是互相可见——这是站点拓扑（"用户拓扑责任"），不是 bridge 越权；
- 若站点要求隔离：每用户独立 X display / 独立账号，或由上层业务包增加"只操作自己的窗口"过滤（属 10-gui 口径）。

### B9（banner=null 无 warning）：spec 未定义的行为

- 《多用户与注册》§3.2 只定义 `banner hostname / daemon user 与 expected_* 不一致 → WARNING`；
- identity 文件缺失/读不到属于站点侧事实；注册第五步已实际连通（skill 冒烟通过）才可能走到这里；
- 需要"取不到 banner 也提示"的话，应在 spec 增加一句，再实现（属可选项，不阻断）。

### B17 与 B19 的上层部分

- B17：`basic.Result.error` 由业务包生成；应为非零 `returncode` 且 stderr 为空时补

- B19：`basic.CommandRequest.parallel` 在包入口被 `bool(request.parallel)` 转换；
  应在 Request 构造阶段用 `StrictBool` 拒绝字符串。`transport` 只接收已经为 bool
  的参数，无法反推 `"no"` 的原始类型。

## 六、Subagent 审查后的收敛与剩余 spec 议题

本轮由 3 个只读 subagent 分别审查代码最小改动/重复/死代码、TB 可信度、
分层与 spec 一致性。已处理：

- **B15 TB 假绿修复**：原测试先创建子进程再 assign，且 `OpenProcess` 权限写错，
  可能在进程仍存活时误报死亡；现在改为“先 assign、再派生后代”，使用
  `PROCESS_QUERY_LIMITED_INFORMATION`，并增加关闭前 child 必须存活的断言；
  另有 `BusinessProcess` 真实后代 shutdown 回收测试；
- **Job Object 降级路径**：assign 失败会在 Windows 记录 warning，并在强制清理时
  使用 `taskkill /PID <pid> /T /F`；业务子进程自行退出时关闭 job，避免后代
  留到下一次 restart；
- **B19 严格类型补齐**：`common/registry.py` 的 `RoleConfig`/`DaemonRoleConfig`/
  `Runtime`/`CdsLog` 也改为 `StrictInt`/`StrictFloat`，update/load/手写注册表
  的字符串数值均拒绝；`connect_timeout` 同时拒绝 inf/NaN；
- **B18 keep-alive 回归**：405 统一带 `Allow` 和 `Connection: close`，业务面
  不再因未消费 405 请求体导致同一连接下一请求解析错位；补 CONNECT 和 header TB；
- **B13 显式整数上限**：`loads_strict` 增加 `parse_int` 位数上限，不再依赖
  CPython 的 `int_max_str_digits` 全局开关；关闭解释器保护后 TB 仍要求 400；
- **B8 凭据剥离补强**：改为 JSON 感知的全局 key 正则替换，覆盖嵌套字段和转义
  字符串；补 nested/escaped credential TB；
- **死代码清理**：删除 `ProcessJob.terminate()`/上下文管理器/未用 ctypes 绑定，
  简化重复异常捕获和未使用 import；NUL 两层校验保留为 defense-in-depth。

剩余需要 spec owner 裁决的事项：

1. **顶层导入白名单**：`server/api_server.py` 现在导入 `common.jsonutil`，但
   《顶层 §1》白名单只列了标准库、`common.paths`、`server.*`、`pyapi.*`；
   建议把 `common.jsonutil` 或“允许使用的 common 工具”补入 spec，不建议在两个
   HTTP 面复制严格 JSON 解析器。
2. **timeout 上限语义**：`2_147_483s` 是 Windows socket 定时器的实现安全边界，
   spec 目前只定义默认 30s，没有定义最大值；建议在总览 §5.8 明确“正有限数、
   超平台上限结构化 4xx 拒绝”。
3. **B20 body limit/413/配额**：见 §四，仍未实现，等待 spec 先定策略。
4. **B15 POSIX 强杀边界**：Windows 强杀/重启已真机闭环；POSIX 下 `ProcessJob`
   是 no-op，且隧道使用 `start_new_session=True`，supervisor 被 `kill -9` 时
   仍可能留下 SSH 后代。若本版要求 POSIX 同等级保证，需要另定实现
   （PDEATHSIG/进程组回收）；否则建议在 spec/report 明确“本版 Windows 保证”。
5. **未知 HTTP 动词**：已知动词已统一 405 JSON；`PROPFIND`/`FOO` 等未知动词
   仍走 BaseHTTPRequestHandler 的 501。若 B18 的“所有不支持方法”包含未知动词，
   需要在 spec 里明确统一口径。
