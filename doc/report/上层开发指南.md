# 上层开发指南

> 版本：v1（2026-09-16） — **已被 spec 取代**：本文升格为 Normative 后拆为 [顶层：HTTP 入口与业务调度](../../spec/design-concepts/顶层/1-顶层.md) 与 [上层：业务包与插件化](../../spec/design-concepts/上层/1-上层.md)；本文只保留为背景说明，与 spec 冲突时以 spec 为准。
> 适用范围：`src/pyapi` 上层业务包，以及未来 `src/server` 中的业务 HTTP 层
> 依据：`spec/design-concepts/总览/1-四层整体架构与接口.md`、`spec/design-concepts/中层/3-路由设计.md`
> 定位：本文只给开发约定，不重新定义 Normative 接口；与 spec 冲突时以 spec 为准。

## 1. 上层边界

上层只做三件事：

1. 接收业务参数并校验业务语义；
2. 把一个业务动作拆成若干步骤；
3. 只通过中层五接口完成每一步。

上层不接触：

- SSH、Paramiko、socket、subprocess、端口、隧道；
- registry 文件、token 路由、daemon 协议；
- Virtuoso CIW 的 socket 或 `ipcBeginProcess`；
- `csh()`、`system()` 伪装成的 Skill 调用。

上层看到的逻辑执行环境只有一个“业务服务器”。

## 2. 五接口是唯一底座

业务包只依赖 `pyapi.models.Middle`：

```python
middle.execute_skill(skill_code, timeout=None, *, token)
middle.run_command(cmd, timeout=None, *, token, parallel=False)
middle.upload_file(local_path, remote_path, timeout=None, *, token, recursive=False)
middle.download_file(remote_path, local_path, timeout=None, *, token, recursive=False)
middle.run_gui_command(cmd, timeout=None, *, token)
middle.run_spectre_command(cmd, timeout=None, *, token)
```

约定：

- `token` 是每次调用的参数，业务包不得把它缓存成“当前用户”；
- `parallel` 和 `recursive` 是可选参数，不是新接口；
- 业务包不根据本地/远端模式写不同代码；模式差异由中层隐藏；
- 长任务由上层用 marker、轮询、文件检查等方式编排，不把中间层改成异步任务系统。

## 3. 业务包推荐形态

每个业务包建议包含：

```text
Request/Result 数据模型
Package 类
package.run(request) -> Result
```

`Package` 通过构造函数接收 `Middle`，不自己创建连接：

```python
from dataclasses import dataclass
from pathlib import Path

from pyapi.models import Middle


@dataclass(frozen=True)
class BuildAndRunRequest:
    token: str
    local_input: Path
    remote_input: str
    remote_output: str
    timeout: float | None = None


@dataclass(frozen=True)
class BuildAndRunResult:
    ok: bool
    steps: list[dict]
    error: str | None = None


class BuildAndRunPackage:
    def __init__(self, middle: Middle) -> None:
        self.middle = middle

    def run(self, request: BuildAndRunRequest) -> BuildAndRunResult:
        steps: list[dict] = []

        up = self.middle.upload_file(
            request.local_input,
            request.remote_input,
            timeout=request.timeout,
            token=request.token,
        )
        steps.append({"step": "upload", "result": up})
        if up.returncode != 0:
            return BuildAndRunResult(False, steps, up.stderr or "upload failed")

        skill = self.middle.execute_skill(
            'sprintf(nil "loaded:%s" "ok")',
            timeout=request.timeout,
            token=request.token,
        )
        steps.append({"step": "skill", "result": skill})
        if not skill.ok:
            return BuildAndRunResult(False, steps, "; ".join(skill.errors))

        cmd = self.middle.run_command(
            "echo build-ok",
            timeout=request.timeout,
            token=request.token,
        )
        steps.append({"step": "command", "result": cmd})
        if cmd.returncode != 0:
            return BuildAndRunResult(False, steps, cmd.stderr or "command failed")

        down = self.middle.download_file(
            request.remote_output,
            request.local_input.with_suffix(".out"),
            timeout=request.timeout,
            token=request.token,
        )
        steps.append({"step": "download", "result": down})
        if down.returncode != 0:
            return BuildAndRunResult(False, steps, down.stderr or "download failed")

        return BuildAndRunResult(True, steps)
```

## 4. Server 如何调用业务包

顶层与上层之间不设死接口。推荐 Server 只做“薄调度”，不要直接堆业务步骤：

```text
HTTP 请求
  -> 校验基本请求体 / token 存在
  -> 选择业务包
  -> 构造 Request
  -> Package(middle).run(request)
  -> 序列化 Result
```

推荐的路由表形态：

```python
from dataclasses import asdict

from pyapi.packages.file_skill_command_file import (
    FileSkillCommandFilePackage,
)


# 实际项目中建议为每个业务包同时登记 Request 模型。
PACKAGES = {
    "file_skill_command_file": (
        FileSkillCommandFilePackage,
        None,  # 替换为该包自己的 Request 类
    ),
}


class BusinessApp:
    def __init__(self, middle):
        self.middle = middle

    def invoke(self, operation: str, payload: dict) -> dict:
        spec = PACKAGES.get(operation)
        if spec is None:
            return {"ok": False, "error": f"unknown operation: {operation}"}
        package_cls, request_cls = spec
        try:
            request = request_cls(**payload) if request_cls else payload
            package = package_cls(self.middle)
            result = package.run(request)
            return {"ok": result.ok, "data": asdict(result)}
        except (TypeError, ValueError) as exc:
            return {"ok": False, "error": f"invalid request: {exc}"}
```

Server 规则：

- 每个 HTTP 请求走独立任务线程；Server 不自己维护业务级全局锁；
- token 每个请求从请求体取，不在 Server 进程中建立“当前用户”；
- Server 不做 SSH/隧道/daemon 状态判断；
- 业务包返回结构化结果；传输异常应由中层封装成 `CommandResult` / `VirtuosoResult`；
- 参数编程错误允许直接抛出 `TypeError/ValueError`，Server 统一转成 HTTP 400；
- 运行期失败应作为结构化 `ok=false` 返回，不把底层异常文本直接变成 500；
- 不要绕过业务包，直接调用 middle 五接口完成一整套业务步骤。

## 5. 业务包内部实现规则

### 5.1 先校验再执行

- 校验 token 是否为空、路径类型、必填参数、数值范围；
- 在调用五接口前，不进行任何本地或远端副作用；
- 业务包内部不要重新解释 SSH、daemon 或端口。

### 5.2 用统一 deadline

如果业务动作包含多个步骤，建议由业务包建立自己的端到端 deadline：

```python
import time

deadline = time.monotonic() + (request.timeout or 30.0)

def remaining():
    left = deadline - time.monotonic()
    if left <= 0:
        raise TimeoutError("business operation deadline exhausted")
    return left
```

然后把剩余时间传给每个中层接口。不要把同一段完整 timeout 在每一步重新开始。

### 5.3 错误必须保留 `kind`

```python
if cmd.kind == "rejected":
    # 只对幂等步骤按业务策略重试
elif cmd.kind in {"timeout", "transport", "path", "unknown-effect", "checksum"}:
    # 立即停止，交给上层或 Server 决定如何报告
```

规则：

- `kind=rejected` 可重试，但要设置次数和业务幂等条件；
- `kind=unknown-effect` 不得自动重发；
- Skill 超时不得自动重试；
- 文件校验失败不要忽略 `checksum`；
- 业务包必须向上层保留失败步骤，不能把失败伪装成成功。

### 5.4 路径只做业务命名

- `Path` 是调用方本地路径；
- `remote_path` 是业务服务器路径；
- 相对 remote path 由中层按目标 role root 解析，业务包不要自己拼 SSH 家目录；
- 不要把 token 放进文件名或目录名；用户可见路径使用 user id。

### 5.5 日志只做消费

`VirtuosoResult.log` 已经是中层返回的过滤、限长增量；业务包不应把它当完整日志。

需要完整日志时：

1. 获取 CDS.log 的远端路径；
2. 通过 `download_file()` 或文件接口读取；
3. 不要把完整日志重新塞进 Skill 返回值。

### 5.6 并发必须显式、独立

- 只有彼此独立的命令才使用 `parallel=True`；
- 业务包可以使用线程池，但必须面对 `kind=rejected`，不能无限重试；
- 同一 token 的 Skill 和默认命令本身有串行语义，不要绕过中层队列；
- 并发不是新接口，只是五接口上的调用方式。

## 6. 参考实现

当前仓库已有两个最小业务包：

- `src/pyapi/packages/file_skill_command_file.py`
  - 上传 → Skill → 命令 → 下载；
  - 任一步失败立即停止并保留步骤证据；

- `src/pyapi/packages/parallel_probe.py`
  - 并行命令/上传探测；
  - 收集每项结果和错误。

新业务包应从这两个包复制结构，而不是从 `transport` 中导入实现细节。

## 7. 新业务包检查清单

- [ ] 只 import `pyapi.models` 和本包自己的模型；
- [ ] 没有 import `transport.*`、`socket`、`subprocess`、`paramiko`；
- [ ] 所有中间操作都带 `token`；
- [ ] 所有必要步骤都有 timeout/deadline；
- [ ] 失败时返回步骤痕迹，不静默继续；
- [ ] `rejected` 只按幂等策略重试；
- [ ] Skill 超时、unknown-effect 不自动重试；
- [ ] 不把 token 当作文件路径；
- [ ] 不假设 local/remote 的具体实现；
- [ ] Server 只负责调度、序列化、错误边界，不复制业务步骤。
