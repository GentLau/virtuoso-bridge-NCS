# 反思与缺陷记录（2026-09-15 进程风暴事件）

> 触发事件：2026-09-15 在 Windows 客户端跑 100 用户级极端压测（`test/tb/p2_extreme_gradient.py`）时，
> 用户机器出现**数百个控制台窗口**，`ssh.exe` 峰值 **800 个**（其中 726 个由 python 进程/孤儿产生），
> 系统接近不可用。本文记录事件、根因、已修复缺陷、改进措施与待办。

## 1. 事件时间线

| 时间 | 现象 | 处理 |
|---|---|---|
| 压测开始 | `p2_extreme_gradient` 在 vps 拉起 100 个 fake daemon，随后 100 用户 × 400/500/600 并发 | 启动（错误决定：在弱 vps + Windows 客户端上做） |
| 运行中 | Windows 弹出大量 `ssh.EXE` 控制台窗口，用户报告"可能一百多个" | 我先解释为"每个 spawn 一个窗口"，未立即停 |
| 峰值 | `ssh.exe` 800 个，其中 726 由 python/孤儿产生；`conhost/OpenConsole` 460 个 | 停止全部本机 python 与 ssh，杀 vps fake daemon 与 wsl TB 进程 |
| 清理 | 本机 `python: 0`、`ssh: 1`（用户自有）；孤儿控制台宿主清掉 151 个（余 13 个属活跃控制台） | 环境恢复 |

## 2. 根因（两个真实缺陷 + 三个工程问题）

### BUG-1（严重）隧道"复用外部监听"分支不记录端口 → 每个请求重开隧道
- 代码：`SSHRunner._start_port_forward_locked()` 在检测到本地端口已有监听时，只置 `_tunnel_using_external=True` 就 `return None`；**没有记录端口**，也没设置 pid。
- 后果：`is_tunnel_alive` 只认 `_tunnel_proc` 或 `_tunnel_pid` → 永远 `False` → 下一个请求再次进入 `ensure_tunnel` → 再次 spawn `ssh -N -L`；因端口已被占用（`ExitOnForwardFailure`）立即失败，而 `start_port_forward` 自身还会**重试 3 次**，每次在 Windows 上最多等 10s。**每个请求最多 3 个注定失败的 ssh 进程**。
- 影响：进程数随请求数线性膨胀 —— 这是 100 条隧道变成数百进程的**主因**。
- 修复：记录 `_tunnel_local_port`；`is_tunnel_alive` 对"外部复用"分支改为**按端口可达性判定**；失败引入**指数退避**（`2^n` 秒，上限 30s，成功清零），退避期内直接快速失败不再 spawn。
- 回归：`test/unit/test_ssh.py` / `test/unit/test_tunnel.py` 全绿（49 项）。

### BUG-2（严重）runner 创建是 check-then-act 竞态 → 每个并发线程各建一条连接
- 代码：`RemoteClient._runner()` / `_one_shot_runner()` 先 `dict.get` 再构造再写回，**无锁**。
- 后果：同一 token 的首次并发调用（线程池默认 32）会创建**每线程一个 SSHRunner** → 每个 runner 自带 paramiko transport / 常驻 shell / 隧道 → 单用户即可产生几十个进程。
- 证据：新增回归 `test/unit/test_runner_single_flight.py`，16 线程并发调用 → 修复前 `16 != 1`（实例数 16），修复后为 1。
- 修复：双检锁（`_runner_lock`）保护两个字典的创建路径。
- 备注：**该竞态在重构前的旧实现中同样存在**（`src_bak/virtuoso_bridge/transport/tunnel.py:234-268` 的 `_role_runners` 也是无锁 check-then-act），属继承缺陷，本次一并修掉。

### ENG-1 压测放错机器（流程问题）
- vps 只有 2 核，且在设计里定位是"**弱目标**"（用来验证拒绝语义），不是压测靶机；100 用户 × 高并发把它拖垮，进一步触发 BUG-1 的重建风暴。
- 规则（已写入测试计划）：**压测从强客户端（glis/wsl-gent）发起；vps 并发上限 ≤40；禁止在 Windows 客户端跑 100+ 用户级压测**。需要极端拒绝证据时用"少用户 × 高并发"或直接压 HTTP 层。

### ENG-2 Windows 控制台未隐藏（测试代码）
- 桥自身 spawn 均带 `CREATE_NO_WINDOW`（隧道为 `DETACHED_PROCESS|CREATE_NO_WINDOW`，`ssh -G` 与 tar/scp 亦然），但 `test/tb/*.py` 里为了准备环境直接 `subprocess.Popen(["ssh", ...])`，没有隐藏 → 每个都弹窗。
- 改进：新增 `test/tb/_win.py::no_window()`，TB 统一使用；`probe.py` 的 `ssh -G` 也已补上隐藏参数（此前注册探测路径会弹窗）。

### ENG-3 环境判读与“先停再查”
- 事件中我先把弹窗解释为"正常现象"，没有第一时间止损；且此前出现过一次"把环境死亡（Virtuoso 全部退出）误判为 paramiko 缺陷"。
- 规则：出现**资源类异常**（进程数、端口数、CPU/内存）先止损（停压测、留现场），再定位；每轮前必须做环境健康检查（`pgrep -c virtuoso`、`ss -tln | grep 651`），每轮后做**客户端侧资源盘点**（见下）。
