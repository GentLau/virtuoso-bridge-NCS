# 控制台三页：后端接口与权限缺口

> 日期：2026-09-30  
> 范围：注册、个人配置管理、管理员系统管理三页对控制面 API 的真实依赖  
> 结论：注册页和管理员系统页不需要后端额外改接口；**个人页“个人 token +
> enhanced_token 自助查询/修改自己的注册表条目”在当前 server 中尚未实现。**

## 1. 三页职责

| 页面 | 前端职责 | 当前后端入口 |
|---|---|---|
| 新用户注册 | 六步申请、校验、探测、部署、连通性、提交写入 | `POST /api/register`、`GET /api/register/<user>` |
| 个人管理 | 查询自己的条目；修改个人连接、角色根、个人策略、用户组；diff 后保存；删除自己的条目 | 目标入口应为“个人身份 + 增强凭据”；当前实际只能走管理端点 |
| 管理员管理 | 全局业务线程池、业务进程 status/reload/restart；注册表只读概览 | `GET/PUT /api/config`、`GET /api/process/status`、`POST /api/process/reload|restart`、`GET /api/users` |

个人页和管理员页已经做成独立工作区，不能再用同一个“用户管理”入口混着操作：

- 个人页只处理一个 user 自己的 registry 条目；
- 管理员页只处理 `config.json` 和业务进程，不逐项编辑个人连接参数。

## 2. 注册页：没有阻断性缺口

当前注册页已经能使用已有的结构化信息：

```text
probe_results[]           逐 role 的 ok/warning/error/not_run
report.fingerprint_ok     第 5 步 SSH 指纹结果
entry.roles.<role>.*      root / display / bin / 用户组
```

role 到业务通道的映射固定为：

```text
daemon  -> Skill
command -> Command
file    -> File
gui     -> GUI
spectre -> Spectre
```

`query` 是只读伴随接口，不是第六条通道。前端不会把 endpoint 作为用户可见的第六项。

对应实现与契约：

```text
src/register/models.py
src/register/flow.py
src/register/server.py
test/offline/unit/test_registration_probe_status.py
test/offline/unit/test_registration_page.py
```

## 3. 个人页：当前后端存在权限/端点缺口

### 3.1 规范当前写的是“收归管理员”

`spec/design-concepts/顶层/add-控制面与业务面.md` 当前明确写：

```text
GET    /api/users            管理权限
GET    /api/user/<user>      管理权限
POST   /api/user/<user>/update  管理权限
DELETE /api/user/<user>      管理权限
```

同文件还写明：

```text
修改类（update/delete）路径以 user 定位，收归管理员；
个人 token 不能自助修改。
```

代码也按这个口径实现：

```text
src/register/server.py:232-285
    查询、更新、删除入口先调用 _require_admin()

src/register/server.py:361-390
    enhanced_token 只在 POST /api/register 的 apply 中校验

src/register/server.py:723-802
    /api/user/<user>/update 只接受管理端白名单 patch
```

需要明确：**这不是“实现偷偷偏离了一份已经定义个人自助权限的 spec”**。当前
v40 控制面 spec 本身就把 update/delete/query 全部收归管理员，所以实现与这份 spec
是一致的；缺口在于这份 spec 没有定义“个人 token + enhanced_token 自助修改自己”的
权限模型。若目标产品语义是个人自助，则必须同时修改 spec 和实现，不能只修 server。

### 3.2 为什么这挡住了个人页

个人页的正确产品模型应当是：

```text
个人 token 证明“我是这个 user”
+ enhanced_token 证明“我有权做受保护变更”
→ 只能读写这个 user 自己的条目
```

但当前 server 没有这个入口：

| 需要的个人能力 | 当前实际结果 |
|---|---|
| 用个人 token 查询自己的条目 | `401 unauthorized` |
| 用个人 token + enhanced_token 更新自己的条目 | `401 unauthorized` |
| 只查询自己，不暴露其他用户 | 无 `self` 端点，且 `GET /api/user/<user>` 也是管理权限 |
| 修改 local 声明 / 复用凭据保护字段 | 逻辑在 apply 中，不适用于 update |

因此当前个人页在真实 server 上只有两种可用路径：

1. 用户输入管理员 token；能查询/更新，但这本质上是管理员操作，不是个人自助。
2. 使用测试 mock；mock 验证了 UI，但不代表真实 server 已有权限入口。

前端不会再用管理员 token 代偿。个人页严格按目标契约提交：

```text
GET:
    Authorization: Bearer <personal token>

POST update / DELETE:
    Authorization: Bearer <personal token>
    body.enhanced_token = <admin 或任一已登记持有者 token>
```

真实 server 返回 `401` 时，页面直接显示“后端权限/契约缺口”，不再回退到管理员
Authorization。管理员 token 只用于独立的系统管理页。

### 3.3 建议后端补的最小能力

不需要给页面做专用接口，只需要把“个人自助”作为 API 语义补上。推荐最小契约：

```http
GET /api/user/<user>
Authorization: Bearer <personal token>
```

规则：

- personal token 对应的 user 必须等于路径 user；
- 只返回本人条目；
- 不返回 token。

```http
POST /api/user/<user>/update
Authorization: Bearer <personal token>
Content-Type: application/json

{
  "enhanced_token": "<admin 或任一已登记持有者 token>",
  "runtime": { "thread_pool_size": 16 }
}
```

规则：

- personal token 只能改自己；
- `enhanced_token` 只在声明 `local`、复用他人凭据、修改 `expected_*` 等受保护字段时必填；
- `enhanced_token` 只校验、不落盘、不回显；
- 白名单字段与现有 registry update 一致；
- 仍需触发 runtime reload。

如果后端选择“所有个人 update 都必须带 enhanced_token”，前端不需要改结构，只需把必填规则文本改成对应口径。

## 4. 个人页字段级权限建议

规范目前缺少“哪些字段个人可改、哪些字段必须管理员”的机器可读矩阵。建议在配置文档中补一张表：

| 字段 | 个人 token | 个人 + enhanced_token | 管理员 |
|---|---:|---:|---:|
| `ssh.default.*` | 可改 | — | 可改 |
| `role.<name>.host/user/jump/proxy` | 可改 | — | 可改 |
| `role.<name>.root` | 可改 | — | 可改 |
| `role.<name>.max_sessions` | 可改 | — | 可改 |
| `role.<name>.display/bin` | 可改 | — | 可改 |
| `role.<name>` 用户组 | 可改 | — | 可改 |
| `runtime.*` / `cdslog.*` | 可改 | — | 可改 |
| `role.<name>.mode=local` | 不可改 | 可改 | 可改 |
| 复用他人已登记凭据 | 不可改 | 可改 | 可改 |
| `expected_*` | 不可改 | 可改 | 可改 |
| `token` / `registered_at` | 不可改 | 不可改 | 不可改 |
| 全局 `config.json` / 业务进程 | 不可改 | 不可改 | 可改 |

这张表是当前 UI 的目标态定义，也是后端实现个人自助接口时最需要明确的契约。

## 5. 管理员系统页：接口已足够

管理员页当前只使用以下已有接口：

```text
GET  /api/config
PUT  /api/config
GET  /api/process/status
POST /api/process/reload
POST /api/process/restart
GET  /api/users              （只读概览，不编辑个人参数）
```

这些接口和 `_require_admin()` 口径一致，不需要后端为页面增加专用接口。

## 6. 结论摘要

```text
注册页后端阻断缺口：无
管理员系统页后端阻断缺口：无
个人自助页阻断缺口：有

缺口不是展示数据，而是权限入口：
当前 server 不允许 personal token 查询/更新自己的 registry 条目；
enhanced_token 目前只属于 apply，不属于 user update。

推荐：
1. 增加 personal-token-only-own-user 的查询/更新语义；
2. 为受保护变更定义 enhanced_token 规则；
3. 在配置文档补字段级权限矩阵；
4. 不为页面添加 UI 专用 schema。
```
