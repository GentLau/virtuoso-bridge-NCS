## 1. 判定标准

本调查不把“功能返回”当成线程生命周期完整，而检查五个条件：

| 条件 | 含义 |
|---|---|
| 所有权 | 创建者是否持有 thread 引用，能决定何时回收 |
| 停止信号 | 是否有 `Event`/timeout/close 等可协作停止机制 |
| 有界等待 | 是否有有上限的 `join`/wait，而不是无限等待 |
| 退出可观察 | join 超时后是否检查 `is_alive()` 并记录/上报 |
| 失败路径 | 异常、超时、取消路径是否与正常路径同样清理 |

结论中：

- **完整**：五个条件都有，或线程由明确的第三方生命周期托管且 close 合同足够。
- **有缺口**：缺少停止信号、join 无界、join 后不观察、失败路径不清理中的任一项。

## 3. P-076 专项复核

### 3.1 原始根因

旧完成判定是：

```python
channel.exit_status_ready()
and process.poll() is not None
and all(not worker.is_alive() for worker in workers)
```

最后一项把“channel 数据通路结束”错误地绑定到了“pump 线程生命周期结束”。
pump 可能阻塞在 Paramiko `ChannelFile.read()` → `Channel.recv()` →
`BufferedPipe` 的条件变量等待上；channel 已结束、本地 tar 已完成，并不自动
唤醒它。于是 `install_staged_path()` 永远执行不到，调用被拖到 per-call
deadline。

### 3.2 当前修复

当前代码已经完成两段修复：

1. 完成判定只看 channel + 本地 tar：
   `src/common/paramiko_backend.py:1425`。
2. channel pump 改为协作取消模型：
   - `_pump_channel` 只在 `recv_ready()` / `recv_stderr_ready()` 为真时读取；
   - 每轮检查 `stop_event`；
   - `_stop_tar_transfer` 先 set stop，再 close/kill/close/join；
   - 见 `src/common/paramiko_backend.py:449-492`、`1439-1464`。

本次复跑：

```text
status=PASS passed=3 total=3
no_residual_pump_after_download: leaked_threads=[]
```

证据：

- `test/artifacts/evidence/p076-thread-residual-red.json`
- `test/artifacts/evidence/p076-thread-residual-green.json`
- `test/artifacts/evidence/p076-thread-lifecycle-audit-current.json`

### 3.3 P-076 结论的边界

P-076 修复的是 **channel pump**。它没有顺带修复同一文件里的本地 pipe worker：

```text
_read_stream()              # 阻塞 stream.read()
_send_stream_to_channel()   # 阻塞 stream.read() / channel.sendall()
```

`_stop_tar_transfer()` 对它们只做 `join(timeout=1)`，没有在 join 后检查
`is_alive()`。因此：

- “P-076 的 channel pump 线程生命周期”：**完整**。
- “download_tar/upload_tar 创建的所有 worker 线程生命周期”：**不完整**。

## 4. 全局缺口分级与最小修复建议

### P1-01 ParamikoTunnel 转发连接 pump 与 handle 线程

**位置**

- `src/common/paramiko_backend.py:194-197`
- `src/common/paramiko_backend.py:215-243`
- `src/common/paramiko_backend.py:286-293`

**证据**

pump 使用阻塞 `client.recv()` / `channel.recv()`；`_stop` 只在循环开头
检查，`_handle_connection` 对子 pump 做无 timeout 的 `left.join()` /
`right.join()`。`terminate()` 设置 stop 并 close，但 `wait()` 即使在 timeout
后仍返回 `0`，不报告残留。

确定性最坏情况探针：

```text
wait_rc 0
wait_elapsed_s 0.5
alive_after_wait [3 个线程]
```

**最小修复**

1. 给 local socket 和 Paramiko channel 设置短 timeout（如 0.5s），
   或在循环内用 `select` / `recv_ready`。
2. 每次阻塞 I/O 返回后检查 `_stop`。
3. `_handle_connection` 的两次 join 改为有 timeout；join 后检查
   `is_alive()`。
4. `wait()` 必须在有残留时返回/报告失败，不能静默返回 0。

**先补红灯 TB**

需要。建议新增 `test/offline/core/thread_lifecycle_tunnel_tb.py`：

- fake client/channel 的 `recv()` 在 release event 上阻塞，`close()` 不解除；
- 启动 `_handle_connection`；
- `terminate()` + `wait(timeout=0.5)`；
- 断言返回后 `_threads` 为空；当前代码应红。

### P2-03 ThreadingHTTPServer 请求线程与“整体线程池”

**位置**

- `src/server/api_server.py:266-268`
- `src/server/api_server.py:397-406`
- `src/register/server.py:922-924`
- `src/register/server.py:986-1010`

**问题**

`ThreadingHTTPServer` 每个连接创建一个线程，`daemon_threads=True`。
在当前 CPython 3.12 的 `ThreadingMixIn` 实现中，daemon thread 不会被
`_Threads` 记录，因此 `server_close()` 不会 join 它们。现有
`max_inflight` 是业务 dispatch 的槽位限制，且槽位是在读取 body 之后才获取，
它**不是线程数上限**。

这意味着：

- 慢连接、坏请求、keep-alive 空闲连接可以长期占用 handler 线程；
- registration server 在停止时没有 drain/join，活动注册步骤可能被进程退出
  截断；
- business server 的 `drain_and_stop` 有 `wait_idle(timeout)`，但超时后
  `server_close()` 不会等待这些 daemon handler，随后 `middle.close()` 释放
  资源，剩余 handler 是否安全结束不再被观察。

**最小修复**

1. 在 `process_request` 进入点之前做线程/连接准入，而不是只在 dispatch 前
   做 slot 获取。
2. shutdown 时记录 active handler 数；drain 超时后给出结构化残留诊断。
3. registration server 需要与 business server 相同的 drain 策略，或明确
   声明“关闭即截断”的行为。该决定涉及 spec，不应由本轮调查擅自实现。

**先补红灯 TB**

需要。建议：

- `test/offline/core/top_layer_thread_pool_tb.py`：
  同时打开超过限制的空闲/慢连接，断言线程数有界、超限请求得到 429；
- `test/offline/unit/test_registration_shutdown_drain.py`：
  在处理中进行 shutdown，断言无未观察 handler。

### P2-04 Paramiko transport 第三方线程

**位置**

- `src/common/paramiko_backend.py:1125`（connect）
- `src/common/paramiko_backend.py:1806-1808`（close）

Paramiko `Transport` 自己创建 transport/packetizer 线程。项目只调用
`client.close()`，不持有/join 第三方线程。这个不在项目自有线程清单里，
但需要明确：

- 连接关闭后 Paramiko 线程是否退出，由 Paramiko 实现决定；
- 项目不应把“close 已调用”误写成“第三方线程已 join”；
- 若验收要求可观察退出，需要增加 Paramiko 版本适配或对 transport
  `is_active()` 做清理后断言，而不是把它算作项目线程。

不需要红灯 TB，除非验收要求第三方线程也必须可观察。

### P2-05 pyapi spectre ThreadPoolExecutor

**位置**

- `src/pyapi/packages/spectre.py:500-515`

`with ThreadPoolExecutor` 会等待所有 future 完成，因此正常/异常路径不会留下
线程；但它是上层批处理，没有取消协议。若某个 `_run_one` 自身不返回，
`run()` 会一直等待。这是上层行为的生命周期问题，不是 P-076 同类挂起。

**建议**

- 上层为每个子任务保留 deadline，并让 `_run_one` 的可阻塞点全部守约；
- 若需要硬取消，必须把不可取消的远端操作拆成可 kill 的进程/连接，
  不能直接靠 `Future.cancel()`。

## 5. 建议修复 / TB 顺序

1. **先补 P-076 扩展红灯 TB**：
   `_stop_tar_transfer` 后本地 pipe worker 不得残留。
2. **修 tar 本地 pipe worker**：这是 P-076 同一根因的最后一段。
3. **补并修 ParamikoTunnel pump/handle**：
   per-connection thread 是生产路径，且当前存在无 timeout join。
4. **补并修持久 shell reader**：
   command/file 常驻资源；reader 残留会随 token 生命周期累积。
5. **补并修 SOCKS5 resolver/connector**：
   先决定“严格零残留”还是“有界残留 + 可观察诊断”，涉及是否需要 helper
   process。
6. **补并修本地 command session reader**：
   当地模式生产路径，和 OpenSSH 后端一起收口。
7. **处理 P2 观察项**：
   OpenSSH 错误路径、supervisor reader、HTTP handler 线程、
   registration drain。
8. **将 maestro worker 移交给上层负责人**：
   不修改 pyapi 业务包代码，只在报告中保留证据和接口需求。

原则：

- 每个缺口必须先有一条确定性红灯 TB；不能先改生产代码再补测试。
- 修复优先复用现有 `_pump_channel` 模式或减少阻塞读，而不是继续加
  “等 close 唤醒”的 after-the-fact 补偿。
- `join(timeout)` 本身不是生命周期保证；没有 join 后的 `is_alive()`
  检查，就不是完整生命周期。

## 7. 最终回答

1. **P-076 的 tar channel pump 生命周期完整吗？**
   **完整。** 已有 stop_event、非阻塞轮询、有界 join 和红灯/绿灯 TB。

2. **P-076 涉及的 tar 全部 worker 线程完整吗？**
   **不完整。** 本地 pipe reader/writer 仍是阻塞读/写，join 后不检查残留；
   确定性探针已复现 `worker_alive_after_stop=True`。

3. **全项目线程生命周期完整吗？**
   **不完整。** 最突出的系统性缺陷是“用 close 当作唯一取消机制”：
   ParamikoTunnel pump、持久 shell reader、tar 本地 pipe、本地 command
   session reader 都是同一类；此外 SOCKS5 resolver/connector 和 HTTP
   per-connection daemon thread 也没有完整的停止/join/观察合同。

4. **下一步最小编码顺序？**
   先补 P-076 扩展红灯 TB，修 tar 本地 pipe；再修 ParamikoTunnel 和持久
   shell；然后处理 SOCKS5 与本地 command session；最后处理 P2 观察项。
   上层 maestro worker 交给上层负责人。
