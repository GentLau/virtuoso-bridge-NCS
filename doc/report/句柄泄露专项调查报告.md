### 0.2 关键官方语义（本报告判据）

| 函数 | 官方口径 | 出处 |
|---|---|---|

| `ddCatClose` | "Closes the category and purges its information from virtual memory."；"the process still has a **lock** on the category until it is freed using `ddCatClose`" | `doc/skdfref/chap3.html`（ddCatClose / dmAddCellToCategory 条目） |

| `ddReleaseObj` | 配对要求仅针对 write/append 模式创建占位文件的场景；读查询不需要 | `doc/skdfref/chap3.html`（ddGetObj / ddReleaseObj 条目） |

`dbClose` 的引用计数语义是全部 A 类缺陷的判据：**打开次数 > 关闭次数时，该 cellview 不会被 purge，常驻虚存**。

## 1. A 类：正常路径真泄漏（上层，必须修）

### A1 [P1] `virtuoso.schematic.read`：打开的 cellview 从不 `dbClose`

- 位置：`src/pyapi/packages/schematic.py:287`（打开）、`:396-399`（返回）。
- 代码事实：

```python
parts.append('let((cv vbOut vbInsts vbCdf vbParam)')
parts.append(
    f'cv = dbOpenCellViewByType({_q(request.library)} {_q(request.cell)} '
    f'{_q(request.view)} "schematic" "r")'
)
...
parts.append('vbOut)')   # 直接返回，全程没有 dbClose(cv)
```

静态配对统计（脚本对 `_read_skill` 函数体计数）：`dbOpen` 出现 1 次、`dbClose` 出现 **0 次**。

- 影响：每次 `schematic.read` 给目标 cellview 的打开计数 +1；重复读同一视图计数累积，永不 purge。大原理图/长会话下虚存随读取次数单调增长，并可能干扰后续需要 purge 的流程。
- 修复模板（与同项目 `symbol._read_skill:939-1005`、`layout._read_skill:1508-1552` 的既有安全写法一致）：

```lisp
let((cv vbCollected)
  cv = dbOpenCellViewByType(... "r")
  unless(cv error("schematic view not found"))
  vbCollected = errset(progn(<现有 vbOut 计算体>))
  dbClose(cv)
  unless(vbCollected error("schematic read failed"))
  car(vbCollected))
```

### A2 [P1] `schematic.write` 的 `place_instance`：master 句柄从不关闭

- 位置：`src/pyapi/packages/schematic.py:421-427`。

```python
if op == "place_instance":
    master = f'dbOpenCellViewByType({...} "schematicSymbol" "r")'
    return (
        f'let((vbMaster) vbMaster = {master} '
        f'dbCreateInst(vbSchemCv vbMaster {...} ...))'
    )
```

- 事实：生成的 SKILL 里 `vbMaster` 打开后没有任何 `dbClose`；`dbCreateInst` 只消费 master 数据，不接管调用方的打开句柄。
- 影响：每放置一个实例泄漏一个 master（`schematicSymbol` superMaster）引用；批量摆放/复刻场景线性累积。
- 修复模板：

```lisp
let((vbMaster vbInst)
  vbMaster = dbOpenCellViewByType(...)
  unless(vbMaster error("master symbol not found"))
  unwindProtect(
    progn(vbInst = dbCreateInst(vbSchemCv vbMaster ...)
          unless(vbInst error("instance not created")) vbInst)
    progn(when(vbMaster dbClose(vbMaster)))))
```

### A3 [P1] `virtuoso.cellview.cell.copy`：`dbCopyCellView` 的目标句柄不关

- 位置：`src/pyapi/packages/cellview.py:332-335`。

```lisp
vbOk = dbCopyCellView(vbSourceCv {new_library} {new_cell} vbView~>name)
dbClose(vbSourceCv)      ; 只关了源
vbOk                     ; 目标 cellview ID 直接返回，未关
```

- 判据：
  - 官方：`dbCopyCellView` 返回 `d_cellViewId`（目标 cellview ID）；
  - 同项目内部先例：`_symbol_generate.py:153-159`、`:162-177`、`:203-223` 对 `dbCopyCellView` 的返回值都执行了 `dbClose`。
- 影响：每次成功 copy 泄漏一个目标 cellview（写模式）。
- 修复模板：

```lisp
vbOk = dbCopyCellView(vbSourceCv ...)
dbClose(vbSourceCv)
when(vbOk dbClose(vbOk))
vbOk
```

### A4 [P1] `virtuoso.cellview.view.copy`：同上

- 位置：`src/pyapi/packages/cellview.py:417-420`：`vbCopied = dbCopyCellView(...)`；`dbClose(vbSourceCv)`；`vbCopied` 未关。修复同 A3。

### A5 [P1] `virtuoso.cellview.cat.delete`：`ddCatOpen` 句柄全路径不关（带锁）

- 位置：`src/pyapi/packages/cellview.py:532-540`。

```lisp
vbCat = ddCatOpen(vbLib {category} "a")
if(!vbCat then list("error" "categoryReopenFailed")
else progn(
  vbRemoved = ddCatRemove(vbCat)
  if(!vbRemoved then list("error" "categoryDeleteFailed")          ; 出口 1：未 close
  else progn(
    vbVerify = ddCatOpen(vbLib {category} "r")
    if(vbVerify then list("partial" "categoryDeleteVerificationFailed")  ; 出口 2：vbCat、vbVerify 都未 close
    else list("ok")))))                                            ; 出口 3：vbCat 未 close
```

- 判据：`ddCatClose` 文档明确"purges its information from virtual memory"，且**在 `ddCatClose` 之前进程仍持有 category 锁**；`ddCatRemove` 只从磁盘移除，不释放句柄。
- 影响：每次 `cat.delete` 泄漏 1 个 category 句柄 + 锁；删除失败的校验路径再泄漏一个读句柄。

### A6 [P1] `virtuoso.cellview.cat.rename`：三处未配对

- `cellview.py:561-562`：目标名存在时 `vbExisting = ddCatOpen(new_name,"r")` → 直接 `list("error" "destinationCategoryExists")`，未 close。
- `cellview.py:583-591`：`vbSource = ddCatOpen(category,"a")` → `ddCatRemove` 之后三条出口（`587` 删除失败 / `590` 校验发现仍存在 / `591` 成功）都没有 `ddCatClose(vbSource)`。
- `cellview.py:589-590`：`vbVerify` 非 nil 分支未 close。
- 影响：rename 每次泄漏源 category 句柄 + 锁；附加分支各泄漏一个读句柄。

## 2. B 类：错误路径漏关（上层，统一用 `unwindProtect` 兜底）

> 判据：这些路径正常返回 `nil` 时 `dbClose` 仍会执行；一旦 SKILL **error**，后续 `dbClose` 被跳过。同项目其它位置已用 `errset`/`unwindProtect` 防御同类失败，属实现口径不统一。

| # | 位置 | 触发条件 | 泄漏对象 |
|---|---|---|---|
| B1 | `layout.py:913-932`（`display` 的 `fit_view`/`zoom`） | 窗口找不到或 `hiZoomIn` 报错 → `dbClose(vbLayoutCv)` 被跳过 | `vbLayoutCv`（r 模式） |
| B2 | `layout.py:1286-1298` / `verilog.py:577-589`（`_verify_import`） | 读属性抛错（如空版图 `bBox=nil` 再 `xCoord`） | 待校验的 cv |
| B3 | `schematic.py:693-698`、`764-769`（写后保存 / `check_and_save`） | `schCheck` 报错 → `when(vbSchemCv dbClose(vbSchemCv))` 跳过（写入命令本身已有 `unwindProtect`，保存步骤没有） | `vbSchemCv`（a 模式） |
| B4 | `layout.py:828-836`（`place_mosaic`） | `dbCreateSimpleMosaic` 抛错 → `dbClose(vbMaster)` 跳过 | `vbMaster`（r 模式） |
| B5 | `cellview.py:329-334`、`413-419`（copy） | `dbCopyCellView` 抛错 → 源句柄 close 跳过 | 源 cv（叠加 A3/A4 的目标句柄） |
| B6 | `maestro.py:3145-3150` + `3162-3163`（`open_waveform_gui`） | `awvPlotWaveform` 失败 → 已创建的 plot window / 可能新建的 session 不回滚 | 波形窗口 + Maestro session |

统一修复模板（示例）：

```lisp
let((cv vbRc)
  cv = dbOpenCellViewByType(...)
  unless(cv error("view not found"))
  vbRc = unwindProtect(
          progn(<业务体>)
          progn(when(cv errset(dbClose(cv))))))
```

## 4. D 类：反向问题（不是泄漏，但违反 spec 的句柄生命周期）

### D1 [P2] screenshot 默认会关闭"操作者自己没打开"的窗口

- 实现：`schematic.py:810-836`、`symbol.py:1015-1040`、`layout.py:1613-1639` 都是"窗口列表里找已有窗口 → 找不到才 `geOpen` → 统一 `unless(leave_open when(vbW hiCloseWindow(vbW)))`"。
- spec：`spec/design-concepts/上层/4-layout.md:174` 明确 "`leave_open` 默认 false；**只关闭本操作自己打开的窗口，不动别人已开的窗口**"。
- 现状：默认路径下会把用户原本开着的原理图/版图窗口一并关闭；显式 `window_id` 同样被关。
- 建议：记录 `opened_here` 标志（仅 `geOpen` 分支置 t），只在 `opened_here && !leave_open` 时 `hiCloseWindow`。

### D2 [观察项] maestro 收尾的作用域

- `maestro.py:629-634` 的 `_purge_cellview` 会对同 `lib/cell/view` 的**所有** open cellview 执行 `dbPurge`，可能波及别的 session；`?forceClose t` 出现在 `maestro.py:441/2765/3184`，而 `:553-558` 的注释已记录 force-close 引发 SIGSEGV 的历史教训。
- 按用户口径（maestro GUI 有人工关路径）不作为泄漏处理，但建议把 purge 限定到本会话自己创建的 cellview。

## 6. 真机复现方案（可回滚，供测试同学执行）

> 本次只读调查未在现场 CIW 执行；以下方案不做写数据，只读计数，并在结束时回滚。

以 vblog 会话为例（token `vb-vblog`，8127 `basic.skill.execute`）：

1. 计数：`before = length(dbGetOpenCellViews())`
2. 触发目标操作（读操作，不落数据）：`virtuoso.schematic.read`（对现有测试 cell），或 `virtuoso.cellview.cell.copy`（对一次性测试 cell）
3. 计数：`after = length(dbGetOpenCellViews())`；预期 `after > before`（A1/A3）
4. 回滚：对新增视图 `errset(dbClose(cv))` 恰好一次，恢复引用计数；若已被其它会话打开无法区分，记录差异后重启该 CIW

说明：由于 `dbOpenCellViewByType` 对同一视图返回同一 dbid、打开计数是全局引用计数，**回滚只需 close 一次**即可抵消本次探测新增的一次打开；不要在存在他人引用的视图上做此实验。

### 9.3 复审新发现（建议修复，尚未改代码）

**R1 [P3] `schematic._open_edit_skill` 的 `type-mismatch` 分支不会中止，类型不符会被误报为 "locked"**
- 位置：`src/pyapi/packages/schematic.py:404-420`。
- 生成文本：`... vbCv = dbOpenCellViewByType(... "r") unless(vbCv "type-mismatch") when(vbCv dbClose(vbCv)) vbEdit = dbOpenCellViewByType(... "a") ...`
- 真机语义探针（8127，token `vb-vblog`，纯表达式）：
  `let((x) x = nil unless(x "MISMATCH") "CONTINUED")` → `"CONTINUED"`，证明 `unless` 只是普通求值，**不会像 return 一样中止 progn**。
- 后果：视图存在但类型不是 schematic 时，read-open 返回 nil → 代码继续做 append-open → 同样失败 → 对外报 "is locked by another session"，误导排障；`_open_failure` 里的 `type-mismatch` 文案是死代码。
- 建议：`if(!vbCv then "type-mismatch" else progn(when(vbCv dbClose(vbCv)) vbEdit = ...))`。

**R2 [P2] `schematic.write` 在"打开之后"做命令校验，校验失败直接 return，泄漏全局 edit 句柄 + 编辑锁**
- 位置：打开在 `schematic.py:703-715`；随后的结构校验 `:716-722` 两处 `return` 均未调用 `_close_edit_skill()`：
  - `not isinstance(command, dict) or "op" not in command` → `return Result(False, ...)`；
  - `_atomic_skill(...)` 抛错（如缺少 `x`/`y`、未知 op）→ `return Result(False, ...)`。
- 离线确定性复现（用假 Middle 记录发出的 SKILL）：commands=`[{"op":"place_label"}]`（缺 x）→ `ok=False, error=command 0 invalid: 'x'`，共发出 **1** 条 SKILL（仅 open），`close_sent=False`。
- 后果：一次非法写请求即把该视图的 edit 锁留在 CIW；后续同会话/异会话写被挡。
- 对照：`symbol.write`、`layout.write` 都在 open **之前**完成 `planned` 校验（`symbol.py:465-477`、`layout.py:500-528`），因此无此问题——schematic 是三者中唯一未对齐的。
- 建议：把命令校验/`planned` 构建移到 `_open_edit_skill` 之前；或在这两个 `return` 前补 `_close_edit_skill()`。并将 `test_schematic_contracts.py:343-357` 的既有用例补上"必须发出 close"的断言（当前只断言报错文案，所以漏检）。

**R3 [P3] close 结果被吞：`dbClose` 失败也把全局置 nil**
- `schematic.py:422-427`、`symbol.py:370-375`、`layout.py:435-440` 的 close 帮助函数都是 `when(... dbClose(...)) <global> = nil t`，不检查 `dbClose` 返回值。
- 后果：close 失败时引用被主动丢弃、也无可观测证据，锁可能仍残留且无法重试。建议 `errset(dbClose(...))` 并将失败写入 step/错误。

**R4 [P2] `maestro.open_waveform_gui` 失败路径仍泄漏新建 session**
- 位置：`maestro.py:3088-3167`。`session_created` 在 `:3103` 计算，但 `except`（`:3166-3167`）只返回失败，不关闭 session；`:3107`（找不到 results 目录）、`:3113`（找不到 PSF）、`:3131`（信号缺失）、`:3145-3152`（建窗/绘图失败）都会走到这里。
- `7e7f258` 只补了"绘图失败时关窗口"，**没有覆盖 session**：用户历史名写错等常见错误会留下一个只读 Maestro session，只能靠人工 `close_waveform_gui`（但失败返回里没有 session 名，调用方拿不到）。
- 建议：在 `except` 里补 `if session_created and session: self._close_session(session, ...)`（与其它 maestro 操作的 `_close_if_created` 口径一致）。

**R5 [P3] `schematic._read_skill` 只保护了正常路径**
- `schematic.py:396` 的 `dbClose(cv)` 追加在长 body 末尾；body 未包 `errset`/`unwindProtect`，任何一个属性访问/过滤表达式报错都会跳过 close（`layout.py:1508-1552`、`symbol.py:939-1005` 的读路径都用 `errset` 做了保护）。
- 建议：改为 `vbCollected = errset(progn(...)); dbClose(cv); unless(vbCollected error("schematic read failed")); car(vbCollected)`。

**R6 [P3 设计注记] 批量写把 edit 句柄存 CIW 全局，需要明确"一 token 一 CIW"不变量**
- `vbSchemCv` / `vbSymCv` / `vbLayoutCv` 都是会话级全局，跨多个 `execute_skill` 请求存活；两用户探针的前提正是"两个 CIW 共享同一库"。若将来两个 token 共用一个 CIW，这两条写序列会互相覆盖句柄；另外业务进程在 open 与 save 之间崩溃会让 edit 锁留在 CIW（跨请求没有 `unwindProtect` 机会）。
- 建议：把该不变量写进 spec/注释；如需更强保证，用按 token 命名的全局变量，或把整批命令+保存收敛为单条 SKILL 请求。

**R7 [P4] C3 修复的注释理由不准确**：`src/common/paramiko_backend.py:1306-1308` 写 "the Transport keeps the channel in its map, so ... never garbage collected"——本机 paramiko 是弱引用表 + `Channel.__del__`，GC 会关；修复本身正确，改注释即可。

**R8 [P4 测试卫生] 一个时序敏感用例**：`test/offline/unit/test_ssh_edges.py:819-829` 用 0.05s 预算；在一次 8 文件组合跑中连续失败两次，单跑/两两组合/`pytest test/offline/unit` 全量均通过。建议放宽预算或改事件驱动，避免 CI 抖动。
