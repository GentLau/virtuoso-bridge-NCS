#### C-02：local 模式没有实现 `parallel=False` 的同 token 串行（P0）

`C:\Users\user\Desktop\repos_Github\virtuoso-bridge-NCS\src\transport\middle.py:109-118` 在 local 分支直接调用 `_local_command()`，没有复用 remote 的 `_serial_lock`；因此同一 token 的两个默认命令会重叠。实测两个各 0.25 秒的 local 命令总墙钟约 0.44 秒，而不是约 0.5 秒以上。

#### C-03：用户标识可造成远端路径逃逸（P0/P1）

这直接破坏 `多用户设计.md` 和 `配置一览.md` 的用户名隔离要求，应增加安全字符集/规范化及 root containment 测试。

#### C-04：默认 file root 仍回退到 token（P1）

`src\transport\remote_roles.py:33-45` 的 `file_root` fallback 是 `f"{scratch}/{entry.token}"`，与当前大多数 Spec 已定稿的 `<scratch_root>/<user>` 相反。注册流程显式写 root 时可能掩盖该问题；直接构造 entry、旧迁移条目或缺省配置会回到 token 路径。

#### C-05：注册步骤状态机没有真正校验前置阶段（P1）

`src\transport\register\flow.py:368-380` 接收 `expected_stage` 却从不比较它。实测：`start()` 后直接调用 `probe()` 会进入 `probed`；`probed` 后再次调用 `validate()` 会退回 `validated`。这不符合六步流程的顺序约束，也使页面接口可以被乱序调用。

#### C-06：`token_ok` 不参与提交门槛（P1）

`src\transport\register\models.py:105-107` 的 `ConnectivityReport.ok` 只判断 `command_ok && skill_ok && fingerprint_ok`，漏掉 `token_ok`。实测构造 `token_ok=False`、其余为 true 的报告仍可让 `RegistrationFlow.verify()` 进入 `committed`。这是注册授权门槛的逻辑缺陷。

#### C-07：split-host/不同账号的路由实现不完整（P1）

- `src\transport\register\flow.py:140-228` 的 remote probe 只用 `request.host/ssh_user` 建一个 runner；即使 `daemon_host != host`，端口、hostname、指纹、Python 和 scratch 可写性仍主要在 command host 上验证。
- `src\transport\tunnel.py:64-77` 的 runner cache 只用 host 作为 key；同一 host 但 daemon user 与 command user 不同时，会复用第一个用户的 runner。实测同 host/不同 user 时 command runner 仍带 daemon user。
- `skill_runner` 使用 `expected.daemon_user`，`command_runner` 使用 `route.command.user`，但二者在同 host 下会被错误合并。

这不仅是“测试缺失”，而是 split-host 和角色账号语义尚未完成。

#### C-08：per-token SSH/channel 隔离未闭合（P1）

- `src\transport\ssh.py:184-195` 的 ControlPath 只由本地用户、SSH user、host、jump 组成，不含 token；两个 token 同 host/account 会共享同一 master socket。
- `src\transport\tunnel.py:215-250` 的 channel semaphore 只包住 `parallel=True` 命令和文件传输，默认串行命令、隧道常驻 channel 没有计入预算。
- 最新的 `SSHRunner.close()` (`src\transport\ssh.py:1268-1298`) 会对共享 ControlPath 执行 `-O exit`；一个 token 关闭 runner 可能把另一个 token 的 master 一起关闭。

这与 Spec 的“不同 token 不得跨 token 复用 SSH/连接/channel”直接冲突。

#### C-09：端到端 deadline 没有贯穿 tunnel 建立（P1）

`src\transport\middle.py:93-102` 先执行 `ensure_tunnel()`，然后才把完整 `timeout` 传给 `SkillClient`。实测把调用 timeout 设为 0.01 秒并让 `ensure_tunnel()` 睡眠 0.08 秒，调用仍耗时约 0.078 秒并成功返回。违反 `spec\README.md:63` 的“端到端 deadline，不得重启完整 timeout”。

#### C-10：日志 max_bytes 不是硬上限（P1）

`src\bridge\resources\ramic_bridge_daemon_3.py:189-205` 在 error 行仍超限时固定保留头尾各 100 行，没有按 `max_bytes` 再裁剪。用 300 行、每行约 100 字节的 error 日志、`max_bytes=10` 实测返回约 10,441 字节。违反日志标准 `80-95` 的单次字节上限。

#### C-11：local 模式可接受不一致的 daemon/local port（P1）

`src\transport\register\flow.py:109-131` 只检查 local daemon port，却允许 `local_port != daemon_port`；`BusinessServer` 后续按 `local_port` 连接，可能连接到错误端口。注册配置明确 local 模式不需要独立 local tunnel port，应拒绝该组合或强制同号。

#### C-12：文件接口没有落实 ServerPath/root 隔离（P1）

`src\transport\middle.py:125-150`、`src\transport\tunnel.py:227-290` 直接接受调用方的绝对 `remote_path`，没有把它限制在 `route.file.root`，也没有拒绝 `..` 逃逸或区分“路径不可见/普通命令失败”。这与 `spec\README.md:62-64,82-84`、`三层整体架构设计.md:255-257` 不一致。

#### C-13：部署部分失败没有远端回滚（P1）

`src\transport\tunnel.py:157-180` 先创建远端目录，再逐个上传 daemon、IL、setup；中途失败时只关闭 runner，已写入的远端文件和目录不清理。Spec 只规定 registry 不落盘，没有规定或实现远端 staging/cleanup，重试可能继续使用半成品。

#### C-14：Spectre route 只存储不消费（P1/P2）

`RegistrationRequest`/`UserEntry` 接受 `spectre_host/spectre_bin`，但 `BusinessServer.run_command()` 没有 `purpose` 或 Spectre route 选择，`RemoteClient` 只使用 `command_runner`。配置表和 README 对 Spectre/RuntimePurpose 的“已定义/未决”口径不一致，当前不能宣称 Spectre 垂直切片完成。
