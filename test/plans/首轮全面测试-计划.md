## 5.1 覆盖率口径（防驳回版，必须照此表述）

**绝不写"覆盖率 100%"这种裸结论**。只允许写成：

> 在口径 `<A>` 下，行覆盖 `<x%>`、分支覆盖 `<y%>`；未覆盖的 `<N>` 行已逐条列明原因（分类见下表），
> 复算命令 `<cmd>`，原始数据 `<path>`。

口径 `<A>` 必须显式声明三件事：**统计范围**（哪些文件）、**执行集合**（跑了哪些测试/TB）、**合并方式**（coverage combine 的输入）。

| 审批最可能的攻击点 | 我们的应对（必须留证） |
|---|---|
| "口径混用"（离线数字冒充全量） | 同时给**离线三层**与**离线+真机合并**两个数字，各自标注执行集合 |
| "用 pragma: no cover 藏行" | 统计全仓 `# pragma: no cover` 出现次数与逐条理由（`rg -c` 证据） |
| "只跑了部分测试" | 列出本轮所有 coverage run/append 命令与时间戳；给出 pytest 收集数 |
| "真机没跑就说覆盖" | 每个真机场景给 TB 输出 + evidence 文件路径；没跑到的显式写"未执行" |
| "分支没测" | 同时给 `--branch` 报告，不只给行覆盖 |
| "覆盖了但没验证行为" | 每条能力域配"行为证据"（TB 的 ok/计数），覆盖率只作辅助 |
| "环境缺陷糊弄过去" | 环境缺陷与被测缺陷分开列，各自给判据 |

**未覆盖行的四分类**（每条未覆盖行必须落入其一，并给出依据）：
1. `env-blocked`：需要当前没有的环境（如 py2.7 解释器、第二台 Cadence 机器）；
2. `spec-exempt`：spec 明确不做（如 split-host CDS.log、跨机启动 daemon）；
3. `defensive`：防御性/不可达分支（要给出"为什么不可达"的证明）；
4. `to-fix`：本轮应补但还没补的测试（必须给出补测计划，不能留白）。

禁止事项：把 `to-fix` 混进 `defensive`；用"大概/基本"描述覆盖；用行覆盖代替行为结论。
