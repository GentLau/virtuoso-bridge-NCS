## A. 仍待修（2 条）

### A-0　P-051 [P1] `layout.gds`（`file_is_local=false`）发布时不建目标目录

* **事实**：`src/pyapi/packages/layout.py:1354-1366` `_publish_remote_copy()` 直接
  `cp <src> <dest>`，**不 `mkdir -p $(dirname <dest>)`**。同一个包里另外两条发布路径都建目录：
  `_publish_remote`（下载到本机）走 `local.parent.mkdir(parents=True)`（`:1339`）、
  截图走 `mkdir -p $(dirname ...)`（`:1434`）—— 只有 remote→remote 这条漏了。
* **A/B 实测（可复跑）**：同一次 `virtuoso.layout.gds --action export --file_is_local=false`
  * A 目标目录**已存在** → `ok=true`，`publish_log`/`publish_gds` 全过；
  * B 目标目录**不存在** → `ok=false`，`publication_error: cp: cannot create regular file
    '.../gds-publish-missing/sub/out.gds.xstream.log': No such file or directory`，
    且停在 `publish_log`（**GDS 本身都没发布**）。
  证据：`test/artifacts/evidence/round3-gds-publish-red.json`。
* **影响**：S11 工程链的 `gds` 阶段必挂（`test/artifacts/evidence/s11-round3/s11-gds.json`），
  drc/lvs 因拿不到 GDS 也全挂（`value_keys=[]`）；调用方只要给一个"还不存在"的输出目录就中招
  （真实场景很常见：按 run-id 建新目录）。
* **建议修法**：`cp` 前加 `mkdir -p $(dirname <dest>)`（与截图路径一致），或复用同一 helper；
  另外 `publish_log` 失败应先报"日志发布失败"而不是让整个导出看起来像 GDS 失败。
* **复现（已固化为 TB）**：`python -m pytest test/offline/unit/test_layout_publish_contracts.py -q`
  —— 当前 `test_publish_remote_copy_creates_destination_dir` 为红，其余 3 条（失败回报、相对路径拒绝、
  下载路径建父目录）为绿对照。

### A-1　P-044 [P1] `layout.write` 锁误判：同一会话第二次写必失败（本轮定位到**双重根因**）

证据（干净实例、可复跑）：`test/artifacts/evidence/round3-layout-p044.json`

```
ciw_pid                      : 964528
lock_files                   : layout.oa.cdslck
                               layout.oa.cdslck.RHEL30.GLIS-DESKTOP.localdomain.964528
lock_owned_by_ciw            : true          ← 锁的持有者就是正在写入的 CIW
write_1_ok                   : true
write_2_error                : RuntimeError: layout view schemtest/p044_probe/layout
                               is locked by another session
write_2_steps                : [view_exists]  ← 卡在判锁，命令一条都没执行
verdict                      : FALSE POSITIVE
```

复现：`python test/semi/probes/layout_p044_second_write_probe.py --work-dir test/artifacts/env/log-vblog --token vb-vblog`

根因 1（判锁）`src/pyapi/packages/layout.py:386-395`：`_is_locked()` 只做 `ls -A <view>/*.cdslck`，**不看持有者**；`:486-489`（write）与 `:1025-1029`（gds export）据此直接拒绝。

根因 2（句柄泄漏，本轮新增）`layout.py:497-508`：写循环 `dbOpenCellViewByType(..., "a")` **从不 `dbClose`**（对照 `_save_expr` 是关的）→ 每次写入泄漏一个 edit 模式 cellview，使本会话的锁常驻。也就是说**写 #1 成功的那一刻就已经把该视图"锁死"**。

影响：layout 包 E2E 自 WRITE-02 起全挂（14:38、14:5x 两次复现）；交互式"连续写同一视图"不可用。

建议：① 写循环补 `dbClose`（失败路径同样 close）；② 判锁改看 owner pid（`<view>.cdslck.<host>.<pid>` 后缀 vs 本会话 pid），或改为"先尝试 append-open，拿到 dbid 即视为可用"。

复验方式：修好后我直接用 `layout_e2e_tests.py`（不改断言）在 wsl-gent 落绿证据。

### A-2　P-047 [P2 新] `verilog.import` 结构导入静默依赖 CIW cwd 的 `cds.lib`，失败被报成 `incomplete_log`

现象：按 [推荐测试环境](../docs/推荐测试环境.md) §0 规范布局启动 CIW（**cwd = 专用 run 目录**）后，`virtuoso.verilog.import` 返回

```json
{"ok": false, "error": "incomplete_log",
 "steps": [..., {"name": "ihdl", "ok": false,
   "detail": [1, "", "ERROR (VERILOGIN-93): Incorrect entry specified with the
              -CDSLIB option. Exiting.\nWARNING (VERILOGIN-208): Could not create the log file."]}]}
```

现场：batch 目录 `/<run>/.vb_verilog/schemtest__vlog_imp_top/` **没有 cds.lib**；对照 14:07 同一操作成功（当时 cwd=`/home/Gent/project/vblog`，有 cds.lib，复制出的 batch cds.lib 7554 B）。

根因（代码）：

* `src/pyapi/packages/verilog.py:140` 用 `getWorkingDir()` 取 work_dir；
* `:450-458` `cp <cwd>/cds.lib <run_dir>/cds.lib` —— 这步**不进 steps、失败不告警**；
* `:509` 用 `<run_dir>/cds.lib` 跑 `ihdl`；
* `:519-522` 缺 `End of Logfile.` 就报 `incomplete_log`，把真实原因（-cdslib 无效）吞掉。

影响：规范布局（cwd=run 目录）下 verilog 结构导入 100% 失败；错误信息把"缺/无效 cds.lib"伪装成"日志不完整"，排障方向被带偏。

建议：batch cds.lib 不依赖 cwd（由 `ddGetObjReadPath`/当前 cds.lib 生成，或调用方显式传入）；`cp` 与 `ihdl` 的失败原样回显（如 `batched_cdslib_missing`）。

测试侧现状：run 目录放了一条指向工程 cds.lib 的软链作为绕行，`verilog_e2e_tests.py` **4/4 PASS**（`round3-package-e2e/verilog-cdslib-workaround.log`）。请设计侧确认"cwd 必须有 cds.lib"是否是既定约定——若是，请在接口文档写明并给出明确报错。
