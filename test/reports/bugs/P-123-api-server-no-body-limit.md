# P-123 · 业务面 `POST /api/operation` 无请求体上限：按声明 `Content-Length` 直接读取（控制面同位置有 16 MiB 上限）

| 字段 | 值 |
|---|---|
| 级别 | P2（暴露面/线程与内存 DoS；默认 127.0.0.1 降险但 `--host` 可暴露） |
| 层 | 顶层 · 业务面 HTTP 入口（api_server） |
| 归属 | 设计侧（`_read_json` 加与注册面一致的 16 MiB 上限；建议抽共享 helper，超限结构化 4xx） |
| 状态 | **待设计修** |
| 位置 | `src/server/api_server.py:91-104`（`read(length)` 无 cap）；对照 `src/register/server.py:62,155-165`（`_MAX_REQUEST_BYTES=16MiB`+拒绝语义） |
| 首报 | 2026-10-08（外部静态审查 A6） |
| 最近更新 | 2026-10-08（测试侧建卡） |

## 现象

`Content-Length: 8G` 的请求可让业务线程按声明长度读取/等待（慢速发送可长期占线程），连接级 DoS。

## 复现

```text
常驻环境：向业务面发声明超大 Content-Length 的 POST（或慢速发送）→ 观察线程占用与超时行为；TB 待补（server 组）。
```

## 证据

静态核实（2026-10-08）：业务面无 _MAX、控制面有；读取路径 `rfile.read(length)`。

## 验收判据（修好即转绿）

① 业务面与注册面同口径上限（或共享 helper）；② 超限结构化 4xx，不静默断连；③ 正常体积请求回归不变。

## 下一步 / 责任人

等设计修；测试侧补超大 body 与慢速 body 两条用例（可离线）。
