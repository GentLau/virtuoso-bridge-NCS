## 5. 未覆盖分类（本轮盘点，滚动补齐）

### env-1（环境阻塞）：S11 的 CDL / LVS

**卡点只有 CDL 源网表一处——Calibre deck 侧已实测可用。**

1. **LVS deck 没问题（已纠正早先判断）**：`1p6m_3X1Z1U/calibre.lvs` 虽是 `#!tvf` 头，但 `calibre -lvs -hier <deck>`
   **能直接解析**：日志回显了 `#!tvf` / `tvf::VERBATIM` / `TVF_NUM_FUN` 等内容，唯一的错误是
   `ERROR: Failure to open input file lvs_top.gds for read access`（因为我没放版图）。deck 内声明的输入是
   `SOURCE PRIMARY "lvs_top"` / `SOURCE PATH "lvs_top.cdl"` / `SOURCE SYSTEM SPICE` / `LAYOUT SYSTEM GDS`。
   → 只要按 deck 期望的文件名提供 GDS + CDL，LVS 就能跑。
2. **CDL 导不出（真卡点，6 个变体全部失败）**：`si -batch -command netlist` 在本 PDK 上
   - 带 `.simrc`（stop list `("auCdl")` 或 `("auCdl" "symbol")` 等 4 种）→ `si_rc=255`：
     `Failed to find 'hnlCDLFormatInst' property for element 'pch_25'` + `OSSHNL-514`；
   - **不带** `.simrc` → `si_rc=0` 但 CDL 只有空 `.subckt`（器件行被静默丢弃）；
   - `simSimulator="auLvs"`（2 个变体）→ `si_rc=255` 且日志无 ERROR（si.env 层就不接受该值）。
3. **根因（SKILL 探针实测）**：器件 cell `tsmcN65/nch_25` 的 CDF **没有**任何 CDL 属性
   （`hnlCDLFormatInst`/`hnlCDLParamList`/`nlAction`/`CDLBlackBox` 全为 no），其 `auCdl` 视图虽然存在，
   但**只有 27 个 shape、0 个 instance、无 `simInfo`、属性表只有 `instNamePrefix`**。
   也就是说 netlister 拿不到"器件行怎么打"的信息，于是把器件当层次单元往下钻，正好对应 Ossh 的
   `Failed to find 'hnlCDLFormatInst' ... Ensure that it is either a black box or it has nlAction property with value = "stop"`。
4. **探针与证据**：`test/semi/probes/cdl_export_variants_probe.py`（6 变体矩阵 + sha256 自证变体不同）、
   `test/artifacts/env/scenario-project65/cdl-variants.json`、`si.log`、以及 SKILL 属性探针
   `test/artifacts/env/scenario-project65/stage/cdl_props.il`。

## 7. 过程风险（已发生，需流程约束）

1. **并发跑测互相覆盖覆盖率数据**：本轮期间有两套独立 coverage 运行同时写 `.coverage`（表现为 20:47 出现 `coverage-run-meta.json`，
   而 20:13 的 `coverage-merged-2026-09-22.json` 被清理删除）。
   对策：**每个 runner 用独立 `COVERAGE_FILE`**（本报告主口径已改用 `.coverage.tb-offline-v3`），并在报告里记录文件名。
2. **TB 共用同一个真机 daemon 会互相干扰**：S8 第一轮"返回日志不是连续切片"就是两个 agent 共用 `vblog` daemon 导致
   CDS.log 交错（环境干扰，非缺陷）。对策：真机 TB 必须独占 token；并发时用不同 daemon 端口。
3. **`.simrc` 有无会改变 `si` 行为**：探针第一版因为没上传 `.simrc`，四个"变体"实际输出完全相同仍全报成功——
   教训已写进探针文件头：**变体必须用 sha256 自证不同**。
4. **场景目录名会被并发 agent 撞车**：本轮 21:38 有另一个 agent 也在做 scale-100，
   直接覆盖了 `test/artifacts/env/scenario-scale-100/evidence.json`（它用 `cloud000`/6801 端口，
   1600 调用 800 失败），我只好换名重跑为 `evidence-scale100-codex.json`。
   对策：**证据文件名带上场景与执行者后缀**（如 `evidence-<scenario>-<who>.json`），
   并且引用证据时必须写全文件名——本轮 §4 表已按此更新。
5. **瞬态红灯（已出现 3 次，三次都做了复现尝试，仍未复现 → 未定级）**：
   - ① v15 全量跑：`test/offline/scenario/test_business_local.py::TestBusinessLocal::test_command_rc_stdout_stderr` 红；
   - ② v10 分支跑、③ v13 分支跑：都是
     `test/offline/integration/test_business_child_supervision.py::TestSupervisedBusinessChild::test_drain_stops_child_cleanly` 红。
   - **每次的单点复核都绿**：单跑该用例、单跑整层（②：26 passed / 3 skipped）。
   - **第三次出现后的复现尝试（本轮新增，全部为绿）**：

     | 尝试 | 命令/条件 | 结果 | 日志 |
     |---|---|---|---|
     | 层内连跑 5 次 | `pytest test/offline/integration` ×5 | 5/5 全绿 | `test/artifacts/evidence/flake-hunt-integration.log` |
     | 顺序/隔离假设 | `pytest test/offline/unit test/offline/integration` | 全绿（含该用例） | `test/artifacts/evidence/flake-hunt-unit-integration.log` |
     | 负载假设 | 6 个 CPU 燃烧 job 下单跑该用例 | 绿 | `test/artifacts/evidence/flake-hunt-load.log` |

   - 线索：两例都依赖**真实子进程/socket**；②/③ 用的是 `--port 0`（**排除**固定端口冲突），
     因此最可能是**全量跑时的外部负载**（当时工作区里有另一个 agent 在并行跑测试），但**未被受控实验证实**。
   - 判定：**未定位到产品缺陷，不报 bug**；属测试侧稳定性风险，按纪律登记。
   - 对策：① L1/L2 层（含子进程/真实 socket）**独占**运行；
     ② **下一个全量/分支 run 必须把输出 tee 到文件**（`... > test/artifacts/run-<ver>.log 2>&1`），
     这样第四次出现时堆栈不会再丢——本轮三次都只在 tail 输出里留下了 `FAILED` 行，这是我取证方式的缺陷。
