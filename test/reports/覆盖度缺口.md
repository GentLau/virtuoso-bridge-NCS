# 覆盖度缺口清单（模块 × 层）

> 维护者：测试工程师 ｜ 版本：v1.0 ｜ 2026-09-22
> 定位：回答"**哪些 `src/` 模块在离线层完全没有契约测试**"，是 [测试架构.md](../docs/测试架构.md) §3（能力域 × 层）的**模块级下钻**。
> 只登记缺口与证据，不写具体用例；补测计划另立。

## 1. 口径与方法

| 项 | 说明 |
|---|---|
| 统计对象 | `src/**/*.py`，去掉 `__init__.py` 后 **52** 个模块 |
| 离线层 | `test/offline/unit` + `test/offline/integration` + `test/offline/scenario`（= CI 同口径三层） |
| 真机层 | `test/**`（排除 `test/artifacts/**`） |
| 计数方式 | `rg -c "\b<模块叶子名>\b"`；`\b` 不把 `deploy_files` 算进 `deploy` |
| 可复现命令 | `rg -c -e "\bjsonutil\b" test/offline/unit test/offline/integration test/offline/scenario`（无输出 = 零引用） |

**两条限制，引用前必读：**

1. 这是**引用计数**，不是行为覆盖。计数 > 0 也可能只是 docstring 提了一句
   （例：`cellview` 的离线层唯一命中是 `test/offline/unit/test_skill_text_utils.py:3` 的说明文字）。
   故本清单**只采信零计数与 ≤2 的低计数行**；高计数行（`server`/`flow`/`roles`/`probe`/`models`）
   与英文常用词撞名，数值虚高，不作证据。
2. "离线层零引用" ≠ "完全没测"：间接覆盖与真机 TB 都可能有，但**真机 TB 不能替代离线契约**
   （代价：一条契约要真机 + 分钟级耗时才能验；且真机不可用时约定失真无人发现）。

补充事实（决定缺口优先级）：

- `common.jsonutil` 的 `loads_strict()` 是**顶层 HTTP 入口的解析器**（`register/server.py:109`、`api_server.py:100`），
  它拒绝 `NaN`/`Infinity` 属于输入安全控制，却零直接测试 —— 归口为**优先级最高的 L0 缺口**。
- `_spectre_util` / `_skillref_docs` / `_symbol_generate` / `_maestro_util` 都是**纯文本/纯结构处理**
  （PSF 解析、fnd/tgf 索引、SKILL 代码生成、maestro 结果解析），**不需要真机**即可确定性覆盖，
  是"投入产出比最高"的补测区。

## 3. 高危：同名函数双实现，单测只测其中一份

`pyapi/packages/basic.py:245-360` 与 `pyapi/packages/_maestro_util.py:18-202` 各定义了一套 SKILL 文本工具，
**7 个同名函数无一处字面相同**：

| 函数 | `basic.py` | `_maestro_util.py` | 字面相同 |
|---|---|---|---|
| `escape_skill_string` | 267 | 18 | 否 |
| `q` | 272 | 23 | 否 |
| `tokenize_top_level` | 277 | 130 | 否 |
| `scan_top_groups` | 310 | 167 | 否 |
| `parse_sexpr` | 316 | 177 | 否 |
| `parse_skill_str_list` | 338 | 114 | 否 |
| `is_single_complete_skill_list` | 360 | 202 | 否 |

**已知语义分歧**：`parse_skill_str_list` ——
`basic` 用 `tokenize_top_level(..., include_atoms=True)` 后按 token 递归展平；
`_maestro_util` 用 `include_atoms=False` 再走 `_collect_strings(parse_sexpr(token))`。
两者对同一输入是否等价，**尚无证据**（未做差分验证）。

**为什么这是测试问题**：`test/offline/unit/test_skill_text_utils.py:14` 只从 `basic` 导入这 7 个名字，
即单测绿灯**只证明了 basic 那一份**；而 maestro 的真机/生产路径用的是 `_maestro_util`
（`src/pyapi/packages/maestro.py:38`）。因此该单测对 maestro 路径提供的是**假信心**，
且两份实现已具备漂移条件（改一份不会红）。

**归属**：单一实现应由设计工程师判定（合一份 or 保留两份并说明差异），
测试侧相应补**差分用例**（同输入喂两份实现比对）或按定稿覆盖。已登记为 P-015。

## 5. 未覆盖与不确定项

1. **未做行为覆盖复核**：本清单是引用计数，不等于语句/分支覆盖。后续若要下结论"够不够"，
   需用覆盖率工具复算（与 [测试架构.md](../docs/测试架构.md) §4 的证据链配套）。
2. **未核对真机 TB 的间接覆盖深度**：需真机环境，本轮未跑。
3. **`pyapi.packages.demo`（离线 2 / 真机 21）** 判为示例包，未列为缺口；如它进准出范围需重新评估。
4. `_maestro_util` 的 20 个函数中，逐个名字在离线层的命中为 0 的有 13 个
   （`parse_detail_csv`、`parse_ocn_text`、`parse_overall_yield`、`natural_sort_histories`、
   `natural_sort_key`、`history_name_for_file`、`decode_skill_text`、`skill_value`、`skill_alist`、
   `skill_string_list`、`unquote`、`parse_bool`、`pairs_to_dict`），补测时按此清单切分。
