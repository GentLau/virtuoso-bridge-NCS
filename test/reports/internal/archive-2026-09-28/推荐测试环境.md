## 0. 真机实例的"启动即完整"要求（2026-09-23 起）

> 教训：run 目录只放 `.cdsinit`、cds.lib 用软链或干脆没有 → `verilog.import` 等依赖
> `<cwd>/cds.lib` 的流程会失败，看起来像产品缺陷。**真实用户的启动目录一定有 cds.lib。**

每个真机实例的 run 目录（`~/.virtuoso-bridge/<user>/run/`）必须同时具备：

| 文件 | 内容 | 说明 |
|---|---|---|
| `.cdsinit` | `load("<该用户>/setup/virtuoso_setup.il")` | 启动即自动拉起 bridge daemon（端口/token 由 setup 决定） |
| `cds.lib` | **真实文件**（不是软链）：场景自己的库 + 参考环境 `/home/Gent/project/test/cds.lib` 的标准库（TEST_BRIDGE / TEST_LIB / …） | 生成脚本：`python3 test/shared/runners/make_run_env_complete.py`（在 wsl-gent 上跑）。厂商库（analogLib/basic）交给 SOFTINCLUDE 的 Cadence setup，重复 DEFINE 会报 `OAVLG-10024` |
| `CDS.log` | Virtuoso 自己生成 | 留在 run 目录，不污染用户工程 |

**启动**（wsl-gent，示例）：

```bash
cd ~/.virtuoso-bridge/vblog/run
nohup ~/start_real_virtuoso.sh ~/.virtuoso-bridge/vblog/run \
      ~/.virtuoso-bridge/vblog/run/cds.lib :11 <任一在跑的 virtuoso pid> \
      > start.log 2>&1 &
```

**自检**（任一 CIW，全部回 `dd:0x…` 才算完整）：

```skill
ddGetObj("schemtest") ddGetObj("maestro_tb") ddGetObj("tsmcN65") ddGetObj("TEST_BRIDGE")
```

多用户协同场景（S2/S3/S6）共享**同一套完整库映射**，只按用户/端口/token 区分实例 —— 不各自造一套假环境。

### 0.1 业务面 8127 的注册表时效（踩过的坑）

`python -m server.api_server`（standalone）**只在启动时导入 registry**；改了 `registry.json`
（新注册用户 / 换 token）后旧进程会一直回 `invalid token`，看起来像"实例挂了"。

- **规范做法**：用 `python -m server.supervisor` 起双进程，改完注册表调控制面 `POST /api/process/reload`；
- **测试侧常用做法**：standalone 起 8127 时，**改注册表后重启该进程**（别去改产品口径）。
