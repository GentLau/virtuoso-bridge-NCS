## 1. 六步流程（顺序固定，不可跳步）

| # | 步骤 | 做什么 | 不通过怎么处理 |
|---|---|---|---|
| 1 | **检查环境是否为所需测试环境** | 断言当前环境就是本 TB 需要的那个（宿主/用户/实例/库/工艺/端口/token/解释器版本） | **TB 直接失败**（不是 skip、不是"换个环境凑合"）；日常环境优先，非日常需求写好 TB 后移交测试工程师准备 |
| 2 | **检查当前环境并构建测试环境** | 要读原理图就先有一张**要被读**的原理图；要写就先造出**要被写**的对象，并**还原到未写基线**（见 §3） | 构建失败 = 用例失败（不得吞掉后继续） |
| 3 | **最终检查环境** | 确认第 2 步的对象/视图/前置状态**都已就位且干净**（数量、命名、参数、锁、打开句柄） | 不干净 → 失败并打印现场（`ls`/`read` 摘要），禁止"带着脏现场跑" |
| 4 | **执行操作** | 只做被测动作；一次只动一个变量；破坏性动作前留可回滚路径 | 报错按 §4 判定归属 |
| 5 | **比对结果并记录（理想 vs 实际）** | **必须**读回/查询/测量被写对象（`*.read`、`read_results`、`spectre.measure`、`stat/sha256`、句柄查询…），把"期望值 vs 实测值"同时写进证据 | 只有 `ok:true` 没有比对 = **不合格**，视同未测 |
| 6 | **重复 4、5 直到本 TB 完结** | 多步场景逐步比对；**跑完不清理现场**（现场由第 2、3 步负责干净），但**必须在证据里记录现场状态** | — |

### 1.1 与 AAA 的对应

| AAA | 六步流程 | 反例（本轮评审抓到的形态） |
|---|---|---|
| **Arrange** | 步骤 1–3：环境检查 → 构建 → 完备校验 | 直接写 `place_*`（空画布恰好是干净基线）却从不构造 delete/rename/set 需要的**既有对象** |
| **Act** | 步骤 4 | 批量发操作、不看返回值 |
| **Assert** | 步骤 5–6：读回 + 比对 + 留证 | 只断言"生成的 SKILL 文本里有 `dbDeleteObject`"；或只断言接口 `ok:true` |

> 离线契约用例（`_atomic_skill` 文本断言）允许存在，但它只能证明**参数拼装**，
> **不得**在报告/矩阵里当作该原子"已覆盖"。参考 `test/offline/unit/test_schematic_contracts.py:209-257`。

## 2. 每个 TB 的证据要求

证据文件（JSON/日志）里必须能看出：

1. **环境指纹**：宿主 / 用户 / 实例端口 / token（或 work-dir+user）/ 库 / 工艺 / 解释器版本；
2. **前置现场**（步骤 2–3 的产物）：构造了什么对象、还原成了什么基线；
3. **动作清单**：发起了哪些操作（operation + 关键参数）；
4. **比对表**：每条断言的 `期望 / 实际 / 判定`（不是只有 `ok`）；
5. **后置现场**：跑完后对象/锁/句柄/端口/临时目录的实际状态（供步骤 3 复用与跨 TB 排查）；
6. **判据说明**：为什么这条算通过（例如"改图后带宽掉 3 倍以上"而不是"接口没报错"）。

证据放 `test/artifacts/evidence/<run-id>/`；命名与报告要求见 [证据与报告.md](证据与报告.md)。

## 3. 状态还原规则（cellview 是持久对象，不是无状态函数）

| 场景 | 规则 |
|---|---|
| 需要"空起点" | 用 `init_work_dir` 绑定的**场景目录** + 专用 lib/cell（`tb_<主题>_<runid>`），不要在共享库上直接跑 |
| 需要"已有对象"（delete/rename/set 类） | 步骤 2 **先造**该对象（place 或 fixture），步骤 3 校验它存在且参数符合预期，步骤 4 才改它，步骤 5 读回确认 |
| 共享库（`/project/libs/*`、`schematic`/`layout` 等公共 cell） | **只读**优先；必须写时用**专属 cell 名**（带 runid），并在证据里登记"我动了哪个对象" |
| 跑完 | **不清理现场**（便于复核与复跑定位），但把现场状态写进证据；下一次运行靠步骤 2–3 自行还原基线 |
| 幂等要求 | 同一 TB 连续跑两次必须都通过（第二次自己把基线还原） |

> 反例来源：P-073（rename 类长期无真机闭环）、P-072（`init_work_dir` 一次性化）、C0（delete/rename/set 系统性缺测）。

## 4. 结果判定的最小强度（防"发而不核"）

按被测对象选**最强可得的读回手段**，禁止只判接口 ok：

| 被测对象 | 最低要求 |
|---|---|
| 原理图写操作 | `schematic.read` 回读实例/网络/pin 列表，逐项比对 |
| 版图写操作 | `layout.read`（形状数/层/属性）或窗口查询；GDS 另有 `stat`/`sha256` |
| symbol 生成 | `symbol.read`（端口集合、pin_order）——**不含**"top 实例化成功"这种间接证据；间接证据要显式标注 |
| Calibre DRC/LVS | `calibre.read_results` 的结论（rulecheck 计数 / `CORRECT|INCORRECT`），不是 `ok` |
| Spectre | `spectre.measure` 的数值 + 物理合理性判据 |
| 文件传输 | 目标文件存在 + sha256/内容比对 |
| 句柄/锁/资源 | 运行前后查询（打开句柄数、`*.cdslck`、端口、临时目录）并给差异 |

## 5. 覆盖度要求（原子级，不只是能力域级）

`test/docs/测试架构.md §3` 的能力域表**不够**：一个包内 17 个原子，测过 `place_*` 不代表
delete/rename/set 也被测过（C0 的根因）。因此：

1. 报告与矩阵里引用"某包已覆盖"时，**必须**附原子级依据；
2. 每个写原子在 **semi 或 live** 至少有一条**符合 §1 六步 + §4 强度**的用例；
3. 原子清单与缺口由机器核账：`python test/shared/runners/audit_atom_coverage.py`
   （输出 `test/artifacts/evidence/atom-coverage-<date>.json`；`--fail-on-gap` 供将来入门禁）；
4. 新增/修改原子（`src/pyapi/packages/*.py`）后**必须**重跑该核账，把新原子并入清单。

## 6. 与分层/归口的关系

本规范**不改变**三级分层口径（见 [测试架构.md](测试架构.md) §2）：离线 / 半真机 / 真机。
它约束的是"每一级内部的用例怎么写"。级别的选择仍按：不需要真机 → 离线；需要真机但只验证单点 → 半真机；
按用户完整动作序列验收 → 真机。

## 7. 检查清单（提交 TB / 写报告前逐条打勾）

- [ ] 六步齐全，且步骤 2–3 有可复查的"构建 + 还原基线"记录；
- [ ] 每条断言都有 `期望 / 实际 / 判定`，没有"只判 ok"；
- [ ] 证据里有环境指纹与后置现场；
- [ ] 同一 TB 连跑两次都通过（或明确说明为什么只能跑一次）；
- [ ] 涉及写原子时，报告里给出该原子的**原子级覆盖状态**（本轮证据 or GAP）；
- [ ] 已知弱判据/间接证据在报告里**显式标注**，不写成"已验证"。
