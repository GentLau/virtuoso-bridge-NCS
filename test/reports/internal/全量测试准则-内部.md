# 全量测试准则（内部 · 草案 v0.3）

> 作者：测试/root ｜ 状态：**草案，待用户/评审确认后定稿** ｜ 日期：2026-09-30
> 定位：这是**测试完成度的判定标准**，不是 TB 写法说明。TB 怎么写见 `test/docs/写TB规范.md`（对外），
> 环境怎么用见 `test/reports/internal/环境Runbook-内部.md` 与 `test/docs/推荐测试环境.md`（对外）。
> 适用范围：每一轮"全面测试"（roundN）与任何新增功能的验收；评审驳回测试结论时，以本准则逐条对照。

## 0. 三条铁律（本准则的核心，其余条款都是它们的展开）

| # | 铁律 | 反例（本项目真实发生过） |
|---|---|---|
| **①** | *覆盖判定必须从原始 spec 出发**：先读 spec 抽出需求/条款，再回头查 TB 与证据**有没有**覆盖它。**禁止**"看 TB 反推需求""看实现反推需求"*。 | round8 只按已写的 TB 统计"覆盖了多少"，被评审判定"虚假覆盖" |
| **②** | **每个操作的每个输入参数都必须被覆盖**，且要有**实际执行证据**（半真机或真机）；一个操作要写**多档用例**（最简输入 / 日常输入 / 边界 / 非法），枚举型取值**一个不落**。 | `spectre.run` 的 5 个 mode 取值（`cx/ax/mx/lx/vx`）只有离线拼装断言，真机从未跑过 |
| **③** | **每个操作的每一个输出值都必须在六步 TB 的"读回比对"里逐项比对**（值级）；不许只判 `ok`、不许只判"非空"。没有读回面的，必须立"读回面/参数裁决"单，**不得默认放过**。 | C06：`print` 的返回值（`CDSlog`）没有任何 TB 校验 → 漏了一个 P2 缺陷 |

## 1. 覆盖层级（L0 / S1 / S2）与"什么算覆盖"

| 层级 | 含义 | 允许声称的结论 |
|---|---|---|
| **L0 离线** | 纯 Python、无真实环境（pytest `test/offline`） | 只能写"契约/拼装/错误语义已覆盖"，**不得**算该操作"已在真机覆盖" |
| **S1 半真机** | 真环境但不完整运行（探针、fake 对端、单步调试） | 写"半真机验证"；不可当作生产路径已通过 |
| **S2 真机** | **全真环境 + 全真操作路径**（标准拉起方式、业务拟真数据、真实用户能产生的操作序列） | 才能写"真机通过" |

硬性约束（来自用户多次强调）：

1. **任何与生产实际使用方式不一致的测试都没有意义**：真机必须用标准拉起方式（如 `server.supervisor` 控制面 8124 + 业务面 8127），
   不许用临时壳/测试专用服务冒充生产面（`stress_server` 类教训：已从源码删除，测试侧同步清理）。
2. **层层递进**：任一层出问题先停下修好再往上跑；上层红了不许用下层绿来"抵消"。
3. 离线契约**永远不能**替代真机覆盖；反过来，真机绿也不等于边界/错误语义已覆盖（两层都要）。

## 2. 三张表：覆盖检查的可追溯链（铁律 ① 的落地）

每轮全面测试必须产出并刷新这三张表；**没有表就不算做过覆盖检查**。

### 表 A · spec 条款表

逐条抽 spec（含 `spec/design-concepts/**` 与冻结设计文档），每行：

`条款编号 | 原文摘要（≤40字） | 类型（功能/契约/边界/错误语义/性能/安全） | 判据形态 | 覆盖 TB | 层级 | 证据路径 | 状态（绿/红/na/待改判）`

规则：

* **na 必须给理由**（"条款本身不要求证据"才可 na，不能因为"测不了"就 na）；
* **引用证据必须存在**（自动核对脚本 `test/shared/runners/verify_spec_matrix_evidence.py`；"引用文件不存在 0"是硬指标）；
* spec 变更后条款状态**必须重判**（本轮 30 条"变更后待改判"就是没及时重判的产物）；
* 现状工具：`test/reports/round9/spec_matrix_r9_audit.py`、`spec_live_evidence_r9.py`。

### 表 B · op × 参数表

每个 op 的每个可传参数一行：`op | 参数 | 取值域（枚举/范围/结构） | 覆盖用例 | 取值样例 | 层级 | 证据 | 状态`

规则：

* **零缺口**是目标：不允许"参数在请求模型里但没有任何 TB 触碰"（审计口径：未触碰 0 / 未覆盖枚举值 0）；
* **枚举值逐个覆盖**：如 `spectre.run.mode` 的 8 个取值，都要有成对用例（L0 拼装 + S1/S2 至少一次真跑；跑不动要写明原因并立卡）；
* **嵌套键也算参数**：对象/字典型参数的二级键（如 `commands[].label_pos`）同样按行登记，不许因为"在嵌套里"漏掉；
* 参数若无任何可观察效果 → **立"惰性参数"卡**（先例 C10 `place_wire.x_spacing/y_spacing`）；
* 现状工具：`test/shared/runners/build_op_param_matrix.py`、`test/reports/round9/nested_key_audit.py`。

### 表 C · 输出字段表（铁律 ③ 的落地）

每个 op 的**每个**返回字段一行：`op | 字段路径 | 期望语义 | 期望值来源（spec/设计推导） | 比对方式 | 判据强度 | 证据 | 状态`

规则：

* 判据必须能回答"**期望是什么**"——只写"非空/存在/ok"的判据视为**未比对**；
* `log`/`CDSlog`/`warnings`/`errors`/`steps` 这类**旁路输出同样算输出**，必须比对内容（C06 就是漏在这里）；
* 失败路径也要比输出形状（错误壳字段、错误码、`steps` 末步）；
* **产品没有公开读回面**的字段：状态写 `readback: none`，并在报告里显式列出，同时向设计提"补读回面 or 补 spec 说明"——**不许**算成"已比对"；
* 现状工具：`test/shared/runners/weak_assert_audit.py`（判据强度审计）。

## 3. 用例设计规范（铁律 ② 的展开）

1. **一个操作 ≥ 2 档输入**：最简输入（最小可用参数集）+ 日常输入（真实业务最常见形态）；写类操作再加 **边界**（极值/空/超长）与 **非法**（类型错/取值错/越权）各至少一档。
2. **不限制"一次只改一个变量"；要求的是"结论可归因"**：
   * 允许、也鼓励一条用例同时改多个变量（组合用例、真实业务操作本身就是组合）；
   * 只有当某条断言要用来**定位责任**（"这个红/绿到底是哪个变量造成的"）时，才需要能归因——
     要么另有一条只改该变量的用例，要么在用例注释里写明"这是组合用例、各变量的责任边界与已排除项"；
   * 反过来说：**不得**因为"改了一个变量就绿/红"就推断其它变量无关；跨变量组合（如 log_level × log_max_bytes、
     role 分主机 × 多用户）必须专门有用例。
3. **值级读回优先**：能用 DB 直读（`dbOpenCellViewByType ... "r"`）或 read 面回读就用它；不要用"接口返回 ok"代替；读回失败要当失败处理，不能降级成"跳过比对"。
4. **用例自洽**：每条用例有自己的唯一 cell/用户名/时间戳标记，可单独复跑，不依赖别的用例先跑过；共享库只读，写操作只写自己的命名空间。
5. **判据强度分级**：strong（值级/结构级）> medium（关系/数量）> weak（存在性/非空/ok）。weak 只能做辅助；发现 weak 要么补齐、要么登记进"待改写清单"，**不许留在正式结论里当覆盖**。
6. **skip 必须有原因**，且必须分类写清（`check_skip_reasons.py` 的"无原因 0"是硬指标）：
   * `平台分支`：如 POSIX-only / Windows-only 路径；
   * `环境限制`：**如 Calibre 侧的 license / 工具 / 夹具不可用** —— 这类由用户 2026-09-30 明确：
     **直接 skip + 写明"环境限制：<具体原因>"即可**，不当作缺陷、也不算覆盖；证据里保留探针输出；
   * `红钉`：产品缺陷未修时的 xfail（等修好转绿并删钉）。
   skip 清单要在本轮报告里**单列**（数量 + 每条的 reason），防止被误读成"已覆盖"。
7. **六步法不要求形式主义**：不适用的步骤写一行注释说明（如最简计算类无"构建"步骤），但**不允许缺步骤而不说明**。

## 4. 输出比对规范（铁律 ③ 的操作细则）

执行顺序（每个 op 都要过一遍）：

1. 从 spec + 请求/响应模型列出**该 op 的全部输出字段**（含嵌套字段）；
2. 逐字段写"期望值来源 + 比对方式 + 容差"；
3. 在 TB 第 ⑤ 步逐字段断言，并在证据 JSON 里保存 **期望 vs 实际** 对照（不是只存原始响应）；
4. 对**每一个**字段判定：值级通过 / 结构通过 / readback:none（并说明）/ 缺口（立卡）；
5. 汇总成表 C 的状态；收尾自检时**逐行**确认没有"未比对"。

**特别提醒（本项目血泪）**：`log`/`CDSlog` 这类"看起来不重要"的返回字段最容易漏；凡是 spec 写了语义的字段（增量、分级、限长、降级说明行、`unavailable` warning），都要有**内容级**断言，"数量/长度"断言只能算 medium。

## 5. 真机（S2）纪律

* 用**标准拉起方式**：`server.supervisor`（8124 控制面 + 8127 业务面）、注册表用户、真实 CIW；
* **单流执行**：同一时间只跑一套真机 TB（并发会触发 P-086 `Empty response` / `SKILL timeout` 窗口，本轮"大面积 timeout"就是并发造成的）；
* 跑前 checklist：CIW 健康（`basic.skill.execute("1+1")`）、无死锁 `*.cdslck`（属主 pid 已死的才清）、license 可用、目标实例未在跑别的 TB；
* 跑后：清理自己的远端工作目录与临时 cell（除非 TB 明确要求留证），确认无 `/tmp` 残留；
* 真机关键路径必须在**安静窗口**复跑一次，避免把环境抖动当产品结论（也不要把产品缺陷当抖动）。

## 6. 覆盖率口径（不虚高的写法）

1. 只引用**完整跑完**的官方 runner 数字（`test/shared/runners/run_main_coverage.ps1`），且必须带 provenance：`head` / `dirty` / `worktree_diff_sha` / Coverage.py 版本；
2. **不引用**残件、`--append` 增量、上一轮 JSON、以及 mtime 早于本轮开始的产物；
3. 若 runner 有失败步骤 → 只能写"**条件覆盖率**（含 N 个失败步骤）"，并列出失败步骤对应的卡；
4. 未跑到的模块要分类：真缺口 / 环境阻塞（env-blocked）/ 防御性代码（defensive）；**不许**把 env-blocked 算进"已覆盖"，也不许把它写成"未覆盖的缺陷"；
5. **不轻易宣布 100%**：任何 100% 结论都要能被逐条反证——列出未覆盖行/分支清单与理由；
6. 工具：`test/reports/round9/verify_coverage_r9.py`、`classify_uncovered.py`、`coverage_evidence.py`。

## 7. 缺陷、红钉与卡

* 发现缺陷**先立卡**，卡放 `test/reports/bugs/`；卡**可以手改**（测试侧维护，补现象/补充判据/补证据都直接写卡里），
  仅注意：`make_bug_cards.py` 重新生成同名卡时会覆盖手改内容，改完顺手同步源或先存一份即可；
* 卡必须含：可复现命令、期望 vs 实际、证据路径、归属（设计侧/测试侧）、级别；
* 产品缺陷同时落**红钉**（strict xfail 或专门 TB 的 FAIL 用例），由 `test/shared/runners/run_redpins.py` 判三态：`HOLD`（仍红，符合预期）/ `UNEXPECTED-GREEN`（已修复，转绿提醒删钉）/ `BROKEN`（钉本身坏了）；
* **关闭条件 = 可复跑证据**（跑一次转绿 + 证据路径写进卡），不能靠口头确认；
* 测试侧有权直接修**明显的 TB 缺陷**（假红/假绿/过时口径），但必须：① 更新注释头（作者改 `测试/root`、最后改动到分钟）；② 在本轮报告里记录改了什么、为什么。

## 8. 反例库（本轮踩过的坑，写进准则避免重犯）

| 反例 | 教训 | 正确做法 |
|---|---|---|
| **C06**：`print` 返回值没被任何 TB 比对 | 输出字段漏检 = 覆盖虚假 | 表 C 逐字段登记（§2、§4） |
| **C10**：`place_wire` 两个间距参数写完毫无效果 | "参数存在"≠"参数有效" | 惰性参数立卡（表 B 规则） |
| **假绿**：`B-sees-A-shapes` 比 `0 == 0` 判通过 | 相等类判据必须有下界 | 断言"A 侧 ≥2 且两边相等" |
| **假红**：`s11` TB 传客户端相对路径给远端 Calibre | 跨机路径必须绝对且校验 | 入参校验 + 明确报错 |
| **假失败**：calibre `pgrep -f <run_dir>` 判活（P-106） | 判活口径要与真实命令行一致 | 多路判活（命令行/cwd/报告文件） |
| **证据命名不一致**导致"今日无证据"误报 | 证据也是产物 | 证据文件名带 TB 名，统一放 `evidence/roundN/` |
| **报告数字与产物对不上**（50 vs 53 套） | 评审判"自相矛盾" | 收尾时用脚本刷新矩阵再抄数字 |
| **并发跑真机**导致大面积 timeout | 真机要单流 | §5 单流纪律 + 安静窗口复跑 |

## 9. 收尾自检清单（宣布"本轮完成"前逐项打勾）

1. [ ] 表 A：条款状态**无"待改判"**（或每条都有明确裁定人与去向）；
2. [ ] 表 B：参数**零缺口**，或每个缺口都有卡/裁定（惰性参数、readback:none 单独列）；
3. [ ] 表 C：输出字段**无"未比对"**；`readback:none` 清单已交给设计并写明；
4. [ ] 弱断言清单已登记（`weak-assertions.md`），本轮新增/修改的用例**不允许**引入新 weak 主判据；
5. [ ] skip **全部有原因**（`check_skip_reasons.py` 无原因 0）；
6. [ ] 三层结果各有本轮证据（离线 XML / 半真机日志 / 真机门禁结果），且**红项都对应卡**；
7. [ ] 覆盖率：只用完整 runner 数字 + provenance；失败步骤已列；条件覆盖率的措辞已写清；
8. [ ] 完整业务流程（至少 2 个真项目：SERDES RX、ADC/SAR 之类）本轮跑过并留证；
9. [ ] 台账一致：`make_bug_cards.py --check` 通过；卡与报告互相不打架；
10. [ ] 证据与报告**自洽**：报告里每个数字都能在产物里找到（用脚本核对，不靠记忆）；
11. [ ] 独立遗漏评审已做（换视角的 subagent 或交叉复核），结论写进报告；
12. [ ] 环境恢复**日常/常驻**状态（不留一次性实验环境）。

## 10. 待定稿需拍板的点（草案 → 定稿）

1. 表 C 是否要求覆盖**内部字段**（如 `steps[].detail` 的内部结构），还是只覆盖对外契约字段？
2. 参数枚举在真机跑不动时（许可/成本），允许的最低替代证据是什么（半真机？探针？）——目前按"必须真机，跑不动立卡 + 写明原因"执行。
3. weak 判据是否**一律重写**为 strong，还是允许"weak 辅助 + strong 主判据"并存（现按后者执行）。
4. 100% 覆盖的**禁止宣告**是否写成硬条款（现按"可宣告但必须给逐行反证清单"执行）。
5. 本准则是否要精简出一版**对外**（给设计与评审）的"测试完成度声明格式"（含三张表摘要口径）。
