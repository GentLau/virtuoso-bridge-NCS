# 两用户同视图读写语义 — 探针结论（2026-09-23）

> 探针：`test/semi/probes/twouser_same_view_probe.py`
> 证据：`test/artifacts/evidence/twouser-20260923T161213/twouser-same-view-red.json`
> 环境：`scenario-multi-user-s3`；账号 `vbmu2`（CIW pid 718632）/ `vbmu3`，两 CIW 共享 `TEST_LIB`。
> 本次只观察、不改产品代码。

## 1. 期望 vs 实测

| # | 场景 | 期望 | 实测 | 判定 |
|---|---|---|---|---|
| T1 | A 写完后 B 读 | 读到 A 的数据 | 读到 label `A1` | PASS |
| T2 | A 写完后 B 写同一视图 | 成功（A 不残留锁） | 失败：SCH-1003 “cellview is of a type other than schematic” | **FAIL** |
| T3 | A 写完后 A 再写 | 成功 | 成功 | PASS |
| LOCK | 写流程结束后的锁残留 | 无残留 edit 锁 | 残留 `sch.oa.cdslck.<host>.718632`（**A 自己的 CIW pid**） | **FAIL** |
| T4 | A 持 edit 时 B 读 | 成功（只读不受编辑锁影响） | 成功，读到 `A1` | PASS |
| T5 | A 持 edit 时 B 写 | 干净、可定位的锁失败 | 失败，但同样报 SCH-1003，无任何锁语义 | **FAIL** |

整体判定：**RED**（T2 / LOCK / T5 三条不符）。

## 2. 结论

1. **schematic.write 每个原子都 `dbOpenCellViewByType(...,"a")` 且从不 `dbClose`**：
   A 写完即留下自己的 edit 锁，B（另一 CIW）后续写被挡。与 layout P-044 根因 2 同源，
   symbol 的 `write` 同结构，预计同样存在。
2. **打开失败不中止、错误被吞**：`_open_edit_skill` 返回 `"open-failed"` 时
   `write` 只判断 SKILL 层面 `opened.ok`，继续执行原子；最终把“被别的会话锁住”
   伪装成 SCH-1003“cellview 类型不对”，排障方向被带偏。
3. **layout 的 P-044 修法方向错了，不能复制到 schematic/symbol**：
   已提交的修法改为每原子 `dbClose`。真机验证：`dbClose` 未保存会**丢弃改动**
   → `layout.write` 现在是“报 `ok=true` 但零落盘”的静默 no-op。
   现有 TB 已检出：`layout_e2e_tests.py --transport direct` → `rect not read back: {}`。

## 3. 为什么原 TB 没检出来

- 单用户 E2E 只断言“写一次 → 读回”，句柄泄漏不破坏单次写读回；
- 锁泄漏只在“另一会话写同一视图”或“写后盘点锁文件”时暴露，原 TB 没有这两类用例；
- layout 上一轮之所以红，是它自己后来加的 `_is_locked()` 预检把自己的残留锁
  误判成“another session”（P-044），并不是 TB 主动盯着锁语义。

## 4. 修法方向（待确认后再改）

1. write 整批合成**一条 SKILL**：一次 `open("a")` → 全部原子 → `schCheck`+`dbSave` →
   `unwindProtect` 兜底 `dbClose`（成功/失败路径都关）；不再逐原子 open。
2. 打开失败立即中止，并按“锁 / 不存在 / 类型不匹配”三态透传真实原因。
3. layout 回退 per-command `dbClose` 修法，改为上述整批 open→save→close；
   同一批内跨命令保持句柄，结束才关。
