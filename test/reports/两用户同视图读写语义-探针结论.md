> 环境：`scenario-multi-user-s3`；账号 `vbmu2`（CIW pid 718632）/ `vbmu3`，两 CIW 共享 `TEST_LIB`。

## 2. 结论

1. **schematic.write 每个原子都 `dbOpenCellViewByType(...,"a")` 且从不 `dbClose`**：
   A 写完即留下自己的 edit 锁，B（另一 CIW）后续写被挡。与 layout P-044 根因 2 同源，
   symbol 的 `write` 同结构，预计同样存在。
2. **打开失败不中止、错误被吞**：`_open_edit_skill` 返回 `"open-failed"` 时
   `write` 只判断 SKILL 层面 `opened.ok`，继续执行原子；最终把“被别的会话锁住”
   伪装成 SCH-1003“cellview 类型不对”，排障方向被带偏。
3. **layout 的 P-044 修法方向错了，不能复制到 schematic/symbol**：
   已提交的修法改为每原子 `dbClose`。真机验证：`dbClose` 未保存会**丢弃改动**
   → `layout.write` 现在是“报 `ok=true` 但零落盘”的静默 no-op。
   现有 TB 已检出：`layout_e2e_tests.py --transport direct` → `rect not read back: {}`。

## 3. 为什么原 TB 没检出来

- 单用户 E2E 只断言“写一次 → 读回”，句柄泄漏不破坏单次写读回；
- 锁泄漏只在“另一会话写同一视图”或“写后盘点锁文件”时暴露，原 TB 没有这两类用例；
- layout 上一轮之所以红，是它自己后来加的 `_is_locked()` 预检把自己的残留锁
  误判成“another session”（P-044），并不是 TB 主动盯着锁语义。

## 4. 修复（上层 `schematic/symbol/layout` 三包）

1. write 改为**一次 `open("a")`，句柄存 SKILL 全局变量**，各原子复用该句柄，
   末尾 `schCheck`/`dbSave`/`dbClose` 一次释放；命令失败、保存失败路径补 close。
2. 打开失败立即中止：schematic 返回 missing / type-mismatch / locked 三态；
   symbol / layout 在既有视图探测之上补 locked；错误文本明确“is locked by another session”。
3. 修复 `schematic._read_skill` 读后不 `dbClose` 的泄漏（读句柄残留会让其后 write
   的 edit 锁无法释放，是 T2 在“先读后写”序列下仍失败的直接原因）；
   `place_instance` 的 master 只读句柄同样补 close。
4. layout 回退 per-command `dbClose`（该修法丢弃未保存改动、造成静默 no-op），
   改为与 schematic 相同的整批 open→save→close。
