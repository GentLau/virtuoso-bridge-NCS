# 证据与报告

> 没有证据的结论等于没测；证据要能被别人离线复核。

## 1. 放哪、怎么命名

| 类型 | 位置 | 命名 |
|---|---|---|
| 机器可读证据 | `test/artifacts/evidence/<run-id>/` | `<主题>-red.json` / `<主题>-green.json` |
| 日志 | 同上 | `<套件>.log` |
| 可复用环境（work-dir / 注册表 / fake 群） | `test/artifacts/env/<name>/` | `registry.json`、`local-root/` |
| 零时产物（可随时删） | `test/artifacts/tmp/` | `.coverage*`、`*.out`、调试 dump |
| 远端工程产物 | `~/project/<user>/tb-out/<run-id>/` | 按产物名 |
| 截图/导出 | 同上 | `<主题>-<状态>.png` / `.vsdx` / `.gds` |

- 一个 run 一个目录，别散落；证据要含命令、期望、实测、时间、机器；**根层不许再出现散文件**。
- `test/artifacts/` 默认被 gitignore；要入库的关键证据用 `git add -f`，并在提交说明写明它支撑哪条结论。
- 环境与产物分开：`env/` 可被多轮复用，`evidence/` 一轮一份，`tmp/` 随时可整目录删除。
- 历史证据只增不改：新一轮用新 `<run-id>`。

## 2. 报告至少写清

1. 环境（节点、靶机账号、daemon 端口；token 不写明文）；
2. 客户端与并发数；
3. 用例构成（层、数量、随机种子）；
4. 期望 vs 实测（逐条）；
5. 失败归因（系统缺陷 / 环境缺陷 / 用例缺陷）；
6. 未覆盖项（PENDING 或豁免依据）；
7. 资源盘点（隧道、端口、临时目录、`ssh.exe` 基线）。

## 3. 红线

- 不用历史绿灯冒充本轮结论；
- 只能 PASS / FAIL / PENDING，没有"基本通过"；
- 不改证据文件，要改就重跑；
- 不把 token、口令、私钥写进报告或 artifact。
